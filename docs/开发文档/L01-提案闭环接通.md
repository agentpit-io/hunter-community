## 一、这一段解决了什么（人话）

改造前：系统会**定时复盘写经验**（`fin.review`）、**定时验证已提出的提案**（`fin.shadow`），
但**不会自己把攒下的经验变成提案** —— 那个能提提案的接口
`POST /internal/fin/evolution/proposal` 写好了却**全仓没有调用方**，
必须有人手工去调，自动闭环只闭了一半。

改变后：新增 `fin.propose` 工作流（**唯一调度权威**里的一条 Schedule），
按市场、对进行中的项目**自动、有闸门地**把可用经验变成提案；并补出「实验」实体
（方案 §12 时间线里缺的那一格「样本外 / 滚动验证」）。

**只自动「提」，不自动「生效」** —— `FIN_AUTO_APPLY` 恒 0 未动，生效仍要人工 `confirm=true`。

## 三、做了什么

### 3.1 新增 `fin.propose` 工作流（确定性编排，**零 LLM**）

- `apps/fin-worker/app/workflows.py` — `ProposeWorkflow`（`@workflow.defn(name="fin.propose")`）+
  `_propose_for_project`；登记进 `ALL_WORKFLOWS`。
- 流程：读日历 → 按市场取进行中项目 → 逐项目
  ① `propose_candidates`（**只读**：开关 / 预算 / 证据闸门全在 api 侧算）
  ② 逐条 `propose_submit`（走**唯一写入口**落库）。
- **逐条 catch**：一条候选失败（撞唯一索引 / 闸门拒绝）不挂别的候选、不挂别的项目。
- **不出现任何 LLM 调用**（方案 §5.2）。

### 3.2 接进调度（唯一调度权威）

- `apps/fin-worker/app/schedules.py` — 新增 `propose_specs()`，每市场一条 `fin-propose-<market>`，
  时点 = 该市场**时段末点 + 复核延迟 + 提案延迟**（`FIN_PROPOSE_DELAY_MINUTES`，默认 2），
  排在 `fin-review-<market>`（产经验）**之后**、`fin-shadow-<market>`（验提案）**之前**。
- `apps/fin-worker/app/config.py` — `propose_delay_minutes()`（可配，非法值回落 2 并留痕）。
- `docker-compose.yml` — 透传 `FIN_PROPOSE_DELAY_MINUTES`。
- **没有**另起 cron / APScheduler / threading.Timer（源码守卫 `test_no_fallback_cron_or_in_process_timer` 仍绿）。

### 3.3 「可用经验」的判定（沿用四期口径，不另发明）

`apps/api/app/services/fin/evolution.py` · `_eligible_evidence`：
`kind='verified'` + `status='已确认'` + `polarity='refute'`（**失败经验是自进化的燃料**，见 `0042` 文件头）
+ `sample_size >= FIN_PROPOSE_MIN_SAMPLE`（默认 20）。分组键 = `strategy_keys`。

证据**只从 `memory.query` 读**（`memory_svc.query`），一行 SQL 都不读 `fin_experience`；
落库时证据要求**一字未放宽**（仍走 `propose()` 的冻结快照 / 同项目 / 非 holdout / 时间边界四道校验）。

### 3.4 闸门

| 闸门 | 在哪 | 行为 |
|---|---|---|
| 经验库开关 | `switches.evolution_enabled(project_id)` | 项目学习强度为「关闭」/ 部署 `FIN_EVOLUTION_MODE=off` → **不提**，原因可见 |
| 预算 | `_budget_used()` + `FIN_PROPOSE_BUDGET_PER_WINDOW`（默认 **1** / 窗口 `FIN_PROPOSE_WINDOW_HOURS` 默认 **24h**） | 本窗口已提 ≥ 上限 → **不提**，原因可见 |
| 证据 | `_eligible_evidence` + `propose()` 原有四道校验 | 证据不足 → **不提**；`unknown` regime → **不提**（`R5` §一.2 规则 4） |
| 只收紧 | `_tighten()` + `propose()` 的方向判定 | 候选方向恒为 `tighten`；风控 `loosen` 在 `propose()` 里本就被拒（红线 8） |

### 3.5 「实验」实体（迁移 `0047`，**只追加**）

- `db/migrations/0047_evolution_experiment.sql` — `fin_evolution_experiment`：
  挂提案；记 **输入**（`data_snapshot_id` / 样本区间 / 成本模型 / 执行模型版本）·
  **方法**（文字 + 可重跑参数）· **结果**（数字，**算不出 `NULL`**）·
  **结论**（`pass` / `fail` / **`inconclusive`**）/ 负责人 / 时刻。
  `BEFORE UPDATE OR DELETE` 触发器 → 只追加。**不碰 `fin_evolution_plan`**（红线 10）。
- 唯一读写入口：`evolution.record_experiment` / `list_experiments`（服务模块里）。

### 3.6 只读入口（不改已有端点契约）

- `POST /api/internal/fin/evolution/propose-candidates`（内网口令；`fin.propose` 工作流用）
- `POST /api/internal/fin/evolution/experiment`（内网口令；只追加写实验）
- `GET  /api/v1/fin/evolution/experiments?proposal_id=...`（JWT，校验归属；跨用户 → 404）

## 四、偏离方案的决策与原因

1. **候选怎么生成（方案 §四 L01 只写「确定性聚合」，没写具体算法）** —— 本段落成：
   按 `strategy_keys` 分组，每组产出**一条**候选，把该策略在项目配置里的白名单参数
   （`strategies.<key>.params.<name>`，**字典序第一个**）朝**收紧**方向挪一个
   **白名单里已登记的 `max_step`**；该策略没有白名单参数 → 兜底顶层 `stop_loss_pct`。
   **理由**：`max_step` 是白名单里**已经登记**的界，用它不引入新阈值（红线 13）；
   方向恒为收紧（红线 8）；「字典序第一个」是**确定性排序**，不是「哪个参数更好」的启发式 ——
   后者要么需要一张未登记的「策略键 → 参数」映射表，要么等于替用户做参数决策（本段不做）。
   **已知局限**：同项目同一 `base_config_hash` 同时只允许一个待验证提案（`0043` 唯一索引），
   所以一次运行里第二条候选会撞 409 —— 预算闸门因此常常比唯一索引**更早**生效。
2. **为「探证据」先做一次不冻结的查询** —— 只在真有可用证据时才冻结快照。
   **理由**：测试栈有 500 个进行中项目，若对每个都冻结，一晚凭空写几百行 `fin_memory_snapshot`。
3. **默认值（写清依据，不当既成事实 · 红线 13）**：
   - `min_sample=20` —— 与 `DEFAULT_PLAN.min_comparable_sample`（R7 校准的 20）同口径；
   - `budget=1 / 24h` —— 受上面那条唯一索引约束，一天提一条以上几乎必然撞索引；1 是最保守的默认；
   - `window=24h` —— 一个自然交易日一个窗口；
   - `propose_delay=2min` —— 复核延迟（30）之后 2 分钟，只影响「早看还是晚看」，不改变判据。
   **样本 / 证据不足时保持「不提」**（实测见下）。
