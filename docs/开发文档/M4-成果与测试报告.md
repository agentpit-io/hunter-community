## 〇、一句话结论

**「能成交」变成了「可靠地自动成交」，而且「谁决定什么时候拉数据」这件事只剩一个答案：Temporal。**

- 六个交易时点（09:15 / 09:30 / 11:30 / 13:00 / 14:55 / 15:30）各是一个 Temporal 工作流，
  由 Temporal Schedule 驱动；**全仓再无第二条业务调度**。
- 现有 K 线 ETL 的**进程内 asyncio 定时循环已删除**，「何时拉」改由 Temporal 工作流调用
  **原来那个 `klines_etl.run_market`**（实现一行没改）。
- 杀 Worker → 重启：未完成的时点**续跑并完成**，`fin_trade` **仍然只有一笔**。

### 3. 六个时点工作流（M-14）

| 时点（上海） | 工作流类型 | 动作 | 打的 paper 端点 |
|---|---|---|---|
| 09:15 | `fin.point_0915` | 同步交易日历 + **T+1 日切** | `PUT /market-calendar/{d}` · `POST /projects/{id}/confirm-t1` |
| 09:30 | `fin.point_0930` | 固定示例策略出意图 → 提交委托 | `POST /orders` |
| 11:30 | `fin.point_1130` | 挂单再撮合 | `POST /projects/{id}/orders/match-open` |
| 13:00 | `fin.point_1300` | 挂单再撮合 | 同上 |
| 14:55 | `fin.point_1455` | 挂单再撮合（尾盘） | 同上 |
| 15:30 | `fin.point_1530` | 收盘撤单 → 估值 → 对账 | `orders/expire` · `/valuation` · `/recon` |

**六个时点是六个独立的 Workflow 类型**（不是一个工作流 sleep 六次）：Temporal UI 的
workflow 列表要能一眼看到「今天 09:30 那轮跑没跑」，一个类型带参数会让六个时点在列表里长得一样。

**交易日历**：`read_calendar` 三种结果分开处理（`app/gating.py`，纯函数，有用例）：

| 日历读数 | 动作 |
|---|---|
| `known=True, trading=True` | 继续 |
| `known=True, trading=False` | **跳过**（非交易日不触发） |
| `known=False`（没有这一天的日历） | **跳过 + 告警** —— 未知 ≠ 交易日，**绝不默认放行** |

**每个时点用 `fin_job.checkpoint` 记业务检查点**（新建了只写检查点的 paper 端点），
配合 M3 的 `fin_idempotency` 做到「重启续跑、不重复下单」。

### 4. 现有 ETL 的触发（本轮验收核心）

M0 报告 §2 的结论：现有 K 线 ETL 由 `apps/api/main.py:48` 的**进程内 asyncio 循环**触发
（不是 crontab、也不是人工）。照任务书处置：

- **删掉** `_klines_etl_loop()`（函数、`create_task`、关机 `cancel` 三段全删）；
- **实现函数一行不改**：新增 `POST /api/internal/etl/run-market` 直接调原来的
  `klines_etl.run_market(market, bars, 100, limit)`；
- 由工作流 `fin.market_etl` 调它，三个 Schedule（A 股 15:25 / 港股 16:45 / 美股次日 03:25 CST）；
- **没有留任何兜底 cron / 定时器**（`tests/test_workflows.py::test_no_fallback_cron_or_in_process_timer` 盯着）。

> ### 「现在谁决定什么时候拉数据」
>
> **Temporal。** 具体说：Temporal 服务端上的九个 Schedule（六个交易时点 + 三个市场的
> K 线 ETL）决定「什么时候」，被触发的工作流调用 `fin-worker` 的 Activity，
> Activity 打 `api` 的 `/api/internal/etl/run-market`，那个端点调用**原来那套**
> `klines_etl.run_market` 决定「怎么拉」。
> **`api` 进程里已经不存在任何业务定时器；宿主机也没有本项目的 crontab。**

### 5. 项目制与「开新项目」（M-16）

`apps/api` 侧新增（复用 M1 的 `services/fin/store.py`）：

| 端点 | 行为 |
|---|---|
| `POST /api/v1/fin/projects/new` | **先关旧、再开新**，同一个事务：旧项目落 `status='closed'` + `closed_at` + `close_reason`，并把 `status` / `close_reason` / `opened` 三条写进 `fin_param_change_log` |
| `GET /api/v1/fin/projects` | 该用户**全部**项目（进行中 + 已关闭）—— 「旧账本可回看」的读入口 |

## 二、偏离方案的决策与原因

### 偏离 1 · `fin-worker` **不注入 `DATABASE_URL`**（与 `08 §3.1` 的示例不同）

`08 §3.1` 给 fin-worker 配了账本库连接串。但那条连接串正是验收项「fin-worker 没有
`hunter_fin` 的写连接」要防的东西 —— 给它一条连接串、再靠「约定不写」保证边界，
就是把红线押在纪律上。M4 的做法是**依赖里根本没有 DB 驱动**（`requirements.txt` 里没有
psycopg2），写账本只有一个入口：`PAPER_BASE_URL`。`08 §十` 的对照表里
「§11.3 推理区 / 执行区隔离」这一条因此**比方案更硬**。

### 偏离 2 · 镜像 tag 按实测钉死

`08 §3.1` 写的是 `temporalio/ui:2.34`，但 Docker Hub 上**没有 `2.34` 这个 tag**，
实际叫 `2.34.0`（实测 `docker pull temporalio/ui:2.34` → `not found`）。
`temporalio/auto-setup:1.25` 与方案一致，可直接拉。
**两个 tag 现在都写死在 compose 里，不用浮动 tag。**

### 偏离 3 · `temporal` 的健康检查地址用**服务名**

`temporal-server` 只绑容器的网卡（实测 `ss` 显示 `172.22.0.5:7233`），**不监听 loopback**。
第一版健康检查写 `--address 127.0.0.1:7233` → 容器永远 `unhealthy`
（`connect: connection refused`）。改成 `--address temporal:7233` 后正常。
`temporalio/ui` 镜像**没有自带 HEALTHCHECK**，补了一条 `wget` 探测。

### 偏离 4 · 给 `paper` 补了三个 M3 交接里点名要的端点

| 端点 | 为什么 |
|---|---|
| `POST /api/v1/jobs/{id}/checkpoint` | 「每个时点用 `fin_job.checkpoint` 记业务检查点」——原来只有 `succeed` 能带 checkpoint |
| `POST /api/v1/projects/{id}/confirm-t1` | M3 报告「遗留 5/6」明确把 T+1 日切交给 M4；`ledger.confirm_t1()` 早就有，只缺入口 |
| `GET /api/v1/projects?status=` | 工作流要知道「今天为哪些项目干活」 |

三个都是 POST/GET，不违反 `test_append_only.py` 的方法集守卫；也不改任何历史行。

### 偏离 5 · 修了一个真实的脚本缺陷

`scripts/fin_provision_paper_role.sh` 里 `psql -c "ALTER ROLE ... :'pw'"` **不生效** ——
psql 的 `-v` 变量在 `-c` 里不做替换（实测报 `syntax error at or near ":"`），
也就是「一次性 provision」这条路本来是断的。改成 heredoc 走 stdin。

### 偏离 6 · **验收环境**把 `PAPER_SNAPSHOT_STALE_SECONDS` 放宽到 7 天

验收要跑「2026-09-30 那一天」的时点，而 `paper` 的新鲜度判定用的是**本机当前时刻**跟
快照时刻比 —— 2 天前的快照必然被判 `stale`（`missing_flag=true`），撮合走「不成交 → 挂单」。
为了能在历史交易日上验证「成交 → 崩溃 → 续跑不重复」，验收环境把阈值放宽到 604800 秒。
**生产默认仍是 900 秒不变**（`.env.example` 里是 900，本次放宽只写在本地 `.env` 里）。

## 三、本轮找出来并修掉的四个真实缺陷

**这四个都不是 review 看出来的，是「把容器真跑起来」逐个撞出来的** ——
换句话说，只跑单元测试它们会全部漏过。

### 缺陷 1（**最重要**）· 「读账户版本」与「提交」合在一个 Activity 里，崩溃重试必然 409

第一版 `run_decide` 一个 Activity 干三件事：读项目（拿 `version`）→ 造 `StrategyDecision`
（`expected_version=version`）→ 提交。崩溃续跑测试当场打脸：

```
WorkflowId fin-0930-2026-09-30  Status FAILED
Failure: paper HTTP 409: {"detail":"幂等键 fin-order:... 已被另一份内容使用过，拒绝覆盖（返回冲突）"}
```

**为什么**：第一次提交成交 → 账户版本 0 → 1；Temporal 重试 Activity 时**重读**项目，
拿到版本 1 → 同一个幂等键配上一份**不同内容**（`expected_version` 变了）→
paper 按 `01方案 §11.1`「同键不同内容 → 冲突，不覆盖」回 409 → 工作流**永久失败**。

**修法**：拆成两个 Activity ——
`build_decision`（**只读**，结果进 Temporal 历史）+ `submit_decision`（**有副作用**，
提交的是历史里那份**冻结命令**）。重试时命令逐字节相同 → paper 认出同键同内容 →
返回原回执。两条用例把这个陷阱钉住，其中一条是**反证**：
`test_rebuilding_the_decision_after_a_fill_would_conflict` 演示「如果按第一版写法会 409」。

### 缺陷 2 · `ScheduleSpec(timezone=...)` 字段名与 SDK 版本不符

真起容器时 `TypeError: ScheduleSpec.__init__() got an unexpected keyword argument 'timezone'`
（这个版本叫 `time_zone_name`）—— Schedule 一个都没建上，而错误只在容器启动日志里。
补了 `test_every_spec_builds_a_real_temporal_schedule`：**真构造一次 SDK 对象**。

### 缺陷 3 · 同步 Activity 必须配 `activity_executor`

`ValueError: Activity sync_calendar is not async so an activity_executor must be present`。
给 Worker 配了 `ThreadPoolExecutor(8)`（而不是把这些 Activity 改成 async ——
它们内部是阻塞 IO，异步化会把阻塞带进事件循环）。

### 缺陷 4 · `WorkflowIDReusePolicy` 导错了模块

`from temporalio.client import WorkflowIDReusePolicy` → `ImportError`（实际在 `temporalio.common`）。
只在真调触发端点时才炸。修法不只是改对路径，还把这两个 import **提到模块顶层** ——
这样 `test_api.py` 只要 import `app.api` 就能挡住同类问题。

### 4.6 ⭐ 杀 Worker → 重启 → 续跑且不重复下单（核心验收）

## 六、下一里程碑（M5 · 报告）交接

**第一件事**：`15:30` 时点（`close`）已经在跑「撤单 → 估值 → 对账」三步，
M5 的报告生成应该**接在估值之后**，作为同一个 `fin.point_1530` 工作流里的一步
（或紧邻的一个新时点）。`fin_report` / `fin_report_fact` 两张表 M1 就建好了。

**开工前必须知道的：**

- **时点工作流加步骤要小心 replay 兼容**：已经跑过的历史（比如今天那几条）在
  工作流的 `_run_for_project` 里少了一段，Temporal 重放会「对不上」。
  加步骤请放在**分支末尾**（现有的 `if point.kind == ...` 链后面再加一个 `elif`），
  不要插在中间；更安全的是给新步骤一个**新的时点 key**。
- **报告的数字必须来自 `fin_report_fact` 的逐行事实**（`01方案 §九`），
  AI 只写文字。校验是逐行比对，不是让模型自查。
- **`paper` 侧没有「生成报告」端点**，也没有必要加：报告是**表达层**，
  数据从 `/projects/{id}/valuation/latest` · `/trades` · `/cash` · `/recon` 读。
- 报告产物走 `hunter_artifacts`（`08 §五`）。
- **`agent_run` 里 `fin.point_1530` 那套口径（收盘撤单要在 `confirm_t1` 之前）不要动** ——
  M3 报告「遗留 5」：日切必须发生在没有挂单的时候。现在的顺序是
  09:15 日切 → 15:30 撤单，两条各自在自己的时点上，互不干扰。
- 测试跑法见 `apps/fin-worker/README.md`。**不要 `docker exec` 进容器跑长任务**（仓内铁律）。
