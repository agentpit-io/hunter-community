## 四、修错（五处，逐条补测试盖住）

### 4.1 `MemoryDisabledError` 文案打破了既有断言

草稿把文案从「经验库未启用（**FIN_MEMORY_ENABLED=0**）：…」改成「…（本部署的总闸为关，或这个项目的经验库开关是关）…」，
`tests/test_fin_switches.py::test_append_rejected_when_disabled` 断言 `"FIN_MEMORY_ENABLED=0" in str(exc)` → **当场红**。

**照实写的不许硬撑**：既有断言是对的（文案该点名是哪个闸）。改文案而不是改宽断言：
`经验库未启用（部署侧 FIN_MEMORY_ENABLED=0，或这个项目的经验库开关是关）：本部署当前不接受这个项目的经验写入`。
→ 既有用例逐字不变地过；新用例 `test_reason_required` 等不受影响。

### 4.2 `evolution.propose` 的 `project_id` 先判后归一

草稿写的是 `if not switches.evolution_enabled(project_id): …` **然后**才 `project_id = str(project_id or "").strip()`。
带前后空白的 `project_id` 会以**原样**当缓存键与 DB 查询键 → 读不到覆盖行 → **悄悄退回「只看天花板」**，
这个项目在界面上关掉了也照样提案。**修法**：先 strip、再判闸门。
→ 用例 `test_evolution_gate_per_project_but_ceiling_for_apply`（真库）盯住「本项目关 = 不提案、天花板不受影响」。

### 4.3 前端硬编码枚举（推翻草稿）

`10` §四 硬规矩 3 / R9 纪律要求「取值全部来自后端 `GET /v1/fin/runtime`，前端不写死任何枚举」。
草稿在 `_parts.tsx` 里硬编码了 `MODE_TEXT` / `MODE_SHORT` 与选项列表。

**改法**：后端 `switch_meta()` 返回**展示表**（`GET /v1/fin/runtime` 的 `meta` 字段）——
枚举取值、短标签、长说明、硬开关文案、「为什么灰」的说明，全部由后端给；前端只渲染。
表在 `switches.py` 改，前端一行不用动。
→ 用例 `test_meta_options_allowed_follow_ceiling` / `test_meta_paper_allows_everything` / `test_meta_off_locks_mode` / `test_meta_has_all_display_names`。

### 4.4 天花板之下的选项可点（推翻草稿）

`10` §四 出口标准 3：「天花板 `observe` → 界面**选不到** `paper`」。
草稿把 `paper` 画成可点，点了才被服务端 400 —— 用户会先看到一个能点的东西再吃一个错。

**改法**：`switch_meta()` 给每个选项算 `allowed`（`MODE_ORDER[值] <= MODE_ORDER[天花板]`），
前端把 `allowed=false` 的选项**画灰、点不动**（`Seg` 新增 `disabledValues`）。服务端仍会 400（两道一起拦，光灰不算）。
→ S8（HTTP）验了服务端那道；`test_meta_*` 验了展示表那道。

### 4.5 读取失败与「还在加载」不分

草稿在 `/runtime` 取不到时永远停在「正在读取运行设置…」。加 `loadFailed`（成长页与向导各自持有 `rtErr`），
真失败显「读取失败 —— 拿不到服务端的开关状态，这里不显示任何猜测值」（后端没给 `meta` 时同理），**不猜不编**。

## 五、S1 · 「关着也烧钱」实测（第一优先级的判断题）

**结论：草稿把守卫放在 api 侧是**对的**，`10` §3.1 判断的「关着照跑整条链、只在最后一步被拒、白烧模型」在本轮修法下不再发生。**

**读代码核实（三处）**：

1. `apps/fin-worker/app/activities.py:717 review_propose` → 只调 `HunterApiClient().review_propose(...)`，**不碰库、不直连模型**；
2. `apps/api/app/services/fin/review.py:401 _analyze_with_llm` → **模型在 api 里调**（`from app.providers.llm import get_llm`）；
3. `apps/api/app/routers/fin_review.py:83` → 守卫**排在 `await review_svc.run_review(...)` 之前**。

**实测（天花板 `FIN_MEMORY_ENABLED=0`，打 `POST /api/internal/fin/review/propose`）**：

```
POST /api/internal/fin/review/propose   (X-Hunter-Internal-Key: …)
{"project_id":"prj_r20a_9570","trade_date":"2026-10-02","market":"CN_A"}
→ HTTP 200
{"candidates":[],"used_fallback":false,
 "reason":"经验库未启用（本项目开关为关），跳过复盘提案",
 "rejected":[],"skipped":"memory_disabled"}

api 日志：
[fin.review] propose project=prj_r20a_9570 date=2026-10-02 跳过：经验库未启用（本项目开关为关），跳过复盘提案

整个 api 进程日志里 llm/provider/gemini/deepseek/openai 命中数 = 0（模型一次没调）
```

- **模型调用了几次**：**0 次**（全日志无 LLM 命中）；
- **`fin-worker` 报了什么**：propose 活动拿到 200 空候选 → 之后 `review_append` 拿 `candidates=[]` 走空循环，
  `memory_query` 在关着时返回 200 空集 —— **不报错、不 503**；
- **有没有重试**：没有触发（没有异常 → Temporal 不会重试）。

> 写进成果文档的**读法**：`10` §3.1 建议「在 fin-worker 三个工作流开头加守卫」。
> 实测表明**放在 api 的 propose 端点等价且更小** —— 因为花模型钱的那一步本来就在 api 里，
> 在它前面拦下就够；worker 三步里 collect / append 都是只读或空操作，不需要额外守卫。
> **没有推翻** `10` 的问题描述（关着确实会白烧模型），**改了的是落点**。

## 十、遗留问题

1. **`meta` 把「展示表」搬到了后端** —— 前端零枚举。将来加/改模式（若 `off/observe/paper` 之外还有别的），
   只改 `switches.MODE_META` 与 `switch_meta()`，前端不动。**别再把枚举写回前端**。
2. **缓存是模块级的**：api 单进程下「写入口清缓存 = 立刻生效」；多 worker 下最多差 5 秒。
   本机个人部署是单进程，实为立刻。**改多 worker 要换共享存储**（同 `screen_resort` 那条纪律）。
3. **`set_project_switch` 的 SELECT→UPSERT 不是原子的**：两个并发写同一项目时，`changed` 可能算错、流水可能多一行。
   本规模（点按钮）无所谓；**要串行化就上 `SELECT … FOR UPDATE`**。
4. **向导里一次改两项只带一个 reason**：`swPick` 记值、`swReason` 记最后一次输入的 reason，两项共用同一个 reason 提交。
   可接受（reason 是自由文本），若要求精细可给每项各配一个 reason 输入框。
5. **`daily-bar.time` 之类与开关无关**：本轮未碰。
