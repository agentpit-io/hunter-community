## 一、做了什么（人话）

产品定位是：**AI 智能体自己选股、自己交易；人工只在「想干预」时才介入**。改造前有两处默认值跟这个定位拧着：

1. **升级就起不来**：`HUNTER_EXEC_KEY` 是 `2.0.0`（L06）新加的**必填**项，老 `.env` 里没有它，
   `paper` / `fin-worker` **直接拒绝启动**。老客户升个级要先改配置、查文档 —— 不该这样。
2. **建了项目也下不了单**：执行允许名单（`fin_exec_allowance`）**默认拒绝**，
   而**只有一个人工接口能写入**、建项目**不会**顺带放行 —— 新客户装好、建了项目，
   AI 一张单也发不出去，得自己去登记。这跟「AI 自己跑」是拧着的。

本段两件事，各对准一条：

- **A · 执行凭证自动回退**：`HUNTER_EXEC_KEY` 没配（或为空）时，`exec_key()` **自动沿用**
  `HUNTER_INTERNAL_KEY`；配了就用自己的（想真正分开两把钥匙的人照样分得开 ——
  我们自己就是分开的，演示站也是）。
- **B · 执行允许名单默认放行**：**不动判据**，只保证「每个项目都有一条现行 active 的登记」——
  建项目时**同一事务**里自动追加一条；升级时用迁移 `0054` 给**历史项目**补齐。

**改完的效果**：老 `.env` 不用改就能升级；新建项目开箱即可交易；**人工仍能一条 `revoked` 收紧**。

## 三、设计

### 3.1 A · 凭证回退（口径与理由）

| | 改造前 | 改造后（L11） |
|---|---|---|
| `HUNTER_EXEC_KEY` 已配 | 用它 | 用它（**不被回退盖掉**） |
| `HUNTER_EXEC_KEY` 未配/空 | `exec_key()==""` → 自检拒绝启动 | **回退** → `exec_key()==read_key()` → 自检通过 |
| `HUNTER_INTERNAL_KEY` 也空 | 拒绝启动 | **仍拒绝启动**（回退无处可回退） |

- 落点：`apps/paper/app/config.py::exec_key()` 与 `apps/fin-worker/app/config.py::exec_key()`，
  实现就是 `return (os.getenv(EXEC_KEY_ENV) or "").strip() or read_key()`。
- **自检口径**（`selfcheck.py`，两个服务）：从「两把钥匙都必须非空」改成
  「**读取凭证必须非空；执行凭证按回退后的结果必须非空**」。只有读取凭证、没有执行凭证
  → **不再拒绝启动**（回退成同一把）。因为回退是「回退到**另一个环境变量**」而非「回退到常量」，
  所以两条问题同时只在「两把都没有」时出现。
- **不是放松判据**：回退只改变「没配时默认取哪把钥匙」，改不了「口令对不对」这条校验本身；
  想真正分开（拉行情的一条链路拿不到下单权限）就配 `HUNTER_EXEC_KEY`，配了就用自己的。

### 3.2 B · 允许名单默认放行（口径）

**判据一字不改**（`apps/paper/app/allowlist.py` 仍是「空表 = 谁都不许」，项目维度是硬闸门）。
本段只做「保证每个项目都有一条现行 `active` 登记」，两条路径：

1. **建项目即自动放行**（应用层 · 新项目）：`store._insert_project()` 在**同一事务**里追加
   `(scope='project', subject=<project_id>, status='active', granted_by='auto:project-create')`。
   与项目行一起提交 / 一起回滚。`create_project()`（幂等开户）与 `open_new_project()`（M-16）都覆盖。
2. **升级补齐**（迁移 · 历史项目）：`db/migrations/0054_exec_allowance_backfill.sql` 给
   **已在 `fin_project` 里、但在名单里没有现行 `active` 行**的项目补一条
   （`granted_by='auto:upgrade'`）。

保留人工收紧：登记一条 `status='revoked'` 即停（只追加、留痕，现成能力，未动）。

**被拒时一定出声**（`allowlist.check`）：抛出 `AllowanceDenied` 前打一条 `WARNING`，
写清「哪个项目 / 哪个工具 / 哪个维度被拒 / 该维度现行 active 都有谁 / 怎么放行」；
403 响应体同样带这些信息（不再只留一个数字）。**不新做界面**（任务书：没有合适提示位就只做后端日志 + 文案）。

## 五、未接与遗留

1. **`0054` 会给「升级前就已被撤销」的项目补一条 active**（§4.4 的 p4）。这是任务书口径
   （「没有现行 active 行」就补）的字面实现。**实践中没有这个场景**：允许名单是 `2.0.0`（L06）
   才有的功能，升级到本补丁时不可能有「更早的撤销」；且迁移**只跑一次**，升级后的撤销照旧生效。
2. **`api` 未补 GRANT**：确认 `api` 用的是库属主 `hunter`（对 `fin_exec_allowance` 有 INSERT），
   故不新增 GRANT 迁移（§二 写了判据与实测）。若将来把 `api` 的 DSN 换成一个**非属主、只读**的角色，
   需另加迁移授 `INSERT`（届时 `selfcheck`/迁移会先报缺权限，不会静默）。
3. **无界面改动**：任务书说「界面上若已有合适的提示位就一并加，没有就只做后端日志 + 响应文案」——
   没有为此新做界面。403 的文案与 paper 的 WARNING 日志已带全放行办法。
4. **`paper` 的 403 文案字面变了**（从「项目 X 不在执行允许名单…」到「执行被拒：项目 X 的
   place_order 不在…」）—— `L06` 成果文档 §6.3 里贴的是旧文案，属**历史记录不必追改**；
   唯一断言这条文案的用例（`test_allowlist.py` 的 `"不在执行允许名单"` 子串）**仍通过**。
5. **本机未做真浏览器**：本段无 `apps/web` 改动（`git diff -- apps/web` 为空），无界面可验。

## 六、怎么回滚

**代码回滚**（一步）—— 回到 `2.0.0` / `L10` 的行为：

```bash
git revert <本段提交 sha>        # 或 git reset --hard <本段的父提交>
# A：exec_key() 回退被撤销 → 又要求 HUNTER_EXEC_KEY 必填（老 .env 会起不来）
# B：新建项目不再自动登记；allowlist 判据本就没改，无需回滚
```

**注意（B 的两点，回滚代码≠自动收紧）**：

- 已经被 `auto:project-create` / `auto:upgrade` 放行的行**留在表里**（`fin_exec_allowance`
  是**只追加**表，触发器挡 DELETE），回滚代码**不会**把它们清掉 —— 这些项目仍然能下单。
