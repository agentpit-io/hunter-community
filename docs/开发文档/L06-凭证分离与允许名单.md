## 一、做了什么（人话）

方案 §7.4 要求：**不配置交易凭证；行情读取凭证与执行权限分离；模拟执行接口采用服务端鉴权、最小权限与允许列表。**
本段把两件欠账补上：

1. **两把钥匙分开**：**行情读取**用 `HUNTER_INTERNAL_KEY`，**下单执行**用新的
   `HUNTER_EXEC_KEY` —— **两个不同的环境变量、都没有默认值**，缺任一 `paper` / `fin-worker`
   **拒绝启动**。
2. **门改成「允许名单」**：`paper` 会改账本的四个端点（下单 / 撤单 / 批量撤单 / 再撮）入口先查
   `fin_exec_allowance`（新表，**只追加**）—— **空名单 = 谁都不许**，要**显式登记**才放行
   （`POST /api/v1/exec-allowances`）。实盘字段的**拒绝名单**（`LIVE_FIELD_DENYLIST`）**继续保留**，
   两道防线都在。

自证：`GET /healthz` 除了「模式 `PAPER`」，多报一个 **执行允许名单的现行条目数**（`exec_allowances`）。

## 三、设计

### 3.1 两把钥匙（环境变量名 + 取自不同变量的证据）

| 钥匙 | 环境变量 | 谁读它 | 干什么 |
|---|---|---|---|
| **行情 / 数据读取** | `HUNTER_INTERNAL_KEY` | `paper` 的 `config.read_key()`（`snapshot/source.py` 用）· `fin-worker` 的 `config.read_key()`（`bridge/hunter_api.py` 用）· api 的内网数据面（既有） | 拉行情 / 取数 |
| **下单执行** | `HUNTER_EXEC_KEY` | `paper` 的 `config.exec_key()`（**执行门** `security.require_internal_key` 用）· `fin-worker` 的 `config.exec_key()`（`bridge/paper.py` 用） | 下单 / 撤单执行 |

**取自两个不同变量的机器可读证据**（变量名，不读值）：

```
$ grep -n "READ_KEY_ENV\|EXEC_KEY_ENV" apps/paper/app/config.py
33:READ_KEY_ENV = "HUNTER_INTERNAL_KEY"
34:EXEC_KEY_ENV = "HUNTER_EXEC_KEY"
   ...（assert READ_KEY_ENV != EXEC_KEY_ENV：tests/test_keys.py）

$ grep -n "config.read_key()"  apps/paper/app/snapshot/source.py     → 178: self._key = ... config.read_key()
$ grep -n "config.exec_key()"  apps/paper/app/security.py            →  44: expected = config.exec_key()
$ grep -n "config.exec_key()"  apps/fin-worker/app/bridge/paper.py   →  45: self._key = ... config.exec_key()
$ grep -n "config.read_key()"  apps/fin-worker/app/bridge/hunter_api.py → 37: self._key = ... config.read_key()
```

**执行门只认执行钥匙**：`tests/test_keys.py::test_exec_gate_accepts_exec_key_rejects_read_key`
用**两个不同的值**证明「拿行情读取凭证下单 → 401；拿执行凭证 → 通过」。真机实测：

```
$ curl -X POST .../api/v1/orders -H "X-Hunter-Internal-Key: <读取凭证>" ... → HTTP 401 {"detail":"internal auth failed"}
$ curl -X POST .../api/v1/orders -H "X-Hunter-Internal-Key: <执行凭证>" ... → 进业务逻辑（见 §六.3）
```

### 3.2 执行允许名单（表 + 判据）

**表** `fin_exec_allowance`（迁移 `0051_exec_allowance.sql`，**权威**；`apps/paper/app/aux_ddl.py`
是 paper 启动时的兜底副本，两处由 `test_l02_single_source.py` 比对）：

```
allowance_id BIGSERIAL PK · scope ∈ {project, instrument, tool} · subject TEXT
· status ∈ {active, revoked} · granted_by TEXT · granted_at TIMESTAMPTZ · note TEXT
```

- **只追加**：触发器 `fin_exec_allowance_immutable` 挡 `UPDATE` / `DELETE`；撤销 = **再追加一条
  `status='revoked'`**（留痕）。某 `(scope, subject)` 的**现行状态** = `allowance_id` 最大的那行的 `status`。
- **权限**：`GRANT SELECT, INSERT ON fin_exec_allowance TO fin_paper_rw`（+ 序列 `USAGE`）——
  **不授 UPDATE / DELETE**，`paper` 自检把它列进 `APPEND_ONLY_TABLES` 强校验。

**判据**（唯一实现在 `apps/paper/app/allowlist.py`）：执行 `(project_id, code?, tool)` 时逐维查表 ——

- **项目维度是基础闸门**：必须有现行 `active` 且 `subject` 命中 `project_id`（或显式通配 `'*'`）的行，否则 **403**；
- **标的 / 工具维度是附加约束**：**只有当该维度存在现行 active 行时才生效**（有人登记过才管）；
- **空表 = 谁都不许**（默认拒绝）。`'*'` 是**显式登记的通配**，不是默认放行。

`scope=tool` 的取值 = `place_order` / `cancel_order` / `expire_orders` / `match_open`
（`allowlist.py` 里的唯一字面量来源）。

**登记入口**（`apps/paper/app/routers/exec_allowances.py`，与其余路由同一把**执行门**保护）：

| 方法 | 路径 | 用途 |
|---|---|---|
| POST | `/api/v1/exec-allowances` | 登记一条放行 |
| POST | `/api/v1/exec-allowances/revoke` | 登记一条撤销（留痕，不删） |
| GET | `/api/v1/exec-allowances` | 看现行清单 + 登记流水 |

**鉴权（401）与授权（403）分开**：进路由前的 `require_internal_key` 管「有没有执行钥匙」→ 401；
路由里的 `allowlist.check` 管「这次执行被没被授权」→ 403。

## 四、偏离方案的决策与原因

### 4.1 行情读取凭证**沿用** `HUNTER_INTERNAL_KEY`（没有新建 `*_READ_KEY`）

`plan/L06.md` §1.1 举例 `*_READ_KEY` / `*_EXEC_KEY`。这里**只新建了执行钥匙**，行情读取凭证沿用既有
环境变量名 `HUNTER_INTERNAL_KEY`，理由：

- **它本来就是「内网读取口令」**：全部 `apps/api` 内网端点（数据面 `fin_data` / `fin_*` 与工具通道
  `internal_uzi` / `internal_ocr` …）、`apps/web` 的 BFF、`scripts/opencode-mcp/*`、部署向导
  （`apps/api/app/services/setup_probe.py`）读的都是它。**把它整仓改名**会牵动 opencode 的 MCP 副本
  （它靠 bind mount 覆盖镜像、与 huntercode 必须逐字一致，见仓内 CLAUDE.md）、web 入口脚本
  （`apps/web/entrypoint.sh`）、部署向导与**所有既有部署**的 `.env` —— 远远超出本段范围，
  且会把「改个钥匙名」变成一次有回归风险的迁移。
- **方案要的是「两把钥匙分开」**，不是「两个都必须叫新名字」：改造前**一把钥匙同时管拉行情和下单**，
  改造后**读取 = `HUNTER_INTERNAL_KEY`、执行 = `HUNTER_EXEC_KEY`**（两个不同变量、不同值）。
  §六的验收项「确实取自两个不同环境变量」逐条满足。
- 名字的语义靠 `config.read_key()` / `config.exec_key()` 两个访问器讲清楚，且在
  `paper/config.py` 顶部写明了「为什么没改名」。

若后续确认要把它也改名（`HUNTER_READ_KEY`），只需：改 `apps/{paper,fin-worker}/app/config.py`
的 `READ_KEY_ENV` 常量 + api 内网端点的 `os.getenv` + `.env*` + opencode 副本 —— **一处常量改动牵动面上列的全部读取方**，
本段的 `READ_KEY_ENV` 常量就是为这次改名预留的单一改点。

### 4.2 项目维度是硬闸门，标的 / 工具维度是**条件**闸门

要求「哪些项目 / 标的 / 工具可以执行」。若三维都硬性要求登记，一次下单要先把**每一只标的**都登记，
不现实。故：**项目必须登记**（项目数少、是可枚举的主体），**标的 / 工具「有人登记过才生效」**——
空则不额外限制，有则收窄。**空表仍然谁都不许**（项目维度就挂了）。

### 4.3 允许名单里**支持显式通配 `'*'`**

登记 `('project','*')` = 放行所有项目。**这是一条显式登记**（有人签了字），不是代码里的默认放行 ——
与红线「默认空名单 = 更严、不许为了不破坏测试就放全」不冲突（默认仍然是空）。

### 4.4 老测试用**登记**通过，不改默认

`apps/paper/tests/conftest.py` 加了一个 session 级 autouse fixture：有 `PAPER_TEST_DSN` 时，向测试库
**追加一条** `(project, '*', active)` 登记（`WHERE NOT EXISTS` 去重），让既有下单类用例照常跑。
**这是「给测试环境补登记」，不是「把默认改成放行」**——生产默认仍是空 = 谁都不许。

## 五、升级后需要先登记什么（⚠️ 给运维 / 演示站）

升级到 L06 后：

1. **配第二把钥匙**：`.env`（或云平台模板）里**新增** `HUNTER_EXEC_KEY`（`openssl rand -hex 32`），
   **必须与 `HUNTER_INTERNAL_KEY` 取不同的值**。缺任一把，`paper` / `fin-worker` 起不来。
   `.env.example` / `.env.personal.example` 已加这两行与说明。
2. **给要下单的项目登记**（否则一律 403）：
   ```
   curl -X POST "$PAPER/api/v1/exec-allowances" \
     -H "X-Hunter-Internal-Key: $HUNTER_EXEC_KEY" -H 'Content-Type: application/json' \
     -d '{"scope":"project","subject":"<project_id>","granted_by":"<你>","note":"升级后登记"}'
   ```
   想再收紧就加 `scope='instrument'` / `scope='tool'` 的行（登记过才生效）。

**本机开发栈已登记**：`prj_m4test`（`(project,'active')`，流水含一次撤销再登记，见 §六.4）。
**演示站 / L10 部署时**：要对实际使用的每个 `project_id` 各登记一条；**不登记 = 下不了单**（这是设计）。

## 九、给 L07 的交接

- **L07（发布适配器 + `UNKNOWN` 待核实）不涉及凭证与允许名单**：发布出口（站内 / Webhook / 文件）
  不经过 `paper`，也**不下单**，无需登记。别把「发布」当执行去查名单。
- 若 L07 的 Webhook 出站要带内网口令回调 api，用**读取凭证**（`HUNTER_INTERNAL_KEY`），
  不要用执行凭证 —— 执行凭证只属于「打 paper 下单」这一条链路。
- `allowlist.TOOL_*` 四个常量是「哪些动作算执行」的唯一来源；**L08 加控制通道入口时，
  若新增会改账本的动作，要同步想清楚它是不是 `tool` 维度的一员**。
