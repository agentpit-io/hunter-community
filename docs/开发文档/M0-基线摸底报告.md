## 2. 现有 ETL 的真相 —— **本轮最重要的一条**

### 2.1 触发方式：进程内 asyncio 循环（不是 cron、不是前端点）

**定义**：`apps/api/main.py:48`

```python
async def _klines_etl_loop():
    """每 10 min 检查一次 · 在收盘后的触发窗口内跑 klines_etl. ..."""
    _last_trigger = {}  # 防止同一触发窗口内重复跑(键: 市场 → 日期)
    while True:
        ...
        now = datetime.now(CST)
        hour_min = now.hour * 60 + now.minute
        weekday = now.weekday()
        is_trading_day = weekday < 5
        if is_trading_day and 925 <= hour_min <= 940 and _last_trigger.get('cn') != today:
            await asyncio.to_thread(klines_etl.run_market, 'cn')
        elif is_trading_day and 1000 <= hour_min <= 1015 and _last_trigger.get('hk') != today:
            await asyncio.to_thread(klines_etl.run_market, 'hk')
        elif 205 <= hour_min <= 220:
            ...
            await asyncio.to_thread(klines_etl.run_market, 'us')
        await asyncio.sleep(600)  # 10 min 检查一次
```

**挂载**：`apps/api/main.py:176`

```python
_klines_etl_task = asyncio.create_task(_klines_etl_loop())
logger.info("[klines.etl] 每日 ETL loop 已挂载(A股 15:30 · 港股 17:00 · 美股次日 03:30 CST)")
```

挂在 `HUNTER_MINIMAL_BOOT` 那道门**之前**（`main.py:190` 才是 `if HUNTER_MINIMAL_BOOT: ... yield; return`），
所以**生产上（`HUNTER_MINIMAL_BOOT=1`）它照样跑**。`main.py:259-261` 在关机时 `cancel()` 它。

**窗口实测换算**（`hour_min = hour*60+minute`，东八区 `CST`，`main.py:44`）：

| 市场 | 代码窗口 | 含义 | 挂载日志写的 |
|---|---|---|---|
| A 股 | `925..940` | 15:25–15:40 | 15:30 ✓（近似） |
| 港股 | `1000..1015` | **16:40–16:55** | **17:00 ✗（日志与代码不符）** |
| 美股 | `205..220` | 03:25–03:40（次日） | 03:30 ✓（近似） |

> 注：`main.py:177` 的日志字符串写「港股 17:00」，而代码窗口是 16:40–16:55。**日志与实现不符**，是 M1 接手时要顺手澄清的小坑。

### 2.4 `klines_etl_log` 与「水位」

表结构：`db/migrations/0008_klines_etl.sql:27-39`

### 2.6 结论（可直接用于 `08 §1.3` 的「接管 vs 合并」）

**现有 K 线 ETL 是「数据面实现」+「进程内定时器」的合体。** 按 `08 §1.3` 的分类：

| 类别 | 现状 | 处置（照 §八） |
|---|---|---|
| 数据连接与内部任务（拉 K 线、UPSERT、写 `klines_etl_log`） | 在 `services/data/klines_etl.py` | **保留**，Temporal 工作流内部调用它 |
| 计划触发（谁决定什么时候拉） | **`main.py:48 _klines_etl_loop` 的进程内 asyncio 循环** | **删掉这个 loop**，改由 Temporal 按交易日/批次触发 |
| 兜底 cron | 无（宿主机无 crontab） | 本来就不存在，**不要新建** |

→ 不是「cron 换成 Temporal」，而是**「删一个进程内 while True 循环，换成 Temporal 工作流调同一个 `run_market` 函数」**。
这比方案设想的更干净：没有 cron 要停，也没有系统级定时器要迁移。

## 5. 迁移机制

### 5.1 执行方式（`apps/api/app/migrate.py`）

- **两阶段**（模块 docstring `:20-27`）：① `app.services.database.init_db()` 建基础表 →
  ② 按文件名顺序跑 `db/migrations/*.sql` 里**没跑过的**。顺序不能反（有 7 个迁移的目标表是 `init_db()` 建的）。
- **advisory lock**：`ADVISORY_LOCK_ID = 8700181780438093709`（`migrate.py:82`），
  会话级 `pg_advisory_lock`（`:408`），解锁 `:447`。
  锁值 = `sha256(b"hunter-community.schema_migrations")[:8]` 取大端再 `& ((1<<63)-1)`。
  **源码明写「不要改这个值」**（`:78-80`）——改了滚动更新时新旧容器会各拿一把锁、互不排斥。
- **账本表**：`schema_migrations(filename PK, checksum, applied_at)`，
  DDL 在 `migrate.py:121`（`SCHEMA_MIGRATIONS_DDL`）与 `db/migrations/0022_schema_migrations.sql` **各一份，必须一致**。
- **checksum 变了只 WARNING 不重跑**（`0022_schema_migrations.sql` 注释）：已生效的 DDL 重跑可能改坏数据。
  要改就**新增迁移文件**。
- **迁移目录**：`DEFAULT_MIGRATIONS_DIR = "/opt/hunter-migrations"`（`migrate.py:100`），
  可用 `HUNTER_MIGRATIONS_DIR` 覆盖；找不到时按仓库内相对路径兜底（`:144-151`）。
  **该路径由 `apps/api/Dockerfile:81` `COPY db/migrations /opt/hunter-migrations` 提供**，
  Dockerfile 注释原话「⚠️ 路径 /opt/hunter-migrations 是迁移执行器写死读的位置,**不要改名**」。
- 连接重试：60 秒内每 2 秒重试一次（`:64-65`）。
- 退出码：全成功 0；任一步失败非 0 → `boot.sh` 的 `set -e` 让容器起不来（**故意**，`:31-33`）。

### 5.2 启动时怎么被调用

`apps/api/Dockerfile:96`：`CMD ["/app/boot.sh"]`（不是 uvicorn，注释 `:95` 写明「直接 CMD uvicorn 的话,迁移永远不会跑」）
→ `apps/api/boot.sh:207-209`：
```sh
# 由 M1 子任务 B 提供 app/migrate.py;失败必须让容器起不来,
python -m app.migrate
```
→ 然后才起 uvicorn。`docker-compose.yml` postgres 服务的注释确认：
「迁移改由 api 启动时执行:镜像自带 /opt/hunter-migrations,boot.sh 调 python -m app.migrate」。

**`db/migrations` 不再挂给 postgres 的 initdb**（compose 里那段挂载被显式删掉，注释在 `docker-compose.yml:34-38`）。

### 5.3 `0022` 之后能不能安全加 `0023`？**能**

- 现有最大编号 = `0022`（`ls db/migrations/*.sql` 23 个文件，编号 0001…0022）
- ⚠️ **编号 0020 有两个文件**：`0020_rs_history.sql` 与 `0020_screen_learned_phrase.sql`。
  `list_migration_files()` 按**纯文件名字典序**排（`migrate.py:170-175`），`rs_history` 在前 —— 结果确定、可复现。
- 新加 `0023_fin_core.sql` 会被 `sorted()` 排在最后，`schema_migrations` 里没有它 → 下一个启动它的 api 容器就会执行。
- 唯一要遵守的规矩（CLAUDE.md 铁律 + 本仓既有约定）：**幂等**（`CREATE TABLE IF NOT EXISTS` / `ADD COLUMN IF NOT EXISTS`），
  且**已有部署不会跑 `db/migrations` 里的旧文件**（那是历史，只对全新安装 + initdb 留档）——
  所以「随代码走的 DDL」要不要写进 `db/migrations` 需要两处都放（`migrate.py` 会跑它，所以放这里即可生效）。
- ⚠️ 顺序坑（CLAUDE.md 有专条）：**往已有 `_DDL` 里追加 `ADD COLUMN` 时必须放在那张表 `CREATE` 的后面**，
  且在**空库**上跑一遍验幂等 —— 只在线上库验，顺序错了也是绿的。

## 7. 标的元数据（涨跌停 / ST / 板块）

### 7.1 `company_master`（`db/migrations/0012_company_master.sql`）

```sql
CREATE TABLE IF NOT EXISTS company_master (
    stock_code   VARCHAR(20) PRIMARY KEY,   -- 裸 6 位,如 600519（不带 .SH/.SZ 后缀）
    name         TEXT,
    industry     TEXT,
    market       VARCHAR(8) DEFAULT 'cn',    -- cn / hk / us
    board        VARCHAR(16),                -- 沪主板/深主板/创业板/科创板/北交所
    listed_date  DATE,
    updated_at   TIMESTAMPTZ DEFAULT NOW()
);
```

- ✅ **有 `board`**（创业板/科创板/主板/北交所）—— 涨跌停幅度可以**间接推**（创业板/科创板 20%，主板 10%）
- ❌ **没有 `limit_up_pct`**（没有显式的涨跌停幅度列）
- ❌ **没有 `is_st`**（没有 ST 布尔列）
- ST 现在**靠名字查**：`0012` 文件头注释（`:4-6`）写着 `filters.py` 执行
  `SELECT stock_code FROM company_master WHERE stock_code = ANY($1) AND (name LIKE '%ST%' OR name LIKE '%退%')`

### 7.2 `stock_universe`（在 `db/migrations/0008_klines_etl.sql:43-50`）

```sql
CREATE TABLE IF NOT EXISTS stock_universe (
    code     VARCHAR(20) PRIMARY KEY,
    market   VARCHAR(8) NOT NULL,
    name     VARCHAR(64),
    enabled  BOOLEAN DEFAULT TRUE,
    added_at TIMESTAMPTZ DEFAULT NOW(),
    priority INT DEFAULT 100
);
```
→ **只有 `priority` 是它独有的东西**（1 = 核心必跑，100 = 普通）。涨跌停 / ST / 板块信息**一个都没有**。

### 7.3 结论与最省事的补齐路径（**本轮不补**）

§八第 7 项要求「从 `company_master`（0012）/ `stock_universe`（0008）同步进 `fin_instrument`；
同步不上就**拒绝该标的**，绝不猜涨跌幅」。实测：

| 需要的信息 | `company_master` | `stock_universe` | 结论 |
|---|---|---|---|
| 板块（board） | ✅ 有 `board` 文本列 | ❌ | **可同步**（但需映射成创业板/科创板/主板的枚举） |
| 涨跌停幅度 `limit_up_pct` | ❌ 无 | ❌ 无 | **缺** |
| ST 标记 `is_st` | ❌ 无（只有 `name LIKE '%ST%'`） | ❌ 无 | **缺**（可派生，但"今天戴帽"≠"历史戴帽"） |

**最省事的补齐路径（供 M1 决定，本轮不动手）**：

1. **`is_st`**：加一列 `is_st BOOLEAN`，在**采集 `company_master` 的那次写库**里由 `name LIKE '%ST%'` 派生落列
   （现状是每次查询现算，落列后 `fin_instrument` 同步就有了）。
   ⚠️ 小鹿 A 股涨停线（CLAUDE.md §9-c）已经踩过：「ST 按**今天**的简称判，历史戴帽摘帽时点拿不到」——
   这是**已知局限**，落列不解决历史，只解决"今天"。
2. **`limit_up_pct`**：**不要新增数据源**（§八「要花钱的一律不做」）。
   按 `board` + 日期规则算：
   - 创业板 / 科创板（含 ST）：20%
   - 沪深主板：10%（ST 2025-07-07 起 10%、之前 5%）
   - 北交所：30%
   - ⚠️ 这套规则**仓内已有实现可抄**：`apps/api/app/services/quant/agent_limitup.py` 的 `limit_of(..., on=日期)`
     （CLAUDE.md §9-c 记录了它踩过的坑：300044 创业板 *ST 涨 10.29% 曾被误判涨停）。
3. `stock_universe` **不参与** —— 它只有 `priority`，标的元数据一律从 `company_master` 来。

## 11. 与方案的偏离（实测 ≠ `08` / `01方案` 的地方）

> 每条：**方案怎么写的 → 实测是什么 → 影响**。

### ① 数据源默认值：方案说 `akshare`，实测默认 `hunter`

- **方案**（§八 / `08 §一`）：「沿用现仓 `providers.data_source`（**`akshare`**，可回退 `yfinance`），不采购新源」
- **实测**：`get_data_source()` 默认 **`hunter`**（网关，无 key 抛 `HunterKeyRequired`）；
  `akshare` 必须显式 `DATA_SOURCE_PROVIDER=akshare`（`app/providers/data_source/__init__.py:31`）
- **影响**：一期若照方案直接 `get_data_source()`，**开源（无 key）部署下拿不到数据**，
  且失败形态是「提示去申请 key」而不是「回退 akshare」。
  → M1 决定 Data Service 用哪一层时，**要么显式设 `DATA_SOURCE_PROVIDER=akshare`，要么改默认**（后者会动现仓行为，需谨慎）。

### ② 前端目录结构与方案描述不符

- **方案**（任务书 §1）：`apps/web/`（Next.js App Router：`app/` 路由树、`components/`、`lib/`）
- **实测**：`apps/web/components/` 与 `apps/web/lib/` **不存在**；实际是
  `apps/web/app/components/`（8 个文件 + `gm/`）与 `apps/web/app/lib/`（5 个文件）（`ls apps/web/` 只有
  `app/ public/ scripts/ Dockerfile entrypoint.sh next.config.mjs package.json …`）
- **影响**：M6 做前端时，共享组件放 `apps/web/app/components/`（跟现仓走），不要新建一个平行层。

### ③ 「现有 ETL 定时」不是 cron，是**进程内循环**

- **方案**（`08 §1.3`）：假设「hunter-community 已有 ETL 定时（`klines_etl_log` 记录水位）」，
  并在文末写「若现有 ETL 是**纯手动的**，一期直接由 Temporal 接管」
- **实测**：既不是纯手动、也不是 cron —— 是 **`main.py:48` 的进程内 asyncio 循环**（§2）
- **影响**：Temporal 接管的动作变成「**删一个 while True 循环**」，比方案设想的更简单（无需迁移 crontab），
  但**必须记得删**，否则就是 §5.3 禁止的两套并存。

### ④ 「水位」不在 `klines_etl_log` 里

- **方案**（`08 §1.3`）：「`klines_etl_log` 记录水位」
- **实测**：`klines_etl_log` 是**运行流水**（每次 run 一行，无 `covered_to` 列）；真正的水位是
  `health()` 用 `max(ts)` 现算的，另有一张 `data_coverage`（**不在 migrations 里，在 `database.py:609`**）
- **影响**：Temporal 工作流若要读「上次采到哪天」，要读 `data_coverage` 或 `max(klines.ts)`，
  **不要**去 `klines_etl_log` 找水位列。

### ⑤ 「第二套调度」的规模比方案设想的大

- **方案**（`01方案 §5.3` / `08 §1.3`）：风险是「两套调度并存」
- **实测**：现状已有 **2 个 APScheduler 实例（8 个 job）+ 9 个进程内循环 + 1 份跨机 crontab**（§10 第 10 项表格）
- **影响**：M1 必须在成果文档里**明确划线**「哪些归 Temporal、哪些是现仓既有不动」，
  否则「不许两套并存」这条会变成无法验收的模糊要求。

### ⑥ 端口 8200 已被占用

- **方案**（`08 §3.2`）：「`paper` **8200** 只绑 127.0.0.1」
- **实测**：本机 **8200 已被 `hca-api` 与 `xinghe-xh-data-1` 占用**（§6.2）
- **影响**：起 `paper` 容器前要换端口或确认网络隔离。其余端口（3100/8100/3921/5442/6479）与实测一致。

### ⑦ 迁移的「对已有部署不生效」铁律已经失效（机制已升级）

- **CLAUDE.md 铁律**：「`db/migrations` 里的 .sql **对已有部署不生效**（只在数据卷第一次初始化时执行）」
- **实测**：compose 里那段挂给 postgres initdb 的挂载**已被显式删除**（`docker-compose.yml:34-38` 的注释），
  迁移改由 **api 启动时 `python -m app.migrate`** 执行，有 advisory lock + `schema_migrations` 账本（§5）
- **影响**：**新加 `0023` 是生效的**。CLAUDE.md 那条铁律**没有过时**的地方在于：**随代码走的 `_DDL`

1. **行情数据源最终口径**（§11-①）：一期 Data Service 走 `hunter` 网关（需用户配 `HUNTER_API_KEY`）
   还是显式 `DATA_SOURCE_PROVIDER=akshare`（免 key、但 A 股以外覆盖差、容器内可达性存疑）？
   方案写的是 akshare，实测默认是 hunter —— **两者不一致，必须选一个**。
2. **涨跌停 / ST 元数据补齐方案**（§7.3）：是按 `board` + 日期规则**推算**（复用 `agent_limitup.limit_of`），
   还是找新数据源（§八说「要花钱的一律不做」）？推算法的**历史 ST 时点**拿不到（已知局限）。
3. **Temporal 相关的四个新容器是否一台机全起**（`08 §2.1` 建议一期上，但本机已经跑 25 个容器、
   内存 17 GB available、**无 swap**）：是否接受在一期就往这台机器上再叠 4 个容器？
4. **`paper` 容器端口**（§11-⑥）：8200 已被占，换哪个？（`08 §3.2` 的其余端口都不冲突）
5. **fin-r1 那份 crontab 的去留**（§10 第 10 项）：Temporal 上线后，`scripts/rs_history_nightly.sh`
   是「迁进 Temporal」还是「继续留在 fin-r1」？留着就是跨机的第二套调度。
6. **`docker builder prune` 是否执行**（§9）：37.81 GB 全是可回收 build cache，
   构建前腾空间是否允许（本机是共享机，可能影响别人正在跑的构建缓存）。
