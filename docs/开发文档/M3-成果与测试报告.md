## 一、做了什么

### 1. 快照层 `apps/paper/app/snapshot/`（M-12 第①步）

| 文件 | 作用 |
|---|---|
| `source.py` | `Quote` / `QuoteSource` / `HttpQuoteSource` / `NullQuoteSource` + 时间戳解析 |
| `store.py` | 编号口径、质量判定、**只追加**落库 |

- **编号**：`SNAP-{日期}-{时刻}-{代码}`，例 `SNAP-20260930-093000-600519`；日期与时刻按**上海时间**切，取自**数据源回报的时刻**。同一秒的同一只票 = 同一张快照（`ON CONFLICT DO NOTHING`），这正是「同一快照 + 同一委托 → 同一成交价」的前提。
- **落库字段**：`last_price` / `bid1_price` / `bid1_volume` / `ask1_price` / `ask1_volume` / `prev_close` / `quality` / `missing_flag`。`raw_ref` 一期留空（不接对象存储，见 §五「需要用户决定」）。
- **`snapshot_time` 来自数据源**（`09 §六-6`）：整个 `app/snapshot/` 里**只有一次时钟调用**，那是判断新鲜度用的 `stamp`；填 `snapshot_time` 的表达式逐字是 `quote.quote_time`。两条都有用例钉着（源码扫描 + 行为断言，见 §三 T-05/T-06）。
- **断流**：`quality='stale'` + `missing_flag=true`（超过 `PAPER_SNAPSHOT_STALE_SECONDS`，默认 900 秒）。撮合见 `missing_flag` 一律走「不成交」。
- **数据源没给时间戳 / 拿不到 / 没有价** → **不落行**（`capture()` 返回 `None`）。`fin_snapshot.snapshot_time` 是 `NOT NULL`，填它就得有一个真实时刻，没有就不写这一行。
- **数据源是复用的**（任务书 §1）：`HttpQuoteSource` 打 `apps/api` 的 `GET /api/quote/{code}`（`auth.py` 里 `/api/quote/` 是免登录前缀），那条链路背后就是现仓的 `providers.data_source`（`08 §五`「数据源抽象」一行）。两个服务各自一个镜像、paper 的构建上下文是 `apps/paper/`，**import 不到 `apps/api`**，所以走 HTTP 复用而不是 import 复用。

### 2. 撮合层 `apps/paper/app/matching/`（M-12 第②③④步）

| 文件 | 作用 |
|---|---|
| `pricing.py` | `match(spec, snapshot, model)` —— **纯函数**，不连库、不取时间、不读 env |
| `model.py` | `ExecutionModel`（滑点 / 最小变动价位 / `part_fill`），从 `fin_execution_model` 读 |
| `engine.py` | 四步链路编排 + 收盘撤单 + 挂单再撮合 |

**口径（逐条对着任务书 §2 写）：**

| 委托 | 能否成交 | 成交价 |
|---|---|---|
| 限价买 | 快照价 **≤** 限价 | **快照价**（`last_price`） |
| 限价卖 | 快照价 **≥** 限价 | **快照价** |
| 市价买 | 有对手价 | **卖一价 + 滑点**（无盘口退回 `last_price`） |
| 市价卖 | 有对手价 | **买一价 − 滑点** |

滑点 = `slippage_ticks × tick_size`，一期 `1 × 0.01 = 0.01 元`（`总控规则 §八` 默认决策，由迁移 `0025` 种下，不是代码里的魔法数）。价格对齐到最小变动价位，用 `ROUND_HALF_UP`（不用 Python 默认的银行家舍入，与 `risk.price_limit` 同口径）。

**四步的顺序里有一个反直觉的地方**：撮合被算了两次。第一次是**试算**（纯函数、无副作用），只为给风控一个价 —— 市价单的资金校验需要知道「按对手价加滑点大概要花多少钱」。第二次才把结果**落账**。两次之间隔着的只有风控；风控不过整笔拒掉，试算的价一个字都不进账本。这样六条风控一条不少，且都在记账之前跑完。

**拒 / 挂单 / 成交的分界：**

| 情形 | 结果 |
|---|---|
| 风控不过 / 过有效期 / **没有可用快照** | `rejected`（留 `decline_reason`） |
| 快照有、但不可成交（断流 / 限价没到） | `pending`（买入**冻结资金**） |
| 能成交 | `filled`（写成交、绑快照、改持仓、版本 +1） |

### 3. 幂等与账户版本 `apps/paper/app/idempotency.py`（M-13）

- 每条命令带 `idempotency_key` + `request_hash`（canonical payload 的 sha256，落在 `fin_idempotency`）。
  - 同键 + 同内容 → **返回原回执**（第二次回执带 `idempotent_replay: true`）
  - 同键 + 不同内容 → **409 冲突，不覆盖**
- **顺序**：幂等命中 → 直接返回原回执 → **否则才**校验账户版本。这条是 `01方案 §11.1` 末两条，写反了会让「已经成功、只是回执丢在路上」的重试被版本校验拒掉。
- `fin_project.version` 每笔成交 +1；命令带 `expected_version`，对不上就**拒绝并留痕**（一条 `rejected` 委托，`decline_reason` 写明期望 / 实际版本）。
- 幂等记录与账本变更共用 `db.cursor(commit=True)` 的那**一个事务** —— 不存在「账记了、幂等没记」的中间态。

### 4. 长任务协议 `apps/paper/app/jobs.py`（为 M4 备好）

`submit → 持久化 job_id → get → 结果引用 → 可取消`。六个状态（`ACCEPTED` / `RUNNING` / `SUCCEEDED` / `FAILED` / `CANCEL_REQUESTED` / `CANCELLED`）+ 一张显式的迁移表，非法迁移返回 409。**先 `INSERT` 再返回** —— 用例用一个**独立连接**去查那个 `job_id`，先返回后落库的实现在那里查不到。

### 5. 迁移 `db/migrations/0025_fin_matching.sql`（只加不减）

| 改动 | 为什么 |
|---|---|
| `fin_execution_model.tick_size` | 滑点是「N 个最小变动价位」，没有 tick_size 的话 N 是个悬空的数 |
| `fin_idempotency.response` | 原回执本体；`response_ref` 只够放一个引用 |
| `fin_order.frozen_amount` | 受理时冻了多少；撤单按它解冻、成交按它退多冻部分 |
| 种下执行模型默认行 `paper-model-v1` | 值取自 `总控规则 §八`，不是编的 |

## 二、偏离方案的决策与原因

### 偏离 1 · 委托请求**不再携带快照**（`OrderIn.snapshot` 删除）

M2 让调用方把快照喂进来（`source='placeholder'`）。M3 起**快照由服务端按 `code` 现取**。理由：一旦调用方能提供快照（尤其能提供 `snapshot_time`），「成交价 = 委托到达时刻的快照价」和「时间戳来自数据源」这两句就都没有约束力了 —— 那是最容易绕过口径、又完全看不出来的一种做法。有用例断言客户端塞进来的 `snapshot` 字段被忽略、成交价仍来自服务端取到的快照。

### 偏离 2 · 「行情完全拿不到」**拒绝**，「行情断流（有旧价）」**挂单**

任务书 §1 写着「行情断流 / 拿不到 → `missing_flag=true`、`quality` 落 `stale` 或 `missing`，撮合必须走不成交分支」。实测这两件事落不到同一行上：

- **`fin_snapshot.snapshot_time` 是 `NOT NULL`**，而任务书同时要求「数据源没给时间戳就别落」。数据源完全没响应时**没有**任何可用的时刻，所以这一行落不下来。
- 能落的只有「**有数据源的时刻、但旧了**」这一种 —— 它正好就是 `missing_flag=true` 的场景。

所以实现是：

| 情形 | 行为 |
|---|---|
| 有快照但旧了（断流：喂价停了） | 落 `quality='stale'` / `missing_flag=true` → **不成交 → 挂单**（买入冻结资金） |
| 数据源无响应 / 无时间戳 / 无价 | **不落行** → **拒绝委托**，理由写明「没有可用快照…无法校验涨跌停与定价」 |

第二条选「拒绝」而不是「挂单」，是因为一张连涨跌停都算不出来的委托挂进队列，等于把风控绕过延后到成交那一刻。挂单的前提是**我们已经见过这只票的有效报价**（有 `prev_close` 能判涨跌停）。两条路径都有用例（§三 T-13 / T-14），验收项「断流 → 挂单」由第一种兑现。

### 偏离 3 · 挂单时**先冻资金再结算**（受理即成交那一路也一样）

验收要求「收盘未成交 → 撤单并解冻（贴 `fin_cash_ledger` 的 freeze / unfreeze 两条）」。这意味着挂单必须先把钱冻上。实现时把「受理即成交」也改成同一条路：`freeze（受理）→ buy → fee [→ unfreeze 多冻部分]`。理由是把两条路的现金语义统一成一句「成交时从冻结里付」，而不是让「立即成交」直接去动一个空的冻结额（第一版就是这么写的，`frozen_after` 当场变负，被 T-02 抓住）。

多冻从哪来：受理时按**限价**冻（`限价 × 数量 + 费用`），成交发生在快照价上（限价买要求 `快照价 ≤ 限价`），于是必然有多冻，退回可用。不退回去那笔钱就永远躺在冻结里，对账的 `frozen_zero_no_open` 会在收盘后报警。

### 偏离 4 · 券的占用**不建账本列**，由未成交卖单算出来

M2 偏离 4 说「券的冻结一期不建模，M3 有挂单时再补」。补法是：`ledger.open_sell_committed()` 从 `fin_order` 直接算「该标的上还没成交的卖单占用多少股」，风控第 2 条（T+1）与第 6 条（持仓）拿 `可卖量 − 这个数` 去判。

**为什么加列不如算**：`fin_order` 本来就是权威，再存一份 `frozen_qty` 就多了一个可能和委托不一致的权威 —— 正是账本不平的经典来源（`09 §4.5` 底注对「余额列」说的是同一件事）。有两条用例：卖方占用拦下第二张挂单（T-18），以及风控的 `sellable_qty` 入参确实是扣过的。

### 偏离 5 · 委托到达时刻 = **快照时刻**（沿用 M2 口径）

风控第 1 条（交易时段）用的是 `at = snapshot_time`，不是本机时间。理由：快照时刻是这张价**有效的那一瞬间**，拿它判时段与拿它定价是同一条口径。**已知局限**：断流时挂单的时段校验是拿一个旧时刻做的 —— 但那种情况下要么被拒、要么本来就挂单（不成交），影响不到成交价。

### 偏离 6 · 撤单端点用 `POST`，不是 `PATCH`

路由方法集合仍然是 `{GET, POST, PUT}`（`test_append_only` 的守卫），撤单是 `/api/v1/orders/{id}/cancel`、批量撤单是 `/projects/{id}/orders/expire` —— 都是 POST。撤单**不改历史行**：`fin_order` 是状态会变的表（0023 里就授了 UPDATE），撤单只动状态列 + 追一条 `unfreeze` 流水，成交与流水本身一行没动。

### 偏离 7 · 修了一个 M2 遗留的真实缺陷：镜像里没有 `boot.sh`

用真实镜像起容器时 `CMD ["/app/boot.sh"]` 报 `exec: /app/boot.sh: no such file or directory` —— Dockerfile 只 `COPY app /app/app`，没拷 `boot.sh`。**开发用的是 dev compose 的 bind mount，本地跑不出来**；M2 报告里的「真容器端到端」实际是 `docker run … python -m pytest` 那种跑法，没走到 `CMD`。已补 `COPY boot.sh` + `chmod +x`（构建期挡不住这类问题，镜像里根本没那个文件）。

### 3.5 验收清单逐条（对任务书）

| 验收项 | 证据（实测） |
|---|---|
| 一笔委托走完四步链路，成交行带 `snapshot_id`，快照的 `snapshot_time` 来自数据源 | §3.4 的联查：`trade.price=10.0000` / `snapshot_id=SNAP-20261002-100000-600519` / `snapshot_time=2026-10-02T10:00:00+08:00`（假行情服务给的就是这一秒）；`source='http'` |
| **重放同一条命令不产生第二笔成交** | §3.4：重放回执 `idempotent_replay=true`、`trade_id` 与首次相同，`fin_trade` 仍 1 行、`fin_order` 仍 1 行、`version` 仍 1。用例 `test_replay_same_key_same_content_does_not_duplicate` |
| 同键不同内容 → 冲突，不覆盖 | §3.4：HTTP **409**；`fin_trade` 仍 1 行；`fin_idempotency.request_hash` 仍是第一条的（`test_conflict_record_keeps_the_first_hash`） |
| `snapshot_time` 用 `now()` 填会被测试抓住 | 两把锁：源码扫描「`app/snapshot/` 里时钟调用恰好 1 处，且那一处是 `stamp = now or datetime.now(...)`」；行为断言「数据源说 1990-01-15 09:30:00，库里就是那一秒」——用了 `now()` 这行当场不等（T-05 / T-06） |
| 行情断流（`missing_flag=true`）时不成交，转挂单 | 见下方「§3.6 逐条证据」④：`status=pending` / `snapshot_quality=stale` / `missing_flag=true` / `fin_trade` **0 行** / 可用 8994.9900，冻结 1005.0100 |
| 限价单快照价劣于限价时不成交 | 「§3.6」⑤：`status=pending`，理由「快照价 10.5000 劣于买入限价 10.00（买入要求快照价 ≤ 限价）」 |
| 市价单成交价 = 对手价 ± `slippage_ticks` | 「§3.6」⑥：卖一 10.02 → 成交 **10.0300**（`ask1_price+slippage`）；真实容器里卖一 10.01 → **10.0200**；`test_slippage_scales_with_the_execution_model`（2 ticks → +0.02） |
| 收盘未成交 → 撤单**并解冻** | 「§3.6」⑦：`expired=1`、`unfrozen=1005.0100`、可用/冻结 `8994.9900/1005.0100 → 10000.0000/0.0000`，流水里 `freeze` 与 `unfreeze` 两条都在 |

## 四、遗留问题（按优先级）

1. **【高】`paper` 镜像未推 GHCR**（M2 遗留 2）。`docker-compose.yml` 里是 `…-paper:${FIN_TAG:-latest}`，M3 只在本地构建（`hunter-community-paper:m3`）。**M8 必须发布镜像**，否则 profile 一开就是拉取失败。
2. **【高】`fin_*` 表 owner 仍是 `hunter`**（M1/M2 遗留 1）。启动自检挡住了「paper 被指到管理员连接」，挡不住「别的服务用 owner 连库直接改账本」。M8 上演示站前处理。**账本侧红线仍是「自检级」而非「物理级」。**
3. **【中】行情链路本身没接通**：`PAPER_QUOTE_URL` 默认指向 `http://api:8000`，但**线上 api 的 `/api/quote/{code}` 对 A 股的可用性没有在 M3 验证**（M3 只用假行情服务端到端验证了 paper 这一侧）。M7（数据接通）要拿真实标点验一次；验之前线上 paper 的表现是「没有可用快照 → 拒绝委托」，不会产生假成交。
4. **【中】`apps/api` 侧的 M1 用例没能在本机重跑**：`m2-py` 镜像里没有 `apps/api/tests`，T-04 没跑成。M8 全量回归时补。
5. **【中】券的占用是「算出来的」**，`confirm_t1()` 在挂单存在时会把 `sellable_qty` 恢复成 `qty` —— 占用本身不受影响（风控现减），但**日切必须发生在没有挂单的时候**。M4 的时点工作流要在收盘撤单之后再调 `confirm_t1()`。
6. **【中】T+1 日切靠 M4 调 `confirm_t1()`**（M2 遗留 5 不变）。
7. **【低】`fin_snapshot.raw_ref` 恒为空**：一期不接对象存储，原始报文不落。
8. **【低】快照保留期未做**（`09 §十-1` 待拍板）：表只增不减，`02` 建议先按一个自然年。归档 / 分区 DROP 属结构性动作，需单独评审。

## 六、下一里程碑（M4 · 自动化）交接

**第一件事**：把 `POST /api/v1/projects/{id}/orders/match-open`（拿新快照再撮挂单）与 `POST /api/v1/projects/{id}/orders/expire`（收盘撤单解冻）接进 M4 的六时点工作流 —— 这两个端点就是为它准备的，`03` 的 09:30 / 11:30 / 13:00 / 14:55 / 15:30 五个时点各调哪一个是 M4 的口径决定。

**开工前必须知道的：**

- **`fin_job` 协议已可用**（`app/jobs.py` + `/api/v1/jobs`），先 `INSERT` 再返回 `ACCEPTED`；六个状态与迁移表在代码里，加新状态要同时改 `0023` 的 CHECK 与 `jobs._ALLOWED`。
- **撤单一定要在 `confirm_t1()` 之前跑**（遗留 5）。顺序错了不会报错，只会让当天的挂单占用出错。
- **`match_open_orders` 不再跑六条风控**（受理时跑过了）：买入的钱冻着、卖出的股由 `open_sell_committed` 占着，这两条保证「再撮合」只可能把一张已经通过风控的单变成成交。**加新的买入类风控条件时，要么在受理时判完，要么在 `match_open_orders` 里补一遍** —— 只写在受理那一边会让挂单绕过它。
- **`fin_snapshot` 是全库共享、只追加的，编号只到秒**。写测试时注意：同一 (代码, 秒) 会被 `ON CONFLICT DO NOTHING` 复用，两个用例会串（`helpers.uniq_when` 就是为此存在的）。
