## 〇、结论摘要

- **三个市场各一组 Schedule 真的建起来了**：Temporal 里 **24 条** Schedule（18 个时点 + 3 条 ETL + 3 条标的同步），
  时点 Schedule 的 `time_zone_name` 分别是 `Asia/Shanghai` / `Asia/Hong_Kong` / `America/New_York`；
  一期的 6 条单市场时点 Schedule **已退役**（列表里 0 条）。
- **「A 股休市、港股/美股照常跑」有真跑证据**：2026-10-06（A 股国庆休市）三个市场各触发一个时点，
  CN_A 返回 `non_trading_day` 并写明原因，**HK / US 返回 `ok` 并读到各自日历的交易日与时段**。
- **日历缺失 → 该市场不跑 + 写明原因，其他市场正常**：2026-11-20（CN_A 无日历行）同样三市场触发，
  CN_A 返回 `calendar_unknown` + warning，HK / US 正常。
- **夏令时交给 Temporal**：Schedule 存的是 IANA 时区名（不是固定偏移）；另有一组**固定日期**的换算断言，
  2026-03-08 / 11-01 两个切换日两侧都验到（EST −05:00 ↔ EDT −04:00，A 股/港股全年 +08:00）。
- **账本按本币记账、跨市场不折算**：`fin_order / fin_trade / fin_cash_ledger / fin_position / fin_valuation`
  写入时带 `market` + `currency`；`fin_valuation` 主键改成 `(project_id, market, as_of)`；
  **账本里没有任何汇率**。
- **子账户隔离，有反例用例**：在 HK / US 子账户买入，CN_A 子账户可用资金**一分不变**（真跑 + 两条单测）。
- **港美股各一笔真实成交（真跑，非打桩）**：在本机这套容器里
  `00700.HK` 成交 100 股 @ **421.2000 HKD**、`AAPL.US` 成交 1 股 @ **333.6900 USD**，
  逐段落了 `fin_order → fin_trade → fin_cash_ledger → fin_position → fin_valuation` 真数据。
- A 股全量用例**一条不减少、全部通过**（见 §四）。

## 一、这一轮做了什么

## 二、偏离任务书 / 方案的决策与原因

> 无人值守模式（`拍板 §〇`）下遇岔路口按**最保守、最可核对**的选项继续，逐条标注。

1. **时点的权威落在 `fin_market_rule.points`，`points.py` 的常量降级为兜底。**
   任务书 §一.1 原话是「改成从 `fin_market_rule.points` 读」。fin-worker **没有账本库连接**，
   所以经 paper 的 `GET /api/v1/market-rules`（新端点）读。**实测证明了这条路径真的通**
   （§三.①）：在 fin-worker 容器里跑 `schedules.load_market_rules()`，返回的正是 DB 三行
   （连我改的港股 CAS 时段都带回来了），生成的 18 条时点 Schedule 用的就是它的 `points`/`timezone`。

2. **一期 6 条旧 Schedule 显式退役（删除），不是留着。**
   留着会让 09:15 同时触发旧 `fin.point_0915` 与新 `fin-point-CN_A-0915` 两个 Schedule。
   幂等键相同不会重复下单，但会白跑一倍、且「调度只有一个权威」这条被破坏。

3. **⚠️ 港股交易时段补上收市竞价（16:00–16:10）—— 本轮唯一一处改交易口径的决定。**
   N3 §五-5 把这件事留给 N4 定。实测根因：数据源（腾讯）给的港股最新价
   **本来就是收市竞价的成交打印**（`00700.HK` `event_time = 2026-10-02T16:08:10+08:00`），
   而 `fin_market_rule.sessions` 只写了持续交易时段 → **港股一笔都成交不了**
   （实测回执：`不在交易时段内（16:08 香港时间，当日时段 09:30-12:00、13:00-16:00）`，`failed_checks=["session"]`）。
   决定：把 CAS 计入港股可交易时段。理由：CAS 是港交所官方交易日的组成部分，
   券商模拟盘按收市价撮合是常规近似；**只动 HK**，A 股 / 美股不变。
   **若用户不认这条口径，回滚 = 把 HK 的 sessions 写回 `0030` 的种子值**（迁移里留了注释）。
   同一条也同步到已有的港股日历行（否则「市场规则说能交易、日历说不能」两处打架）。

4. **`fin_valuation` 主键加 `market`（三列主键），而不是「一行三市场」。**
   设计 §3.1 A 方案：一个项目三个市场各一行估值，同日共存。旧的主键 `(project_id, as_of)`
   会让先写的市场把后写的顶掉。

5. **`resolve_market()` 对 `MULTI` 项目回落到 `CN_A`。**
   项目 `market_scope` 可能是 `MULTI`（二期多市场）——那不是单个子账户。
   缺省时落到 `CN_A`（一期语义），要港美股子账户**必须显式传 `market`**。这样 A 股旧调用点行为逐字不变。

6. **订单的市场**以 `fin_instrument.market` 为准（拿不到才按代码形态兜底）。
   所以「一个项目下按市场分子账户」是**按标的所属市场**自动分派的，不需要调用方声明市场。

7. **修掉一个 N4 引入的、会让调度整体失效的缺陷（见 §二.7）。**
   原实现把 `ZoneInfo` 实例建在模块级（`_TZ` 字典），进 Temporal 工作流沙箱后成 `_RestrictedProxy`，
   `astimezone()` 抛 `tzinfo argument must be None or of a tzinfo subclass`。
   **「在调用点现建 `ZoneInfo`」也不行**（实测仍被包成 proxy）。最终把时区换算整体挪进
   新 Activity `market_clock`（沙箱外），结果进事件历史、replay 读历史那份，确定性不受影响。
   ⚠️ 这个失败**不报错到 HTTP 层**：`POST /internal/trigger` 照样回 200，
   只有 Temporal 的 `WorkflowTaskFailed` 事件里有——排查时先看事件历史。

### 二 · 附：N4 之前就存在、本轮**顺手修掉**的两个测试基建缺陷

> 这两个都在 N3 基线上**同样随机失败 1~2 条**（本轮用 `git worktree` 在 `75b6ef2` 上复现，
> 见 §三.⑧ 的对照），不修则「A 股全量用例全部通过」这条出口标准不可复现。

8. **测试夹具把上海时区写死成 `+08:00`，而日期池是 1990–2022。**
   中国 1986–1991 年实行过夏令时（当地 `+09:00`），于是池子里 1990/1991 年 4–9 月的
   「盘中时刻」实际落到当地 15:xx，被交易时段校验拒掉（症状：随机某几条用例莫名 `rejected` /
   `market_value` 差一截 / 对账报「缺价」）。修法：`apps/paper/tests/helpers.py` 的 `CST`
   改用 `ZoneInfo("Asia/Shanghai")`，`uniq_when()` 用真实时区拼时刻，用到固定时刻的用例改传不带偏移的串。

9. **`test_ledger_e2e.py` 全文件共用一个标的代码（`600000`），而 `fin_snapshot` 是全库共享、只追加的。**
   估值 / 对账按「该代码 ≤ as_of 的最新快照」取价，后跑的用例会取到前一个用例留下的、日期更晚的那张快照。
   修法：`ready` fixture 按 `project_id` 派一个**独有代码**（纯数字，归 CN_A）。
   「日历缺失」类用例改用池子外的固定日期 `ABSENT_DATE`（日历表同样跨用例累积）。

```
US 2026-03-07 12Z          -> 2026-03-07T07:00:00-05:00 (offset -5h)   ← EST
US 2026-03-08 12Z          -> 2026-03-08T08:00:00-04:00 (offset -4h)   ← EDT（3/8 进入夏令时）
US 2026-10-31 12Z          -> 2026-10-31T08:00:00-04:00 (offset -4h)
US 2026-11-01 12Z          -> 2026-11-01T07:00:00-05:00 (offset -5h)   ← 退出夏令时
US open 03-04 14:30Z       -> 2026-03-04T09:30:00-05:00   # 「美东 09:30 开盘」冬天对 14:30Z
US open 03-11 13:30Z       -> 2026-03-11T09:30:00-04:00   # 夏天对 13:30Z —— 所以不能写死 ±N 偏移
CN_A 2026-01/07/12-15 04Z  -> 12:00:00+08:00（全年）
HK   2026-01/07/12-15 04Z  -> 12:00:00+08:00（全年）
```

**Schedule 侧**：存的是 IANA 名 `America/New_York`（不是偏移），Temporal 自己按该时区解 cron：

```
$ curl .../schedules/fin-point-US-0930
timezoneName: America/New_York
futureActionTimes: ["2026-10-05T13:30:00Z", "2026-10-06T13:30:00Z", …]
```

`13:30Z` 正是**夏令时期间的**美东 09:30；进入冬令时后同一 cron 会落在 `14:30Z`
（Temporal 存的是时区名，不是固定偏移 —— 这是「夏令时交给 Temporal」的落点）。
