## 二、两层架构：为什么影子事件由 api 写、paper 只算不记

`plan/R7.md` §一.1 要求影子路径落在 `apps/paper/app/shadow.py` 并**复用** `ledger.py`
的费率 / 滑点 / 停牌 / 撮合实现（红线 9：口径只许有一份）。同时 `R6` 的 `0043`
（照 `0041`）**刻意不给** `fin_paper_rw` 任何授权 —— 而 `paper` 连的正是那个角色。
两者合起来的唯一自洽解：

```
 fin.shadow 工作流（fin-worker，无库连接）
     │  ① prepare  ──► api（读提案/计划/两臂配置/两臂状态，重建自最近一条影子事件）
     │  ② 两臂各跑一次 build_decision（同一策略、候选臂用候选配置）
     │  ③ simulate  ──► paper（取【一次】快照 → 复用 risk/matching 实现撮合 → 只记不落库）
     │  ④ record    ──► api（写 fin_evolution_shadow_event，唯一键幂等）
     └  ⑤ evaluate  ──► api（算指标 + 读【冻结计划】判定，终局才追加状态事件）
```

- **撮合实现只有一份**（`paper`），影子与真实下单走**同一批函数**（`risk.evaluate` /
  `matching.pricing.match` / `risk.fee.compute_fee`）。影子成交价与直接调 `match(...)`
  逐位相同（`tests/test_shadow_isolation.py::test_two_arms_share_one_snapshot_and_same_quote_as_of`）。
- **影子账本只有一份**（api 的 `services/fin/evolution.py`）。`paper` 只**算出**每一行该长什么样、
  经 HTTP 返回；写库由 api 做（唯一入口，与 `fin_experience*` 同一条纪律）。
- **`fin_trade` 与这张表毫无关系**：`paper` 的影子路径一行写账本表的路都没有。

## 四、影子账本的口径（写进成果文档，且可复算）

### 4.1 每一行是什么

`fin_evolution_shadow_event` 是**事件溯源式的影子账本**：一行 = 某臂在
`(validation_id, trade_date, point, symbol)` 上的一次决策及其结果。

| 列 | 口径 |
|---|---|
| `validation_id` | = `proposal_id`（一条提案恰好一次验证；`R6` 建表时**不设外键**） |
| `arm` | `incumbent` / `candidate` |
| `quote_as_of` | 行情时间戳；**同一次两臂完全相同**（同一张 `fin_snapshot`） |
| `signal` | 该臂在这一点**是否出了决策**（JSON 文本）；没出决策 → `NULL` |
| `filled` / `reject_reason` | 是否（模拟）成交 / 未成交原因（风控拒 / 限价没到 / 行情缺口） |
| `fee` / `slippage` | 按 `fin_fee_model` 算的费用 / 市价单的滑点（价差 × 股数） |
| `position_ref` (JSONB) | **该臂该步之后的持仓快照**：`{cash_available, cash_frozen, positions:[{code,qty,avg_cost,sellable_qty,price}]}` |
| `valuation_ref` (JSONB) | **该臂该步之后的估值快照**：`{cash_available, cash_frozen, market_value, total_assets, nav, initial_capital, as_of_price}` |

**唯一键** `(validation_id, arm, trade_date, point, symbol)` —— 重试 / 重启 / 补跑
**不会重复记账**（`ON CONFLICT DO NOTHING`）。

### 4.2 持仓与估值：由事件逐笔重建，不新建账本表

影子臂**没有自己的账本表**（红线：不新建账本表）。它这一步之前的现金 / 持仓，
由 `shadow_prepare` 从**该臂最近一条影子事件的 `position_ref`** 里取出、随请求带去
（`paper` 侧 `_state_view` 还原）。**每个事件行本来就带着它那一步之后的完整快照**，
所以「重建」= 取最近一条 ≤ 当日的行 —— 与「从头逐笔重放」逐位等价。

### 4.3 估值口径（**可复算**）

```
总资产 total_assets = cash_available + cash_frozen + Σ(股数 × 价)
净值   nav          = total_assets / initial_capital
```

这与 `apps/paper/app/valuation.py` **逐字同口径**（那边是真实账本，这边是影子状态）。
**缺价就不出估值**：任一持仓翻不到价 → `total_assets = null`、`missing_prices` 点名 ——
不拿成本价顶替市值（`valuation.py` 的 `MissingPrice` 同一立场），并由判定侧据此走 `inconclusive`。

**手工复算（验收 §⑧，真实输出）**：

```
⑧ 复算: 10000.0000 + 0.0000 + 0 = 10000.0000 ; 库中 total_assets = 10000.0000 ; nav=1.000000 ; 一致=True
```

（`10000.0000` 本金 + `0.0000` 冻结 + `0` 持仓市值 = 库中 `total_assets`，与 `nav=1.000000` 自洽。）

### 4.4 样本口径的真值表（红线 11）

一个 `(trade_date, point, symbol)` 计为**一个可比样本**，当且仅当**两臂都出了决策**：

| 现行臂 `signal` | 候选臂 `signal` | 计入样本 | 说明 |
|---|---|---|---|
| 有 | 有 | ✅ | 两臂**均有可比机会** —— 这才是样本 |
| 有 | 无 | ❌ | 只有现行有交易 |
| 无 | 有 | ❌ | **只有候选有交易 —— 不许直接相减**（红线 11） |
| 无 | 无 | ❌ | 都没决策（如总开关关闭 / 买不起） |

两臂的行**总是**各写一行（没决策时 `signal=null`），所以「只有一臂有交易」的那一天
**在库里看得见、但不计样本**。实测：`6 → 6`（塞一个只有候选臂出决策的时点后样本数不变，§六.9）。

## 五、判定：读冻结计划，窗口未到绝不通过

判定**只读 `fin_evolution_plan` 冻结下来的** `metric` / `window_days` / `min_comparable_sample` /
`pass_line` / `fail_line` / `early_stop_condition`（红线 10：改口径 = 新建提案，不许事后改）。

`delta = candidate_portfolio_net_return − incumbent_portfolio_net_return`（**组合口径**，
不是单笔 `realized_net_pnl`；后者只作辅助诊断，输出里带 `auxiliary: true` 明示）。

```
① delta ≤ fail_line            → failed（提前失败，与窗口无关）
② 候选最大回撤 ≤ early_stop 线  → failed
③ 窗口未结束                    → 不判定、不写事件（绝不 passed）
④ 窗口结束 & 样本 < min_sample  → inconclusive
⑤ 窗口结束 & delta ≥ pass_line  → passed
⑥ 其余                          → inconclusive
```

**终局才写事件**：中间每次跑只算不写 —— 否则一个中途的 `inconclusive` 会把提案投影压成
inconclusive、让它退出 `validating`，后续就再也跑不到。

- `pass_line` / `fail_line` / `window_days` / `min_comparable_sample` 的**默认值与依据**沿用
  `R6` 的 `evolution.DEFAULT_PLAN`（`docs/开发文档/R6-…md` §四）。**本轮不预写新阈值**（红线 13）：
  当前没有真实达标样本，占位值原样保留；要校准得**新建提案**。
- `kind='failed'` 是 `R7` 新加的（迁移 `0044`）：验证**跑出来不达标**与 `rejected`
  （提案被驳回）是两种语义；`proposal.status` 仍投影到 `rejected`（状态列没有 failed）。

## 八、遗留问题与下一阶段（`R8`）交接

### 8.1 交给 `R8`：哪些信号算「可生效」

1. **只有 `kind='passed'` 才算「验证通过」**。它成立的三个条件缺一不可：**窗口已结束**
   + **可比样本 ≥ `min_comparable_sample`** + **delta ≥ `pass_line`**（`plan` 冻结值）。
   `R8` 的「应用到模拟盘」入口只能读这一条 —— **不得**把 `inconclusive` 当通过。
2. `failed` 是**终局**（提案跑出来不达标 → `proposal.status` 投影为 `rejected`）。
   `inconclusive` 也是终局（不结论是合法终局，红线 10）。
3. `R8` 的 CAS 校验用提案的 `base_config_hash`（`R6` 已落）—— 生效前确认当前 `fin_param`
   的配置哈希仍是它（变了说明基线动过、提案过期）。
4. **一次失败不得事后改 plan 再判通过**（红线 10）—— 改口径只能新建提案。

### 8.2 已知局限（如实列出）

- **两臂当前决策相同**（§七-6）：示例策略不读白名单参数，所以本轮真实运行的
  `delta = 0` → 落在 `inconclusive`。**框架已就绪**（候选配置已进决策入参），
  要看到真实分化，得让策略真读这些参数（后续阶段）。
- **影子臂不做 T+1 / 不挂单跨时点**（§七-5）：A 股的 T+1 差异在影子里被简化；
  要精确复现得让影子也走 multi-point 的挂单簿。
- **`regime` 恒 `unknown`**：接了基准行情源后，在 `shadow_step` 里调
  `regime.detect_for_market` 填 `regime_tags` 即可（本模块不用改结构）。
- **影子事件表无保留期清理**：与 `R6` 的追加表同口径，只增不减。
- **`quote_as_of` 一定相同**是构造保证（整次调用只 `capture` 一次）；但两臂**共用一张快照**
  也意味着影子不是「每个臂各自取价」——那是刻意的（红线 11「同一行情快照」）。
