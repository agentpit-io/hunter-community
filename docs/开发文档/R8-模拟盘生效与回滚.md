## 二、四条口径（**改这一段之前先读这里**）

### 2.1 CAS：基线一动，旧提案就作废

`apply_proposal` 放行前**两次**核对基线：
1. **闸门层**（读）：`hash_config(read_config(project))` 必须仍等于提案的 `base_config_hash`；
   不等 → `计划已过期` → 追加 `rejected_by_gate` 事件 + 400，**配置一动不动**。
2. **写入口层**（`control.activate_candidate`，锁）：`SELECT … FROM fin_param WHERE project_id=%s FOR UPDATE`
   取行 → 现算配置哈希 → 与 `expected_base_config_hash` 比；不等 → `CasMismatchError`，
   **整笔回滚**。

**哈希口径只有一份**：`evolution.config_from_row` + `evolution.hash_config`。
`control.py` **晚导入**它们（函数体内 `from … import`）—— 既不复制第二份口径（复制就会
「永远 CAS 失败且不报原因」），也避开 `evolution → control`（生效调用）与
`control → evolution`（哈希）的模块级循环。

**并发人工改策略时阻止旧提案生效**（`03 §6` 必测场景）就是这两层合起来的效果：闸门读到的
已经是改过之后的行；即便有缝隙，`FOR UPDATE` 也会把两个写入串行化，后到的那个必然 CAS 失败。

### 2.2 版本链：回滚目标从事件里取，**不猜**

回滚目标**不是**某个字符串字段，而是 `fin_evolution_event(kind='applied')`
的 `from_key`（那次生效是「从谁切到谁」）。`rollback_proposal` 拿到它之后**再校验三件**：

| 校验 | 不过怎么办 |
|---|---|
| `from_key` 非空 | 版本链不完整 → **拒绝并告警** |
| `from_key` 真的在 `fin_param.strategies` 里 | 目标已不存在 → **拒绝并告警** |
| 当前 active 就是那次生效的 `to_key` | 版本链对不上（已被人改过）→ **拒绝并告警** |

所以**不是「只信 `base_strategy_key` 字符串」**：字符串只是线索，能不能回滚由**版本链三验**说了算。
核验失败落一条 `alert` 事件 + `fin_alert_log` 告警 + HTTP **409**（`EvolutionRollbackRefused`）。

### 2.3 紧急线：**全系统唯一自动改配置的触发点**

观察期**继续按同一份 `fin_evolution_plan`** 算（窗口 / 指标 / 通过线 / 失败线 / 回滚线都不变，
`plan_hash` 前后一致 —— 见 §五.7）。

**触发顺序**（`observe_applied`）：
1. 实盘（`fin_valuation` 净值）最大回撤 **≤ 冻结的 `rollback_line.max_drawdown_pct`**（默认 −10%）
   → **自动回滚**（调 `rollback_proposal`，唯一自动路径）；
2. 否则触及冻结的 `early_stop_condition`（默认 −8%）、或窗口结束但净收益 ≤ 冻结的 `fail_line`
   → **只告警**（`alert` 事件 + `fin_alert_log`），**配置一动不动**，等人工确认是否回退；
3. 其余 → 无动作。

**回滚方向永远是回到已验证版本**（风险只降不升）。回滚时**一并停掉该项目的模拟下单**
（`auto_enabled=false`，复用既有的 `halted` 形态 —— `fin-worker` 的 `build_decision` 读它，
为 false 时不产生新委托）；**重新开启是人的动作**（本模块不自动恢复）。

**所有风险上限对新旧策略都适用 —— 策略切换 ≠ 可放宽风控**：放行闸门里
「不触及任何风控上限」是一条硬条件，`target='risk'` 的提案**不走生效路径**（风控只经
`apply_risk_tier` 人工棘轮）。

### 2.4 四步同事务：绝不出现「配置已改而日志缺失」

`control.activate_candidate` 在**一个事务里**做四件事（任何一步失败 → **整笔回滚**）：

```
 ① CAS              SELECT … FOR UPDATE → 现算配置哈希 → 与提案的 base_config_hash 比
 ② 注册候选版本      新条目 {key,name,params,version} 追加进 strategies[]（**新 key，旧条目不动**）
 ③ 写 change_log    逐字段 old → new（顶层字段 + strategies.<新key> 登记 + active_strategy 切换）
 ④ 切换 active key   新条目标 active，其余取消
```

`apply_proposal` 通过 `within_txn` 回调把 **`applied` 事件也写进这一笔事务** ——
否则「配置改了而事件没写」会切断回滚链（回滚找不到 `from_key`）。

## 三、回灌重试机制（`plan/R8.md` §一.4「回滚了但没学到是必须被看见的失败」）

回滚要落**三样**：`rolled_back` 事件 · `fin_param_change_log` 行 · **一条有证据的失败经验**
（`polarity='refute'`，经 `memory.append_evidence` 内网通道，证据指向本项目**账本真值**
`fin_trade` 行）。

第三样可能写不进去（记忆库关着 / 暂无成交 / 校验不过）。**不许吞**：

```
回滚事务提交
   └─ queue_rollback_experience()
        ├─ 落一行 fin_evolution_reinject_task(status='pending', payload=追加所需全部字段)
        └─ 立即尝试一次 _reinject_one()
             ├─ 成功 → status='done'
             └─ 失败 → 保持 'pending' + attempts+1 + last_error
                        → 只读接口 reinject_pending = true（「回灌待完成」）
                        → POST /internal/fin/evolution/reinject/retry 再试
```

- **任务落库那一刻，「要写什么」就定了**（payload 存全套字段）—— 重试不回原上下文重新解释，
  与 `R6`「计划写后冻结」同一思路。
- 这张表**不是账本、不是审计权威**：审计仍以 `fin_evolution_event`（`rolled_back`）为准；
  所以它**可更新**（`status` / `attempts` / `last_error`），与 `0043` 的两张不可变表不是一类。
- **幂等**：`status='done'` 的任务再调 `_reinject_one` 直接返回，不重复写经验。

| 1 | `let` 生效路径**只收 `target='strategy'`** | `target='risk'`（哪怕收紧）也走闸门拒绝 | `plan/R8.md` §一.2 明写「**不触及任何风控上限**」是一条放行条件。风控只经真人 `apply_risk_tier(confirm=True)` 棘轮（红线 8/9）—— 生效路径碰风控等于给自进化留了一条改刹车的缝 |
| 2 | 「计划未过期」的口径 | = **基线没被改动**（当前配置哈希 == 提案 `base_config_hash`），不新增「过期天数」阈值 | 表里没有 `expires_at` 列，凭空加一个「N 天过期」是新阈值（红线 13）。基线的 CAS 才是「过期」的真实含义，且它不引入新数字 |
| 3 | 观察期指标从哪来 | 生效后用 **`fin_valuation` 实盘净值**算回撤/收益，**不再用影子** | 生效后候选臂就是现行臂，影子已结束（`R7` 的 `fin_trade` 真值此时才是候选的成绩）—— 继续用影子的两臂差 = 拿旧数据判新问题 |
| 4 | 回滚后**不自动恢复** `auto_enabled` | 停单后保持关着，等人工重开 | 紧急线与的方向是「风险只降不升」（红线 9）。自动重开等于自动放宽 |
| 5 | 回滚失败经验的证据只取 `fin_trade` | `evidence_kind='trade'`（最多 5 条）；**没有成交就写不进去** → 回灌待完成 | `memory` 只认 `trade/report/fact/snapshot` 四类，**影子事件不是可校验的证据类型**。硬编一个不存在的引用等于违反「防编造引用」。没有成交时如实留「待完成」，不编 |
| 6 | 告警写 `fin_alert_log` 不直接调 `notify-qq` | 服务端只落投递记录，宿主 `scripts/fin_recon_alert.sh` 负责发 | 与 `paper/recon.py` 同一条既有链路；测试里不会真发邮件，离线环境也不会因发不出去而失败 |
| 7 | `alert` 事件的投影状态 | `STATUS_OF_KIND['alert'] = 'applied'` | 告警**不改变**提案状态（仍处生效 / 观察态）；不映射会让 `projection_mismatches` 非空（`R6` 的投影一致性会红） |
| 8 | 事件 payload 多记 `base_config` / `candidate_config` / `active_config_hash` | 在要求的五个锚点之外**额外**记三样 | 回滚要「恢复成预先记录的 base 配置」—— 只有哈希恢复不出来；`active_config_hash` 是**回滚 CAS 的期望值**（生效后的行哈希，与提案锚点不是同一个值，见 §二.2） |
| 9 | 未引入「非 owner 最小权限连接」 | 仍以库属主连接 | 与 `R6 §6.5` 同一结论：单人本地部署下「防机器所有者」没有对手；`R10` 之后若多用户再议 |

## 七、已知局限（如实列出）

- **`_apply_errors` 的 `except LookupError` 会把 `IndexError` / `KeyError` 也吞成 404** ——
  这是 `R6`/`R7` 就已存在的路由约定（`LookupError` 是 `IndexError`/`KeyError` 的父类）。
  本轮**实测被它误导过一次**（真 bug 被显示成 404「tuple index out of range」）。
  已在 `R8` 的用例里逐条断言拒绝文案，但**路由层这个宽 except 未改**（改了会偏离 `R6` 的既定口径）。
  下一轮若要收口，建议给「提案不存在」定义一个专用异常，别再借 `LookupError`。
- **观察期调度未接 `fin-worker`**：`observe_applied` / `rollback_proposal` 已完整可调（内网端点），
  但**没有**新增 `fin.observe` 工作流 / Schedule（`R9`/`R10` 接线）。当前靠守控台或人工触发。
- **回滚不重置纸面持仓**：只切配置 + 停单；已开仓按既有风控继续管理（`R8` 不动 `apps/paper/**` 账本语义）。
- **`applied_at` 未写进 payload**：观察窗口起点取 `applied` 事件的 `created_at`。
- **回灌证据只到「账本真值」**：影子一侧（`plan_hash` + 指标）记在 `rolled_back` 事件的
  `applicability` 文案里，不作为可校验的证据引用（见 §六.5）。

## 八、交给 `R9` 的只读字段清单

`R9` 的成长页**只读**这些（全部由 `R8` 落好，界面零硬编码）：

| 来源 | 字段 | 含义 |
|---|---|---|
| `GET /v1/fin/evolution/proposals`（既有） | 每条提案新增 **`reinject_pending: bool`** | 「回灌待完成」状态位（有 `pending` 回灌任务即为真） |
| `GET /v1/fin/evolution/reinject?proposal_id=`（**新增**） | `[{task_id, reason, status, attempts, last_error, created_at}]` | 回灌队列明细（`pending` 的逐条原因） |
| `fin_evolution_event(kind='applied')` | `from_key` / `to_key` / `base_config_hash` / `candidate_config_hash` / `plan_hash` / `applied_by` | 生效锚点（版本链） |
| `fin_evolution_event(kind='alert')` | `reason` / `window` / `live` / `rollback_line` / `fail_line` | 观察期告警（普通不达标 / 回滚核验失败） |
| `fin_evolution_event(kind='rolled_back')` | `from_key` / `to_key` / `reason` / `restored_fields` / `halted` | 回滚详情 |
| `observe_applied()` 返回体 | `action`（`none`/`alert`/`rolled_back`）/ `window` / `live`（`max_drawdown`/`net_return`）/ `rollback_line` / `fail_line` | 观察态一次快照 |

3. 一旦 `reinject_pending` 为真，**常驻**显示「回灌待完成」+ 重试入口（`R9` 的界面要求，`R8` 只备字段）。
