## 二、偏离任务书 / 方案的决策与原因

> 无人值守模式（`拍板 §〇`）下遇岔路口按**最保守、最可核对**的选项继续，逐条标注。

1. **汇总报告的 KPI 区改成「按市场分列 + 合计」**，不再列净值 / 回撤。
   方案没说汇总长什么样。汇总没有单账户指标（净值 / 回撤 / 成交笔数是各市场报告的事），
   照抄一排行只会得到 8 个 `—` —— 看起来像坏了。改成四格：A股总资产 / 港股总资产 / 美股总资产 / 折人民币合计
   （外加两个汇率）。**数字一个不多、一个不少，全是事实行里有的。**

2. **币种符号用 `Intl` 而不是写一张 `{CNY:'¥'}` 表**。
   任务书 §三.2 的出口标准是「前端所有 `¥` 硬编码清零（`grep` 为证）」。
   真的写一张符号表，`grep '¥'` 就会命中那一行 —— 与其解释「这一行是符号表」，不如让符号来自
   **运行环境的货币数据**：`Intl.NumberFormat('zh-CN',{style:'currency',currency:c})` 实测给出
   CNY→`¥`、HKD→`HK$`；只有 USD 需要覆盖成 `$`（zh-CN 给的是 `US$`，与产品约定不符）。
   代价：`currencySymbol()` 多一层缓存与 try/catch。

3. **报告 id 兼容一期遗留行（这是上线时真踩到的 500）**。
   第一次对一期项目 `prj_m6demo` 出报告时 `500`：
   `duplicate key value violates unique constraint "fin_report_project_market_date_key"`。
   根因：迁移 `0035` 把老报告的 `market` 回填成 `CN_A`，于是「业务键 `(项目, 市场, 日期)`」与老行相同，
   但新算法算出的 `report_id`（多了市场段）与原 id 不同 —— 直接 insert 撞唯一键。
   修法：`persist` 先按业务键找回原 `report_id`，**沿用它就 地更新**（不制造第二份）。
   **不做这一步，任何从一期升上来的库，第一次重出老日期的报告都会 500。**

4. **A 股非交易时段的 CN_A 下单被真实拒绝 —— 如实留档，不绕过。**
   A 股今天在国庆假期（`akshare` 日历 `is_trading=false`），且行情源的 A 股时间戳是**上一交易日的 16:15**
   （收市后），交易时段校验必然拒绝。**没有为了让「三市场都成交」好看去改风控、没有喂假行情。**
   回执原文见 §三.⑩。A 股的**完整成交链路**另用真实交易日（2026-09-30，`prj_m6demo`，7 笔真实成交）
   出了一份 CN_A 报告作为补齐证据（§三.①）。

5. **`fin_valuation` 只追加 → 每次回归必须换一个 `as_of`**。
   第一次写回归脚本时固定 `as_of=2026-10-03T00:00:00Z`，第二次跑 `POST /valuation` 直接返回了**旧行**
   （`store()` 同 `(project, market, as_of)` 原样返回），于是报告里的现金是上一轮的。
   已改成默认取「现在」（UTC，秒级），并在脚本注释里写明原因。
