## 〇、一句话结论

**「AI 写复盘」这件事被拆成了三层，数字那一层 AI 碰不到：**

- **事实层**由确定性代码从账本算出，一行一个 `metric_key`，带 `source_ref`（从哪来）
  与 `computed_by`（哪段代码算的）；
- **分析层**由 AI（或规则文案）基于事实表写，**只能使用事实表里的数字**；
- **表达层**渲染成 HTML 产物，进 `hunter_artifacts`。

生成后**必过回读校验**：把正文里每个数字抽出来逐个比对事实表，对不上就
`status='failed'`、**不出产物、不写发布回执**。这条防线用「AI 故意写错一个数」实测过两次
（一次端到端写库、一次只读自检），都拦下了。

## 一、做了什么

### 1. 三层结构，落库落地

| 层 | 谁做 | 落哪 | 代码 |
|---|---|---|---|
| 事实层 | **确定性指标代码**（AI 碰不到） | `fin_report_fact` 每行 `metric_key/value/unit/source_ref/computed_by` | `apps/api/app/services/fin/report.py::build_facts` |
| 分析层 | AI 基于固定事实写（不可用时降级为**规则文案**） | `fin_report.analysis_text` / `self_review`（JSONB） | `analyze_with_llm` / `fallback_analysis` |
| 表达层 | 风格化渲染（一期一种风格） | `hunter_artifacts.published_artifact`（HTML）+ `fin_report.artifact_ref` | `render_html` |

**19 个指标**（`METRIC_SPEC` 是唯一标签来源，渲染与提示词都读它，不另抄一份）：

`initial_capital` · `total_assets` · `cash_available` · `cash_frozen` · `market_value` ·
`nav` · `return_pct` · `daily_return_pct` · `max_drawdown` · `fee_total` · `fee_today` ·
`trade_count_today` · `trade_count_total` · `position_count` · `open_order_count` ·
`recon_passed` · `data_quality_ok` · `days_traded` · `return_caliber_count`

任务书点名的六项（`nav` / `return_pct` / `max_drawdown` / `fee_total` / 当日成交笔数 / 持仓数）
全部在内。**算不出就是 `None`，渲染成 `—`，绝不兜底成 0**（`总控规则 §六-1`）——
典型场景：只有一根净值点时 `daily_return_pct` 与 `max_drawdown` 都算不出（下 §四有实证）。

### 2. 「今天的自我总结」三栏

`fin_report.self_review = {did_well, did_bad, change_tomorrow}`，三栏都进回读校验
（`validate_report` 逐字段扫，不只看 `analysis_text`）。AI 只写文字；
提示词里把「正文里出现的每一个数字都必须逐字来自事实表」写成硬性要求第 1 条。

### 3. 正则回读校验（本轮核心）

`extract_numbers` → `validate_numbers` → `validate_report`。三个设计点：

- **先掩掉不是「数字主张」的东西**：ISO 日期 / 时刻 / `T+1`·`MA20` 形态的标识 / 版本号。
- **裸 6 位代码不无脑掩**：`601398` 与 10 万档的本金 `100000` 都是 6 位数。做法是
  代码命中「本项目持仓 + 成交的代码集」才忽略 —— 本机实测过：不这么干，
  `manage` 档的 `100000` 会被当成代码掩掉。
- **比对是精度感知的**：事实按主张的小数位数四舍五入后相等即算命中
  （`nav 1.000000` 与正文里的 `1.00` 是同一个数）；带 `%` 的主张只认 `%` 单位的事实，
  反之亦然 —— 单位错了就是错了。

校验不过 → `status='failed'` + **不生成 HTML 产物** + 写一条 `FAILED` 发布回执。
校验通过 → `status='validated'` + HTML 产物 + `SUCCESS` 回执 + `artifact_ref` 落库。

`prompt_version`（`fin-report-zh@1.0`）与 `llm_model` 都落库，便于事后追溯。

### 4. 生成时机、幂等与空态

- **接在 `15:30` 时点里、收盘估值之后**（`apps/fin-worker/app/workflows.py` 的
  `close` 分支末尾）：报告的事实层读的正是刚写下的那次收盘估值。
  加在分支末尾（M4 交接的 replay 提示），整体退出走 `req.get("report", True)`。
- **`fin_worker` 仍然是「不碰账本」的**：新增 Activity `generate_daily_report`
  在 `paper` 登记一条 `type='report'` 的 `fin_job`（幂等键 `fin-report:{项目}:{交易日}`），
  调 api 的 `/api/internal/fin/reports/generate`，再按结果收尾
  （validated → SUCCEEDED + 产物引用；failed → **FAILED** 且不重试；no_report → SUCCEEDED + 原因）。
- **报告 id 从业务身份推导**（`rpt_ + sha256(project:date)[:24]`，不含随机数）：
  同项目同日重跑覆盖同一行，事实行按 `(report_id, metric_key)` upsert，不产生第二份。
- **无报告日 → 空态**：这一交易日没有收盘估值时，生成接口返回
  `{created: false, status: "no_report", reason}` 并且**一行都不写**；读接口返回
  `{report: null, facts: [], receipts: [], empty_state: {...}}` —— 不是空白，也不是编一份出来。

### 5. 数字口径校验（M-32）

- **可重复跑的脚本**：`apps/api/scripts/check_report_numbers.py`
  （`--report` / `--project + --date` / `--list` / `--tamper`），逐行打印
  「数字 → metric_key」，就是「可追溯」的凭据。退出码 0/1/2。
- **接口**：`GET /api/v1/fin/reports/{id}/validate`（同样逐数字回追）。
- **不信任落库时的结论**：`validate_stored` 用同一份事实重新跑一遍回读校验。
- **「三种口径不拼接」写成可校验的事实**（`assert_single_caliber`）：
  ① 事实行 `return_caliber_count = 1`（本期只有实盘模拟一种口径）；
  ② **任何事实行的 `source_ref` 不许指向回测 / 前向模拟 / 影子**。
  HTML 产物里也常驻一句：「收益口径：**实盘模拟（1 种）**……**回测 / 前向模拟 / 影子运行
  不与之拼成同一条曲线**（01方案 §2.2）」。

### 6. 验收夹具（不是产品功能）

`apps/api/scripts/seed_m5_demo.py`：构造一个专用项目 `prj_m5demo`（manage 档 · 本金 10 万 ·
2 笔成交 · 3 天估值 1.0000 → 1.1200 → 1.0500 · 一条对账），**幂等**，可反复跑。
它的作用只是让报告有真账本可读；报告本身的每个数仍由报告代码从这些行算出。

## 二、偏离方案的决策与原因

### 偏离 1 · 报告生成落在 `api`，不落在 `paper`（与 M4 交接的建议不同）

M4 交接说「`paper` 侧没有也不需要加『生成报告』端点」。顺着这句话往下，报告代码需要一个
**同时能读账本、能调 LLM、能写产物**的地方 —— `api` 三者都有（`providers.llm` +
`hunter_artifacts` + 已在写 `fin_project`），而 `paper` 按设计不该碰 LLM。
于是：**`paper` 一行没改**，报告放 `apps/api/app/services/fin/report.py`。

**读账本的方式**：api 直接读 `fin_*` 表（只读），而不是绕 paper 的 HTTP。
三条实测理由：① 最大回撤要**整段净值序列**，而 paper 只暴露 `/valuation/latest`；
② 报告要按「某一交易日」出，需要按 `as_of` 过滤，纸面上没有这个读接口；
③ `api` 本来就在读 `fin_project`（M1 的开户）。**写账本仍然只归 paper** —— 红线未动。

### 偏离 2 · 给 `api` 加了随代码走的幂等 DDL（老库缺列）

`hunter_artifacts.published_artifact` 在本机 M4 那个验收库里是「只有 markdown」的版本
（实测 `information_schema.columns` 里没有 `artifact_type` / `content_html`），
而现仓的 artifact 路由早就在用这两列 —— 说明它们靠的是手工跑过的
`apps/api/sql/20260807_artifact_html.sql`。M5 要往这张表写 HTML 报告，
所以把它写成 **`db/migrations/0026_fin_report.sql` + `report.ensure_columns()` 两处幂等 DDL**
（`CLAUDE.md` 铁律：migrations 里的 .sql 对已有部署不生效，真正生效的要随代码走）。
本机实测：`python -m app.migrate` 之后两张列就位，产物 insert 成功。

### 偏离 3 · 报告 id 由 `(project_id, trade_date)` 推导（不是随机 id）

好处是同日重跑天然幂等；代价是 `fin_report_fact` 用 `ON CONFLICT DO UPDATE` 而不是
纯追加。**理由**：`fin_report_fact` 的 API 角色只有 `SELECT/INSERT`（`0023` 的 GRANT），
而重算一份当天的报告是正常运维动作；用确定性 id + upsert 既不新增第二份报告，
也不违反「账本追加表不给 DELETE/UPDATE」的边界（报告不是账本）。

### 偏离 4 · 无 LLM 时降级为**规则文案**，并如实标注

本机验收环境没配大模型（`RuntimeError: 大模型尚未配置:缺 base_url`）。
降级产出的 `analysis_text` 开头写着「（未启用 AI 分析：<原因>。以下为按事实表生成的
自动摘要，只复述数字。）」，`llm_provider='fallback'`、`llm_model='none'`。
**这是降级，不是伪装**；数字照样逐条来自事实表、照样过回读校验。
（`used_fallback` 也在生成接口的响应里明示。）

2. `assert_single_caliber` 会扫**每一行**的 `source_ref`，命中
   `backtest / pred_backtest / shadow / 前向模拟 / 影子 / 回测` 任一即判失败
   （`test_single_caliber_rejects_cross_caliber_source` 是反证用例）。

HTML 产物正文里的原话：

> 收益口径：**实盘模拟（1 种）**。本报告的收益只来自这一条模拟账本；
> **回测 / 前向模拟 / 影子运行不与之拼成同一条曲线**（01方案 §2.2）。

## 五、本轮找出来并修掉的三个真实缺陷

**都不是 review 看出来的，是「把容器真跑起来」逐个撞出来的。**

### 缺陷 1 · 给过去某天出报告时会读进未来（前视）

`collect` 原来一律取**最近一次**估值。于是给 `2026-09-29` 出报告时，拿的是 `09-30` 的估值 →
被「trade_date 与估值日对不上」挡成 `no_report`；更要命的是**净值序列没有截断**，
`max_drawdown` 会拿 09-30 的点去算 09-29 的回撤 —— 这是典型的**看答案做题**。
修法：取**当日**估值；序列与成交都截到估值那一刻（`as_of <= valuation.as_of`）。
实测（09-29 报告）：`days_traded=2`、`trade_count_total=1`、`daily_return_pct=+12.00%`、
`max_drawdown=0.00%` —— 09-30 那根净值与那笔成交**没有**混进来。

### 缺陷 2 · 产物表 insert 撞 `short_id` 唯一键

`ON CONFLICT` 原来只兜 `(owner_user_id, source_message_id)`，而实际冲突发生在
`short_id` 上（验收夹具换过 owner 之后留下同名 short_id 的旧行）。
一次 500：`duplicate key value violates unique constraint "published_artifact_short_id_key"`。
改成按 `short_id` upsert（short_id 由 report_id 推导，稳定）。

### 缺陷 3 · 夹具自己不是幂等的

`fin_snapshot` 是**全局**的（按代码，不属于项目），夹具没清它，第二次跑就撞主键；
`fin_account` 只按 user_id 清，换了 owner 之后清不掉旧行。
两处都改成幂等写法（快照 `ON CONFLICT DO UPDATE`；账户按 account_id 或 user_id 清），
现在**连跑两次结果一致**。

## 七、下一里程碑（M6 · 前端四页）交接

**第一件事**：M6 的「每日报告页」直接打这三个读端点，**不要再写一套取数**：

- `GET /api/v1/fin/projects/{project_id}/reports/{trade_date}`
  —— `report` / `facts` / `receipts` / **`empty_state`**（无报告日时 `report` 为 `null`，
  前端照 `empty_state.reason` 显示空态，**不许编一份出来**）。
- `GET /api/v1/fin/reports/{report_id}/validate` —— 逐数字追溯表（M-32）。
- `GET /api/v1/fin/reports/{report_id}/artifact` —— HTML 产物。

**开工前必须知道的：**

- **前端零硬编码业务数字**（`strategies/agent.html` 那条约定同样适用）：事实值可能是
  `null` → 渲染 `—`，不要 `|| 0`。`facts[].value` 为 `null` 就是「没算出来」。
- **`status` 有三种要区分**：`validated`（正常）/ `failed`（**回读校验没通过，不可发布**，
  前端要明说原因，别当成正常报告）/ 空态（这天没有报告）。
- **不要在前端重算任何指标** —— 报告页只渲染 `fin_report_fact` 给的东西。
- 时点工作流加步骤的 replay 注意：`generate_daily_report` **加在 `close` 分支末尾**，
  部署请在收盘之后（15:30 之后），避免在途工作流重放对不上。
- 验收环境留在机器上：`prj_m5demo`（夹具，`seed_m5_demo.py` 可重建）、
  一次性 api 容器 `m5-api`（8599）。**用完记得 `docker rm -f m5-api`。**
