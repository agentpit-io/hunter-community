## 二、表与触发器设计（迁移 `0049_strategy_registry.sql`）

### 2.1 `fin_strategy_definition` —— 策略版本登记表（**只追加**）

`strategy_version_id`(PK) · `strategy_key` · `name` · `source_ref`（代码引用 / 公式） ·
`params`(JSONB) · **`content_hash`** · `origin`（`builtin`/`user`/`evolution`） · `note` ·
`created_by` · `created_at`。

- **`strategy_version_id` = `strv_` + 内容哈希前 24 位**（`strategy.version_id_of`，由
  `strategy_key + name + source_ref + params` 的规范化 JSON 求 sha256）。同一份内容在任何进程
  算出来都是同一个键（幂等），**内容变一个字就是新键**。
- 唯一索引 `(strategy_key, content_hash)`：同一个 key 下同一内容不会登记两次。
- 触发器 `fin_strategy_definition_immutable`：`BEFORE UPDATE OR DELETE` → `RAISE EXCEPTION`。

### 2.2 `fin_strategy_candidate` —— 候选状态事件（**追加式**）

`event_id`(PK) · `candidate_id`（= 被考虑的 `strategy_version_id`） · `strategy_key` ·
`project_id` · `kind`（`submitted`/`cancelled`/`activated`/`rejected`） · `payload`(JSONB) ·
`created_by` · `created_at`。触发器同样 `BEFORE UPDATE OR DELETE` → 抛异常。

**候选状态是「从事件重建的投影」，没有 `status` 列** —— 照四期「proposal 表一面只追加一面
UPDATE status」的教训（`记忆系统追加规则.md` §3.2 第 4 条）：审计以事件为准，状态列只做可重建投影。

### 2.3 权限：**一条 GRANT 都不写**

与 `0041`/`0043`/`0047`/`0048` 同一决定：登记不是账本，读写能力来自**连接身份**（库属主），
不来自 GRANT；「任何角色不给 DELETE」由**触发器**兑现（比「不给授权」更硬 —— 连属主都拒）。

## 三、为什么用机制保证不可变，而不是靠自觉

因为**「自觉」在本仓已经被证伪**：`fin_param.strategies[].version` 一直是自由字符串，
`fin_param` 是普通可 UPDATE 列，多处直接改写（`control.py` 三处 + 自进化通道）——
**没有任何机制阻止**「改一个字而版本号不动」。

四期 `R6` 已经给出了正确解法：`记忆系统追加规则.md` §3.2 第 3 条——「零 GRANT **不构成限制**
（应用若以 owner/superuser 连接），改用**数据库触发器** + **哈希审计**」。本段照做：

1. **内容哈希推导版本键** —— 「改内容」和「换键」在机械上就是同一件事，改不动老行；
2. **触发器** —— 老行 `UPDATE`/`DELETE` 一律抛异常（应用代码、甚至库属主连接都拦得住）；
3. **「改策略」的语义被钉死为「登记一个新版本」** —— 新键、新行，老行一个字节不动。

> ⚠️ 书面结论同 `0043`/`0047`：触发器对**表属主同样会触发**（这是它挡得住应用的证明），
> 但库属主 / superuser 永远能 `ALTER TABLE … DISABLE TRIGGER` —— 所以**不宣称「对机器所有者
> 绝对不可篡改」**。

## 四、三个正式入口（`apps/api/app/routers/fin_strategy.py` · 内网口令）

业务全在 `apps/api/app/services/fin/strategy.py`（唯一服务模块）。**服务层不写 `fin_param`** ——
让候选生效仍走 `control.py` 那个唯一写入口（红线 7）。

| 工具 | HTTP | 语义 |
|---|---|---|
| `strategy.submit` | `POST /api/internal/fin/strategy/submit` | 登记候选版本（**未生效**）+ `submitted` 事件 |
| `strategy.get` | `GET /api/internal/fin/strategy/get` | 查状态（候选 / 生效中 / 已取消 …，从事件重建） |
| `strategy.cancel` | `POST /api/internal/fin/strategy/cancel` | 取消**未生效**的候选；**已生效的拒绝** |
| （只读辅助） | `GET /api/internal/fin/strategy/active` | 项目当前生效版本（`fin-worker` 的 `strategy_version` 来源） |

**状态闭集**：`candidate`（候选）/ `active`（生效中）/ `cancelled`（已取消）是方案点名的三个；
`superseded`（曾生效·现已让位）与 `rejected`（提交被拒）、`registered`（只登记、未提交候选）
是**如实的额外终态** —— 不把它们硬塞进三个之一（「空的比假的好」同一精神）。

## 五、接线：复用四期 `R8`，不另起一套

| 点 | 做法 |
|---|---|
| **让候选生效** | **不改** —— 仍走 `control.py` 的唯一写入口（`set_strategy` / `activate_candidate`，红线 7） |
| **生效审计** | `control` 在**同一事务**里追加一条 `activated` 事件（`strategy.record_activated_event`，SAVEPOINT 兜错 —— 侧记失败不拖垮生效） |
| **版本键播种** | `tiers._strategies` 的 `version` 从 `"v1"` 换成登记行的稳定版本键（开户即指向真实登记行） |
| **`fin-worker` 取版本** | `build_decision` 经 `_resolve_strategy` 调 `GET /internal/fin/strategy/active` 拿稳定版本键；**拿不到就回退 `fin_param` 声明的原值**（离线照常决策） |
| **绑定数据集快照（L03 交接）** | `build_decision` 调 `data.snapshot_create` 冻结一张 `DataSnapshot`，写 `data_snapshot_id`；**建不出就留空 `NULL`**（不编假键） |

**示例策略「降级为内置策略」的落点**：`strategy.ensure_builtins()` 把 `tiers._STRATEGIES` 的每个内置
策略登记成 `origin='builtin'` 的定义，`source_ref` 指向**当前唯一的执行体**
`apps/fin-worker/app/strategy/sample.py:build_decision`。要「替换」它 = `submit` 一个 `source_ref`
不同（→ 新内容 → 新版本键）的候选，再经唯一写入口切换。**登记表就是「可被替换」的落点。**

**说清边界**：本段**没有**为「一个执行体」建插件加载框架（只有 sample 一个实现）；
登记表控制的是**哪一版身份在生效**，执行体仍是内置 sample（`note` 里如实写明）。
