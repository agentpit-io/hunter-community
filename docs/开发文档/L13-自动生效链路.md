## 二、偏离 / 需要如实理解的决策

### 2.1 自动入口「被拒」回 **HTTP 200 + 结构化原因**，不回 4xx

`/internal/fin/evolution/{id}/auto-apply` 在「开关关 / 方向不是收紧 / 闸门没过」时**一律返回 200**，
体里是 `{auto_applied: false, skipped: true, reason: "...", ...}`。**只有**「提案不存在」回 404。

理由：调用方是 `fin.shadow` 的 **Temporal 活动**，活动按 at-least-once **重试 6 次**。
若「被拒」抛 4xx，`HunterApiClient` 会抛 `ApiError` → 活动失败 → **重试 6 次**，
而每次闸门拒绝都会写一条 `rejected_by_gate` 事件 —— **重试会把事件刷屏**。
所以：**「被拒」是正常终局，不是错误**；活动连「调用失败」都不抛（见 §二.5），
从根上保证「不重试」。

### 2.2 方向拒绝的留痕 **不改提案投影状态**（`update_status=False`）

`rejected_by_gate` 在 `STATUS_OF_KIND` 里投影成 `rejected`。但自动路径拒绝一条**放宽**提案，
意思是「机器没代按」，**提案本身没被驳回** —— 人仍可在界面上确认它。
所以 `_record_auto_skip` 追加事件时传 `update_status=False`，提案状态**保持 `passed`（等人确认）**。
（闸门拒绝那条仍走 `apply_proposal` 的 `_gate_reject`，保持老口径 —— 那种「闸门没过」是真驳回。）

### 2.3 `apply_proposal` 多一个 `auto` 参数，人走的调用点**不用改**

给 `apply_proposal` 加 `auto: bool = False`（默认假），生效事件 payload 里多标一句 `auto`。
人走的两个入口（`/internal/…/apply`、`/v1/…/apply`）不传 → 写 `auto: false`；自动路径写 `auto: true`。
**这是一行 payload 字段，不是判据** —— 不影响任何人走的鉴权 / `confirm` / 闸门。
单独一个布尔是为了让界面 / 查询不必去解析 `actor` 字符串。

### 2.4 自动路径**也传 `confirm=True`**（不绕 `confirm` 语义）

`apply_proposal` 里 `if not confirm: raise …` 那道锁**一个字没改**。自动路径只是**代按**：
`apply_proposal(confirm=True, actor='system:auto-apply', auto=True)`。
「谁按的」由 `actor` 写清。人走的入口照旧**必须调用方显式传** `confirm=true`。

### 2.5「验证通过」的 `passed` 事件来自 **R7**，L13 从它之后开始

`passed` 事件由现成的 `evaluate_validation()`（影子盘两臂比对、样本够了自动判定）在**终局**写出。
L13 **不重新判验证**（任务书 §三.A.3 明令「交给现成的 `apply_proposal` 去判，不要重复实现判据」），
只做「`passed` 之后那一步」。所以自动化程度是：**提建议 → 验证 → 应用** 三段全自动，
中间那段（R7）本段一行没动。

### 2.6 改了 `test_workflows.py` 的活动清单（**不等于改松测试**）

`test_activity_list_covers_workflow_calls` 断言「登记的活动的集合 **恰好等于** 这份清单」。
新增一个活动就必须往清单里加一行 —— 这是**该用例的设计意图**（它是一份完整性守卫，
历史上一路加过 R7 / R13 / L01 / L09 的注释分组）。本次**只是把 `auto_apply` 加进去**，
断言从「恰好 24 个」变成「恰好 25 个」，是**更严**而不是更松。**没有动任何别的用例文件。**
