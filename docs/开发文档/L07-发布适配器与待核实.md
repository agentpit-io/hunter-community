## 一、做了什么（人话）

技术方案 §9.1 把发布流程定成一条链：`冻结估值 → 生成 ReportFacts → 分析 → 渲染 → 校验 → 调用发布适配器 → 保存渠道回执`。
改造前这条链**断在最后两步**：发布**内嵌在生成流程里**、渠道是**写死的字符串**，而且
「发出去了但不知道成没成」这个状态**表里留着、代码从不写**（方案 §2.1 第 5 条）。

本段补上三件事：

1. **发布拆成独立一步、渠道走适配器**：新增 `apps/api/app/services/fin/publish/` ——
   **接口统一**（入参：报告 + 目标；出参：状态 + 回执），三个适配器：
   - `in_app` —— 把现成行为原样搬进来（**行为不变**）；
   - `webhook` —— 通用 Webhook（POST 到可配置 URL，本机假接收端即可测）；
   - `file` —— 文件落盘（记路径 + `sha256` 校验和）。
   **只做这三个**，不接任何要注册 / 要付费 / 要审资质的第三方内容平台（`§6.1` 边界）。
2. **`publish.submit` / `publish.get` 两个入口**（`§10.1`），回执统一落 `fin_publish_receipt`。
3. **`UNKNOWN` 待核实 + 不盲目重发**：超时 / 回执不明 → 写 **`UNKNOWN`**（本段的核心动作），
   进**待核实队列**；**`UNKNOWN` 下再发同一份报告 → 拒绝**，除非显式带**重发标记**
   （且重发**留痕**：谁 / 何时 / 为何）。核实 = 查外部状态（webhook `status_url` / file 重算校验和）
   或**手动**落定 → `SUCCESS` / `FAILED`；查不出就**保留 `UNKNOWN`**（`§11.2`）。
4. **补上故障注入第 7 项**（`§14.1`「内容已发布，但返回超时或网络断开」）—— 真跑一遍，结果见 §五。

              submit（未通过数字回读校验） ──────────────► FAILED（不发布，无产物）

## 四、偏离 / 决策与原因

1. **`in_app` 回执 id 公式保持不变**（`rcp_<sha256("{report_id}:in_app")[:24]>`）。
   新渠道按同一公式 `rcp_<sha256("{report_id}:{channel}")[:24]>` 推导 —— 同一报告同一渠道**一行回执**，
   重复提交就地更新。**老数据 / 老用例不动**（用例 `test_receipt_id_in_app_matches_legacy` 盯着）。
2. **连接被拒 = `FAILED`，超时 = `UNKNOWN`**。判据：请求**根本没发出去**（connect refused / DNS）
   → 可安全重试，判 `FAILED`；**可能已送达**（读超时 / 对方中途断开 / 说不清）→ `UNKNOWN`。
   这是「宁可待核实，不可盲目重发」的保守取舍。
3. **`FAILED` 允许直接重试，不加重发标记**。它明确「没发出去」，重试是安全的；
   只有 `UNKNOWN`（可能已发出）才需要显式重发标记。方案 §9.2 原文只对结果不明要求「不盲目重发」。
4. **`SUCCESS` 再提交 → 幂等返回（不重复发布）**，不是被拒。方案 §2 要求「不盲目重复发布」。
5. **回执 `target` 列存「目标规格字符串」**（dict → JSON 字符串），而不是只存 URL ——
   因为 `UNKNOWN` 核实时要**知道去哪回查**（`status_url`）。webhook 目标因此支持
   `{"url": ..., "status_url": ..., "headers": ..., "timeout": ...}` 与裸字符串两种写法。
6. **file 适配器不产生 `UNKNOWN`**（本地写盘，成功即确认）。它的 `probe` 仍实现
   （重算磁盘文件的 `sha256` 与回执里记的比对）—— 供「落了网络盘 / 写完回执前进程挂了」这类
   将来场景核实用。
7. **新增 HTTP 端点走 JWT + 归属校验**，放在默认硬鉴权前缀 `/api/v1/fin/…`（**不是**免登录前缀），
   写操作（发布 / 核实）不会裸露给匿名。
8. **没有新增调度、没有新增基础设施**（`§6.1`）。适配器是纯代码，目标 URL / 目录由调用方给。

## 五、故障注入第 7 项（`§14.1`）· 真跑结果

脚本 `apps/api/scripts/inject_publish_timeout.py`：假接收端 `/deliver_then_hang`
**先把请求体完整收下并记账，再挂起 3s**；发布方 `timeout=0.5s`。

```
$ TEST_DATABASE_URL=postgresql://hunter:hunter@127.0.0.1:5598/l07_test PYTHONPATH=. \
    .venv/bin/python scripts/inject_publish_timeout.py
[1] 假接收端已起：http://127.0.0.1:40847   （/deliver_then_hang：先收下、记账，再挂起 3s）
[2] 发布（客户端超时 0.5s）→ status=UNKNOWN  detail=结果不明（0.5s 内没拿到回执，可能已送达）：ReadTimeout
[3] 接收端日志：其实**已收到** 1 份，bytes=259（内容已发布，只是回执超时 —— 所以不能盲目重发）
[4] 不带重发标记再发 → 被拒 [unknown_needs_resend]：上一份回执状态为 UNKNOWN（结果不明，可能已经发出去了）——要重发必须显式带重发标记并写明原因（report=rpt_inj7_e63e2ecff6 channel=webhook）
[5] 核实（查外部状态 http://127.0.0.1:40847/status）→ status=SUCCESS resolved_at=2026-10-04T19:37:35.591024+00:00  probe=SUCCESS

故障注入第 7 项：**通过** —— 超时判 UNKNOWN、拒重发、核实后落 SUCCESS；临时数据已清理。
```

这正是方案 §14.1 第 7 项要防的场景：**内容已经发出去了，但发送方只看到超时**。
本段用 `UNKNOWN` 把它挡住 —— 不重复发，先核实。

## 七、未接数据源清单（`五期追加规则 §五` 第 15 条）

**本段不涉及业务数据源** —— 发布适配器只处理「把已经算好、已经校验过的报告送出去」，
不引入任何新的行情 / 财务 / 情绪数据。故**数据源侧「未接」= 无**。

但按 `§6.1`，必须写清**「没接哪些外部平台、为什么」**：

| 没接的类别 | 具体 | 为什么没接 |
|---|---|---|
| 要注册 / 要付费 / 要审资质的**第三方内容平台** | 微信公众号 / 知乎 / 微博 / Medium / Substack / X(Twitter) 等 | `§6.1` 明写「**不接**任何要注册、要付费、要审资质的第三方内容平台」；完整度分析 §七 第 6 条把它定性为「要花钱 / 建新基础设施」的**延后项** |
| 邮件 / 短信 / IM 推送 | 邮件网关、企业微信、飞书、Telegram Bot 等 | 同上；且这些属于「通用通知工具」，`§9.2` 末句明确「**不能将通用通知工具视为支持所有平台的文章发布工具**」 |

**将来要接某个具体平台时动哪里**：在 `publish/` 下加一个适配器（实现 `submit` / `probe` 两个方法），
在 `publish/__init__.py` 的 `ADAPTERS` 登记一行，`CHANNELS` 加一个名字即可 ——
**上位机（生成流程 / 路由 / 待核实队列 / 重发判据）一行都不用改**。这就是把接口做对的意义。

人工登记入口：发布目标（URL / 目录）由调用方在 `POST /api/v1/fin/reports/{id}/publish` 的
`target` 字段给出；`file` 渠道的目录即「人工指定的落盘位置」。

## 八、遗留问题

1. **api 全量用例里有 17 条**（`tests/test_fin_evolution_router.py`）**在「整目录一次跑」时失败 —— 这是既有的测试污染，与 L07 无关**。

   后者用它自己的 `test-internal-key` 打请求时 `internal auth failed`（401）。
   **证据**：`pytest tests --ignore=tests/test_fin_publish.py --ignore=tests/test_fin_publish_router.py`
   （即**不含任何 L07 用例**）同样 17 条失败；单独跑 `tests/test_fin_evolution_router.py` → `18 passed`。
   本段**不改别人的用例**（红线 6「顺序强制、别越界」）；已在 §六 表里给出「排除污染源一次」的干净读数（959/0/4）。
   建议后续单开一个小修：`test_fin_evolution_propose.py` 收尾还原 `_INTERNAL_KEY`。
2. **`fin_report.status` 的 `'published'` 仍未使用**。本段把「发布状态」放在**回执表**（一行一渠道），
   报告行仍是 `validated`。这是有意的：一份报告可发多个渠道、每个渠道各自 SUCCESS/FAILED/UNKNOWN，
   用报告行的单一状态表达不了。**没有写 `'published'` 不是遗漏**，是口径选择（可讨论）。
3. **重发留痕只在回执行上（`resend_*` 四列），不是逐次追加的日志**。同一 (报告, 渠道) 多次重发时，
   只保留**最近一次**重发的 who/when/why；上一次的会被告辞 `detail` 里累积的「· 核实[…]」部分覆盖不到。
   若将来要求完整重发审计链，需要一张追加式 `fin_publish_attempt` 表（本期未做，避免过度建设）。
4. **`in_app` 渠道暂不支持「核实」**（`probe` 恒返回 `None`）—— 站内产物本地写、写成功即确认，
   不存在「结果不明」，属设计。
5. **目标（URL / 目录）由调用方给，未做白名单**。`file` 渠道能写到 api 进程可写的任意路径、
   `webhook` 能 POST 到任意 URL（含内网地址）—— 这是「通用 Webhook / 文件落盘」的固有形态，
   与 `L06` 的「执行允许名单」不是一回事（那是下单执行，本段是发布）。**当前端点走 JWT + 报告归属校验，
   只有报告所有者能发**。若要收紧（限制目标域名 / 目录白名单），应单开一段，**不在这里顺手加**。

## 九、给 `L08` 的交接

- **`L08` 的控制通道**（`runtime.workflow_start/get/pause/cancel` + MCP 控制类 + 长任务取消）**不受本段影响**：
  本段只加了发布这一层的 HTTP 端点与适配器，**没有改 Temporal、没有另起调度**（`§6.1` / 红线）。
- 若 `L08` 要让**工作流**触发外部发布，直接调 `publish.submit(conn, report_id, channel, target=…)` 即可 ——
  幂等 / 不盲目重发的判据都在服务层，工作流侧不用重复实现。
