#### 3.1.1 S14 的一个**如实说明**（不是 `R20` 回归）

`r10_demo_verify.py` 的提案 id 是**写死的全局主键**（`evp_r10verify_passed000001`）。
演示站上这条早就属于 `R10` 的验收项目 `prj_2a30fdf07de949e19695d043`（`status=applied`）。
所以：

- **对 `R10` 的验收项目跑 → 24/24**（与 `R13` 一致；这也是脚本设计的用法）。
- **对一个全新项目跑 → 22/24**：`s567` 提议时命中 `EvolutionConflictError` → 复用**别的项目**那条提案，
  它的 `base_config_hash` 是当年那次（已被 `S9` 改动过的）配置；`s12` 拿**新项目**的 hash 去 apply → CAS 拒。

**证明这不是 `R20` 的回归**：把同一版工作区代码（`1.8.0`，与镜像同源）在本机 `r21_test` 上对
**同一个项目**重跑 → **24/24**（S12a 事件链 `['rolled_back','applied','rejected_by_gate','passed','validating','created']`）。
`R20` 对 `evolution.py` 的改动只有一处（`propose` 的闸门改成按项目判），**没碰 `apply_proposal` / `rollback_proposal`**。
这是**脚本写死 id + 共享演示库**的历史局限，**不是本版引入的回归**，单独记进 §五。
