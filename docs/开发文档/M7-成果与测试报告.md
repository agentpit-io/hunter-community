**结论与决策：**
1. **A 股真实行情可用，走腾讯免费通道**（`fin_data._tencent_quote`）。它给得出
   **沪深 Level-1：最新价 + 买一/卖一价量**（上面 601398 的 `bid1 8.27×9562 / ask1 8.28×11922`

   港美股盘口缺失如实标注，不用别的字段顶替。
3. `market_source` 里 A 股被显式关掉（「A 股不走这里 —— 原链路已经通了，别抢」），
   而原链路在本机**没通**（无 key）。所以新增的解析器写在新模块 `fin_data` 里，
   **没有改 `market_source` 的行为**，港美股仍走它。
4. **akshare / yfinance 两条路都不可用**，如实记录；`08 §九-5` 那条待验证项
   在本机有了结论：**沿用 `providers.data_source` 的取数实现，但一期实际生效的是免费通道**。

> 今天是国庆假期（10-01 ~ 10-08），A 股所有票的最新 tick 都停在 **09-30 16:14 前后**，
> 这是数据源的真实状态，不是程序错误。08/09/10 的报价是当天港美股的真实盘中价。

三项必查对应的就是：`balance_equation`（持仓市值 + 可用 + 冻结 = 总资产）、

同一次估值给出的三个数：`可用 97989.98 + 冻结 0 + 市值 2000.00 = 总资产 99989.98`。

> `balance_equation` 取的是**账本里记过的那一个** `total_assets`（估值行），不是拿推导值跟自己比 ——
> 后者是恒等式，证不了任何东西（没有估值行时实现会如实标 `derived=true`）。

**结论：** 重试拿回**同一个 `job_id`**，库里只有一行。`ID` 只在 `INSERT` 之后才返回
（`09 §4.7`「任务只有在已持久化后才能返回 ACCEPTED」），所以「根据稳定请求标识找回原
`job_id`」有依据。

### FI-2 ✅ 模拟订单已提交或记账，但回执丢失 → 返回原订单与成交，**不再创建**

### FI-3 ⚠️→✅ 同一计划重复触发，两个 Worker 同时处理同一账户

**第一次真跑：双双成交（这是本轮跑出来的真缺陷）。**

```bash
VER=$(psql ... "SELECT version FROM fin_project WHERE project_id='prj_m7demo'")   # = 1
# 两个 Worker 同时提交，同一 expected_version=1
curl ... -d '{"...","expected_version":1,"idempotency_key":"fi3-A"}' & \
curl ... -d '{"...","expected_version":1,"idempotency_key":"fi3-B"}' & wait
```

```
worker-a: status=filled order=ord_44fa17383c2d4ee0805b0bb2 trade=trd_e0d68eaa72c84fa48124ecc0
worker-b: status=filled order=ord_268f3d0a9ceb44258ee395f9 trade=trd_d9ae79927447427391bc80af
version: 1 → 3    trades: 1 → 3
```

**根因**：`fin_project.version` 是**乐观锁**，只在调用方显式传 `expected_version` 且
那个版本已过期时才拒。两个请求**同时读到 version=1、同时通过检查**，谁也没被拦下。
更糟的是两笔 `freeze` 从同一个可用余额各冻一次，账本自此内部不一致（§五-7 那次不平）。

**修复**：`ledger.lock_project` —— 进事务先按 project 拿一把**事务级 advisory lock**
（`01方案 §11.2`「并发操作同一账户 → 版本校验、事务锁或单写者机制」里的「事务锁」）。
四条会改账本的路径（下单 / 再撮合 / 撤单 / 过期）都加了闸门。

**重跑（修复后）：**

```
worker-a: status=filled   order=ord_e1f6ac4230a14cadabbffb03 trade=trd_16e0b767e4694bb787622454
worker-b: status=rejected order=ord_e4d94760e74049cdb3293db2 trade=None
          reason=账户版本冲突：委托基于 version=3，当前 version=4。同一账户的并发命令里，后到者被版本校验拦下
          expected=3 actual=4
version: 3 → 4    trades: 3 → 4（只 +1）
```

**结论：** 一个成交、一个被版本校验拦下，版本只 +1，账本只多一笔。
回归用例 `apps/paper/tests/test_concurrency.py`（**去掉闸门时该用例会红**：`['filled','filled']`，
已验证）。

### FI-5 ✅ 行情断流后恢复，旧信号已经过期 → 丢弃并重新分析，**不补造成交**

见 §四-1 与 §四-2：断流时（`999999`）不落快照、记缺口、拒绝委托；
恢复后数据源有了新价，但旧信号的 `valid_until`（09:30）早于快照时刻（16:14:58）→
**拒绝并写明两个时刻**，没有补成任何成交。

```
decline_reason = 委托已过有效期（有效期至 2026-09-30T09:30:00+08:00，快照时刻 2026-09-30T16:14:58+08:00）
```

**结论：** 「过期不补单」是**在撮合之前**判的（`engine.execute` 的 ②-预），
且判据是**数据源时刻**而不是本机时间 —— 重试不会把一张过期单补成成交。

## 七、偏离方案的决策与原因

| # | 偏离 | 原因 |
|---|---|---|
| 1 | **新增腾讯免费通道的 A 股解析器**（放在新模块 `fin_data`，不动 `market_source`） | 官方链路在本机无 key，akshare/yfinance 都不可用；而 A 股是这个项目唯一的目标市场，「沪深 Level-1」这条验收项没有别的真数据可依。`market_source` 里 A 股被显式关掉且注释写明「别抢」，所以另起一个只读解析器，港美股仍走它 |

| 9 | **`_run_point` 支持 `project_id` 过滤** | 验收环境里有 400+ 个测试残留项目，一次手工触发会给每一个下单，证据被冲散。调度器永远不带这个字段，生产路径逐字节不变 |

## 八、本轮发现并修掉的缺陷

1. **并发同账户双双成交（FI-3 跑出来的）**：乐观锁对**同时**提交的两个请求两边放行，
   而且留下**内部不一致的账本**（两笔 `freeze` 从同一个可用余额各冻一次）。
   修复：账户级事务锁 `ledger.lock_project`。→ `apps/paper/tests/test_concurrency.py`。
2. **`/internal/trigger/{point}` 漏 catch `WorkflowAlreadyStartedError`** → HTTP 500
   （「同一天同一时点已跑过」是预期拒绝，不是服务故障）。已补 catch → 409。
3. **美股 `event_time` 时区错**：第一版一律贴 `+08:00`，于是 12:04 ET 被记成 12:04 CST，
   **差 12 小时且不报错**。已按市场给时区（修复后实测 `AAPL ts=2026-10-02T12:25:40-04:00`）。
   → `apps/api/tests/test_fin_data.py::test_event_time_us_is_new_york_not_cst`。
4. **`is_now` 严格比较把「现在的对账」判成历史时点**：调用方把 `as_of` 写成"此刻"时
   落在服务端 `now()` 前面几毫秒是常态，于是 `project_version` / `position_ties_trades`
   被静默标成 `skipped` —— 三项必查里有两项没真跑而结果显示「通过」。已加 5 秒容差。
5. **`fin_data_gap` / `fin_alert_log` 的 `ensure_table` 会把事务打成 aborted**：
   `fin_paper_rw` 是受限角色，跑 `CREATE TABLE` / `GRANT` 没权限，错误在很远的调用点
   冒出来（「current transaction is aborted」）。改成**先查 `to_regclass` 存在性**再决定要不要 DDL。
