## 二、偏离方案的决策与原因

### 2.1 `human_mixed` 的落法：**服务端按证据真值判定**，不加第三个工具名

`plan/R3.md` §一.1 要求「人的成交 → 单独产出一条 `source='human_mixed'` 的经验……工作流只要走对应通道即可」。
但 R2 的规则 7 把它写死了：**内网口令 → `ai`；JWT → `human_mixed`**，而 `fin-worker` 手里**没有 JWT**
（它只有 `HUNTER_INTERNAL_KEY`）。两条硬要求正面撞车。

两条出路都不好：

- **新开一条内网路由** `/internal/fin/memory/evidence/human` —— 那等于**第三个工具名**，
  直接违反红线 2（「读写只有 `memory.query` / `memory.append_evidence` 两个工具名」）。
- **让工作流自己传 source** —— 直接违反规则 7「入参里传什么都不认」。

**采用的办法**：`source` 仍然由服务端定，判据从「谁在调」扩成「谁在调 **+ 证据是谁的交易**」：
内网通道写经验时，若**每一条证据都是人工成交**（`fin_trade.source ∈ {human, human_confirmed}`），
记 `source='human_mixed'` / `created_by='human:trade'`；否则记 `ai`。
`resolve_source()` 在 `memory.py`，`_verify_refs` 顺带把 `fin_trade.source` 读回来。

这条判据**伪造不了**：调用方只能引用库里真实存在的成交行，而那一行的 `source` 是 paper 写下的。
掺一条 AI 证据或报告证据就退回 `ai`（保守方向：宁可把人工记成 AI，不把 AI 记成人的）。
**没有新增工具名**、**没有改变原有两个通道的行为**（R2 的 30 条真库用例全绿）。

### 2.2 「负向」这一层本轮**判不出来**，按任务书字面判据执行

§一.4 的判据是 `kind='verified'` + `status='已确认'` + `applicability` 命中：
**区分正负的 `polarity` 列在 `0042`（R5）才加**。所以本轮**任何**关于该标的的已验证结论都会拦单 ——
方向是安全的（只减少下单），但表达力偏弱。已在 `memory_gate.py` 顶部与 §七 交接里写明：
`R5` 拿到 `polarity` 之后要在这里加一道 `polarity='refute'`，并回来更新本模块与本文档。

### 2.3 复核回路**不产出 `verified`**（模型只能写 `fact` / `hypothesis`）

`kind='verified'` 要求 `method` + `sample_size`（样本笔数）。这两个数**只能来自真实的验证过程**，
模型从当日的账本读数里拿不到 —— 让它「随便给一个样本数」就是编数字（撞红线 5）。
所以复核回路的候选一律限定在 `fact` / `hypothesis`；`verified` 留给后续的验证器。

### 2.4 复核端点在 **api 侧**，`review_propose` 由 api 调模型

`fin-worker` 没有 LLM 客户端（也不该加：它是 Runtime Bridge，不碰推理）。
口径照 `report.generate`：`POST /internal/fin/reports/generate` 也是 api 侧调模型。
所以新增 `services/fin/review.py`（收集 + 提议 + 回读校验）与 `routers/fin_review.py`（两个内网端点）；
`fin-worker` 的三个活动只做 HTTP 往返，**全程不碰数据库**。

**这一层一行经验都不写**：候选由 `review_append` 提交到 `POST /internal/fin/memory/evidence`
（唯一写入口）。于是「经验三表只有 `services/fin/memory.py` 碰得到」在复核这条链路上也没破
（`test_fin_memory_guard.py` 仍绿）。

### 2.5 `review_append` 自己做幂等（经验 id 是服务端生成的随机段）

Activity 是 at-least-once。经验 id 不可预知，所以不能用幂等键；
这里用**内容身份**去重：写之前先 `memory.query` 把该项目已有经验读回来，按
`(statement, 证据集合)` 建表，已存在的候选直接跳过。读不回来 → **抛错让 Temporal 重试**（不硬写）。

### 2.6 `fin.review` 对「读不到经验集」是 **fail-closed**

`freeze_memory` 读不到经验集时抛错让 Temporal 重试，**不放过这道闸门**。
反过来（读不到就跳过经验检查照常下单）正是「只收紧不放松」要防的事 ——
一个读不到的故障不该变成一次没有刹车下的单。R4 的 `FIN_MEMORY_ENABLED` 会让服务端返回空集，
那时这条路径自然不再触发。

### 2.7 其余照方案执行，无偏离

- 内容哈希**只在服务端算**（`memory.py`），`fin-worker` 只是把 `query_filter` 读回来放进 checkpoint。
- 冻结**不新增列、不新增迁移**（`query_filter` 本就是 JSONB）。
- 时点 = 时段末点 + 延迟，**延迟不硬编码**（`config.review_delay_minutes()`）。

## 三、内容哈希口径（**契约**，换口径 = 换版本）

`plan/R3.md` §一.3b 要求把哈希口径写进成果文档。口径本身写在 `memory.py` 的
`CONTENT_HASH_VERSION` 旁边（`= "1"`），逐字如下：

```
content_hash(一条经验) = sha256( kind \x1f status \x1f statement \x1f applicability \x1f valid_until \x1f superseded_by )
    · 字段以 U+001F（单元分隔符）相连 —— 正常文本里不会出现，避免「AB|C」与「A|BC」撞值
    · NULL 一律写空串（不是 "None"）
    · 时间字段取 `.isoformat()`；其余取 `str()`
content_hashes         = { experience_id: content_hash }，按键**升序**（顺序固定 → aggregate 可复现）
aggregate_hash         = sha256( "".join(f"{id}={hash}\n" for id, hash in 升序(content_hashes)) )
```

存进 `fin_memory_snapshot.query_filter`：

```jsonc
{
  "filters": { "for_decision": true, "as_of_basis": "…", "market": "CN_A",
               "kind": null, "status": null, "exposure_scope": "searchable" },
  "for_decision": true, "as_of_basis": "…", "market": "CN_A", "kind": null,
  "status": null, "exposure_scope": "searchable",        // ← 与 filters 同一组键的**平铺副本**，
                                                          //   为了兼容 R2 已发布的读法
  "content_hash_version": "1",
  "content_hashes": { "exp_…": "…" },
  "aggregate_hash": "…"
}
```

回放时 `get_snapshot` 顺手算一遍此刻的指纹，返回 `content_drift`：
`frozen_aggregate_hash`（当时冻的那个，永远不变）· `current_aggregate_hash` · `drifted`（被改动过的 id）·
`missing` · `match`。**老快照（R2 冻的、没有 `content_hashes`）→ `hashes_frozen=false`，不假装匹配。**

## 四、规范化标的匹配口径（真值表）

口径写在 `apps/fin-worker/app/strategy/memory_gate.py` 顶部。两步：

1. 本次标的规范化成 **`<MARKET>:<CODE>`**（市场取决策上下文里的规范三值，代码去空格转大写）；
2. `applicability` **按非字母数字字符切词**，在词序列里找**连续的一段**与 `signature(标的)` 全等。

用「连续子序列」而不是「两词对」，是为了让 `CN_A` 这种带下划线的市场码（切词后是 `("CN","A","601398")`）
与 `HK`（`("HK","00700")`）共用一套代码。

**实测真值表**（`memory_gate`，本次运行的原始输出）：

| `applicability` 原文 | 本次标的 | 命中 |
|---|---|---|
| `HK:00700 追高后回撤` | `HK:00700` | ✅ |
| `HK-00700` | `HK:00700` | ✅ |
| `HK 00700` | `HK:00700` | ✅ |
| `US:0700 同类形态` | `HK:00700` | ❌ |
| `US:00700` | `HK:00700` | ❌ |
| `HK:0700` | `HK:00700` | ❌ |
| `放量后 0700 回落` | `HK:00700` | ❌ |
| `00700` | `HK:00700` | ❌ |
| `港股 00700` | `HK:00700` | ❌ |
| （空） | `HK:00700` | ❌ |

`港股 00700` 判不命中是**有意的**：加中文市场别名表就是把「精确」重新变成「模糊」，
而 `applicability` 的写方是我们自己（复核工作流）与真人（成长页），都该写规范化形态。
**宁可保守（漏拦），不做模糊匹配** —— 误拦会让系统在本该下单时不下单，且没人看得出原因。

拦单还要 `kind='verified'` **且** `status='已确认'`：

| 条目 | `is_blocking` |
|---|---|
| `verified` + 已确认 + 命中 | **True** |
| `verified` + 已确认 + 别的市场 | False |
| `verified` + 已确认 + 裸代码 | False |
| `hypothesis` + 命中 | False |
| `verified` + 待验证 + 命中 | False |
