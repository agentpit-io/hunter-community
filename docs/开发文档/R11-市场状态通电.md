### 1.1 基准映射（`klines_etl.BENCHMARKS`）

```python
BENCHMARKS = {
    "cn": ("000300", "sh000300"),   # 沪深300
    "hk": ("HSI",    "hkHSI"),      # 恒生指数
    "us": (".INX",   "us.INX"),     # 标普500（带点前缀）
}
```

左列是**落库代码**（写进 `klines.code`），与 `regime.RULES["regime-v1"]["benchmarks"]`
（`CN_A→000300` / `HK→HSI` / `US→.INX`）**逐字一致**；右列是腾讯代码。

> ⚠ **不许靠 `_tencent_symbol` 前缀猜**（实测反证见 §四.6）：`(code, market)` 那套是给
> **股票**用的 —— `.split(".")[0]` 把 `.INX` 截成空串（拼出 `us`，代码整个丢了）、
> 港股按股票补零把 `HSI` 拼成 `hk00HSI`。而实测 `usINX` 只返回 1 根、**必须 `us.INX`**。

### 1.2 `regime.observe()` 换数据源

```python
cur.execute(
    "SELECT ts, close FROM klines "
    "WHERE code = %s AND period = 'daily' AND close IS NOT NULL "
    "ORDER BY ts ASC",
    (_benchmark_code(mkt, rule_version),),
)
```

返回 `{"code", "closes", "dates"}`（不再有 `source_snapshot_id` 键）→ `detect_for_market`
取到 `None` → `detect()` 走**已有的确定性回退** `SNAP-BENCH-<market>-<code>-<最后一根日期>`。

**`RULES` / `classify()` / `detect()` / `_source_snapshot_id()` / `is_available()` 与四元组形状
一个字节都没动**（§四.4 有逐段哈希比对）。

### 1.3 `run_market()` 里的位置（本阶段最容易踩的一条）

`run_market()` 原来在 `stock_universe` 为空时**提前返回**（演示站 / 新库的池子常常是空的）。
基准取数放在**这个检查之前**，且**失败不抛**（`try/except` 只记进返回体的 `benchmark` 字段），
否则空池的部署永远取不到基准、或者基准一次超时就把整个股票池那一轮带崩。

## 二、偏离方案的决策与原因

| # | 事 | 决定 | 原因 |
|---|---|---|---|
| 1 | **数据放哪** | 复用 `klines`（`period='daily'`），不新建表 | 任务书指定；且 `klines` **本来就有指数约定** —— `index_kline.py` 落 `000300`、`us_kline.py` 落 `.INX`，`factor_engine.beta_60` / 回测基准都按这两个代码读（§三） |
| 2 | **解析代码放哪** | 抽 `_fetch_tencent_bars(sym)`，`fetch_tencent` 与 `run_benchmark` 共用 | 模块头坑 1（`[date, open, close, high, low, volume]`，close 在 high 前）**只解一处**；各写一份 = 迟早有一处把收盘当最高 |
| 3 | **`run_benchmark` 入参用哪套市场键** | 用 ETL 通道键（`cn/hk/us`），不用 regime 的规范名（`CN_A/HK/US`） | 它由 `run_market(market=cn/hk/us)` 调；规范名那侧的映射在 `regime.observe()`，两处各管一段，用 `BENCHMARKS` 的**落库代码**对齐 |
| 4 | **基准取数失败怎么办** | 不抛，记 `{"error": …}` 进返回体 | 基准是「锦上添花」，取不到应继续 `unknown`（fail-closed），**不该挡股票池那一轮** |
| 5 | **`observe()` 只取 `close`** | 不取 volume / high / low | `classify()` 只用收盘序列；取不需要的列 = 多一处可能出错的来源 |
| 6 | **来源身份用确定性回退** | `SNAP-BENCH-…`（本部署没有 `SNAP-` 快照行） | 任务书 §二.3 指定；四元组形状不变，`source_snapshot_id` 仍有审计含义 |
| 7 | **不回填 `fin_snapshot`** | `fin_snapshot` 语义一行不动 | 它是「持仓 / 成交标的的行情快照」，不是基准存储；往里塞指数会把两种语义搅在一起 |

## 三、为什么落 `klines` 是安全的（改动影响面核查）

`klines` 是量化侧（因子 / 回测 / 日历）的数据源，加代码有污染风险，逐条核过：

1. **`000300` / `.INX` 本就是量化侧的指数代码**。`index_kline.py`（沪深300 等）与
   `us_kline.py`（`code='.INX'`）**已经在往 `klines` 写这两个代码**；
   `factor_engine` 的 `beta_60` 直接依赖 `code='000300'`，回测 A 股基准 = `000300`、美股 = `.INX`。
   → 本轮只是让**同一个代码有更全的数据**，没引入新约定。
2. **`HSI` 是唯一的新代码**。量化侧的港股基准在 `rs_daily`（`market='hk'`），**不在 `klines`**。
   核查了所有 `FROM klines` 的查询：
   - 股票池枚举走 `data_coverage`（`universe.covered_codes`），不读 `klines` → `HSI` 进不了股票池；
   - 美股日历用 `code = '.INX'`（不是 `SQL_IS_US`）→ `HSI` 不影响；
   - A 股日历用 `SQL_IS_A`（纯数字）→ `HSI` 不匹配；
   - 唯一「字母代码」过滤 `SQL_IS_US` 的两处（`data_center` / `universe`）都打在 `data_coverage` 上。
   → `HSI` 不会被当成美股股票。
3. **本机部署库 `hunter` 灌数前 `klines` 是空的**（0 行）。本轮的 2400 行就是这三个基准，
   不覆盖、不影响任何既有行。

> ⚠ 遗留（非本轮职责）：`quant/market.py:is_benchmark()` 的白名单目前只含 `.INX`，
> `000300` / `HSI` 不在里面。它们靠「不在 `data_coverage`」而天然不进股票池，
> 但**语义上不完整**。真要动量化侧白名单属于另一件事，本轮没碰（`R12/R13` 若要复用
> 基准代码需先看这条）。

## 六、遗留问题与下一阶段（`R12`）交接

1. **演示站 / 线上要等下一次 `api` 镜像重建才生效。** 本轮**不部署**（任务书 §六）。
   线上 `api` 容器跑的是预构建镜像，`/internal/etl/run-market → klines_etl.run_market`
   走的是**镜像里的**代码 —— 所以**每晚定时任务在旧镜像上仍只取股票、不取基准**。
   本轮的 `hunter` 库是用宿主机直接调 `run_benchmark` 灌的（走 ETL 函数，非手写 SQL）。
   → `R13` 出口发版后，三个 `fin-etl-*` Schedule 那一轮会**自动**开始带基准。
2. **`unknown` 的语义没变**：取不到 / 窗口不足 / 查库异常 → 仍 `unknown` → 仍停止提案。
   本轮只是让 `unknown` **不再恒真**（有数据时能判出来）。
3. **`is_benchmark()` 白名单只有 `.INX`**（§三 遗留）—— `000300` / `HSI` 靠「不在
   `data_coverage`」不进股票池。`R12/R13` 若要在量化侧复用这三个基准代码，先补这条。
4. **`regime` 复评路径已自动受益**：`review.propose` 会 `detect_for_market(market, conn)`，
   基准落库后**它产出的 `regime_tags` 会从 `unknown` 变成明确值**（`R3` 那条链路不用改一行）。
5. **`R12`（两条臂可比）不受影响** —— 它动的是 `fin-worker` 的策略 / 影子臂读参数，
   与 regime 数据源无交集。
6. **灌数范围**：本机 `hunter` 库；`r10_test` **没灌**（它是测试库，不能被塞业务数据）。
