### ✅ 3. 自动交易页总开关**真能停**

判据是 `fin_order` 计数（每次都先读开关当前值，再触发同一个 `09:30` decide 时点）：

| 步骤 | prj_m6demo 的委托数 |
|---|---|
| 开关 **ON** → 触发 `fin-0930-2026-10-15` | `10` → **`11`**（+1） |
| 开关 **OFF** → 触发 `fin-0930-2026-10-16` | `11` → **`11`**（不变） |

`fin_job` 里的检查点是直接证据（停下来的那一轮**不是失败**，是「本时点未交易」）：

```
   交易日    | 已停 |               result_ref
-------------+------+-----------------------------------------
 2026-10-15  |      | point:0930:2026-10-15:prj_m6demo
 2026-10-16  | true | point:0930:2026-10-16:prj_m6demo:halted
```

**停的是「产生委托」这件事本身**，不是在接口层把单拒掉 —— 后者会在 `fin_order` 里留下
一行被拒委托，用户看到的是「它还在动」。判定点放在**出意图之前**（`build_decision`），
因为出意图与提交是两个 Activity，隔着重试；放在提交侧，重试时读到的可能是已经恢复的开关。

### ✅ 4. 风险档位改动进了 `fin_param_change_log`

收紧（稳健值 → 保守，**不需要二次确认**）：

```
POST /auto-trade/risk {"tier":"conservative"}
→ {"risk_tier":"conservative","label":"保守",
   "applied":{"max_position_pct":0.1,"daily_loss_halt_pct":-0.02,"account_drawdown_halt_pct":-0.05},
   "changes":[单票0.15→0.10 收紧, 日亏损-0.03→-0.02 收紧, 回撤-0.06→-0.05 收紧], "tightens":true}
```

放宽（保守 → 激进，**409 拦下**，返回放宽了哪几条）：

```
POST /auto-trade/risk {"tier":"aggressive"}   → HTTP 409
{"message":"这次调整会放宽风控上限，需要二次确认",
 "loosened":[单票0.10→0.35, 日亏损-0.02→-0.05, 回撤-0.05→-0.15], ...}

POST /auto-trade/risk {"tier":"aggressive","confirm":true} → 200
```

那几行日志（`fin_param_change_log`，只追加、不可修改）：

```
 id |                field      |   old_value    |   new_value
 66 | risk_tier                 | null           | "conservative"
 65 | account_drawdown_halt_pct | -0.06          | -0.05
 64 | daily_loss_halt_pct       | -0.03          | -0.02
 67 | max_position_pct          | 0.1            | 0.35
 70 | risk_tier                 | "conservative" | "aggressive"
```

> **方向判据是逐字段的，不是档位序号**：单票占比「变小 = 收紧」，两条熔断线是负数、
> 「越接近 0 = 越早停 = 收紧」，方向正好相反。写成同一套会让每次收紧都要求二次确认、
> 而真的放宽畅通无阻 —— 正好反了。`tests/test_fin_risk.py` 有反证用例。

## 四、偏离方案的决策与原因

| # | 偏离 | 原因 |
|---|---|---|
| 1 | **风险档位的「收紧 / 放宽」按字段比，不按档位序号** | 项目模板（`tiers.py`）的三档值与风险档位预设不是同一套数，只看序号会出现「序号在收紧、实际却把某条刹车松了」。 |
| 2 | **总开关的判定点在 fin-worker 的 `build_decision`，不是「提交前再查一次」** | 出意图与提交是两个 Activity，中间可能隔着重试；放在提交侧，重试时读到的可能是已恢复的开关。 |
| 3 | **「我还能怎么控制」只画真的能生效的那一招** | 一期只有总开关这一个控制手段。原型页的「只卖不买」「一键模拟清仓」需要在 paper 里加清仓通道（那是二期的人工委托），页面上**不画灰色按钮**，只写明排在二期。 |
| 4 | **`fin_param` 加两列（`auto_enabled` / `risk_tier`），不新建表** | 开关与档位是「开户那套参数」的一部分；新建表就多一个权威。DDL 随代码走（`control.py` 幂等补列）+ 迁移文件留档，两处一致。 |
| 5 | **时刻表在 api 侧留了一份展示副本** | 权威在 `fin-worker/app/points.py`（真正跑它的是那边的 Temporal Schedule）。api 不该依赖 fin-worker 的 HTTP 才能渲染一个静态清单，所以留副本 + **测试逐条比对源码**（`test_fin_schedule.py`）。 |
| 6 | **验收环境用夹具账本（`prj_m6demo`）** | 与 M4 的 `prj_m4test`、M5 的 `prj_m5demo` 同性质，不是产品功能。**每个数字都是账本算出来的**，夹具只负责把账本摆成「发生过这些事」的样子；快照的 `source` 写 `seed-m6`，页面如实显示。 |
| 7 | **`GET /v1/fin/reports` 而不是 `/v1/fin/reports/latest`** | `fin_report.py` 已注册 `/v1/fin/reports/{report_id}`，先注册的会把 `latest` 当成 report_id 吃掉。 |

## 六、本轮发现并修掉的缺陷

1. **M5 遗留：报告里三项资金事实恒为 `—`**。`report.collect()` 的 SELECT 只取了
   `as_of/nav/total_assets/quality/missing_flag`，而 `build_facts` 还要读
   `cash_available` / `cash_frozen` / `market_value` —— 于是报告页的
   「可用资金 / 冻结资金 / 持仓市值」三项**永远是 `—`**，不报错、不告警。
   报告页与总览页同屏对照时一眼可见。已补上三列并**重跑两份报告**：
   现在事实行里的数字与总览页逐位一致（`420393.51 / 18600.0 / 575020.0 / 1014013.51`）。

2. **`finFetch` 丢掉对象型 `detail`**：风险档位放宽的 409 带着「放宽了哪几条」，
   原来的错误封装只留一句 message，二次确认框就没有内容可显示。已把 `detail` 原样挂在 error 上。

3. **`fin_job` 的列名是 `type` 不是 `job_type`**：读接口写错列名 → 500（真跑才撞到，单测不连库）。

## 七、遗留问题（交给 M7 / M8）
