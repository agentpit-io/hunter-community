## 一、做了什么

### 1. 迁移 `db/migrations/0023_fin_core.sql`（439 行）

- 建 **25 张 `fin_*` 表**：`09 §三` 一期清单 20 张 + `§4.9` 人机协作 5 张空表（一期只建不写）。
- 建运行期角色 `fin_paper_rw`（`DO` 块判存在，幂等），逐表 `GRANT`，**任何角色都不给 DELETE**。
- 部分唯一索引 `fin_project_one_active (user_id) WHERE status='active'` —— 「一个账户同时只有一个进行中项目」由**库层**保证。
- 严格照抄 `09 §四` 的命名与类型：金额 `NUMERIC(18,4)`、价格 `NUMERIC(12,4)`、比例 `NUMERIC(9,6)`、时间 `TIMESTAMPTZ`；**全表零 `float`/`double`/`REAL`**。
- 幂等：一律 `IF NOT EXISTS`；不 DROP、不改列类型、不重命名。
- 只放 `db/migrations/`，由 `app.migrate` 在 api 启动时执行，不挂 initdb、不手工跑。

## 二、偏离方案的决策与原因

> 依据 `总控规则.md` §一：「与实测冲突时**以实测为准**，在成果文档写明偏离与原因。」

### 偏离 1 · 账本表建在应用库（`fin_` 前缀），不建独立库 `hunter_fin`

`09 §一` / `§七` 要求迁移用管理员连接执行 `CREATE DATABASE hunter_fin`。**实测做不到**，三条：

1. `app.migrate.apply_one()` 把**整个 .sql 文件当一条语句**在一次事务里执行（`cur.execute(sql_text)` 后 `commit`）。
   PostgreSQL **禁止在事务块里 `CREATE DATABASE`**；psycopg2 也没有 psql 的 `\gexec`。
2. 任务书要求「迁移只放 `db/migrations/`，不过 initdb 挂载，不手工跑」——在 app.migrate 这套 runner 下，独立库**没有可执行的落点**。
3. M1 的开户接口经 `DATABASE_URL` 连应用库（本轮不接 `paper`），表必须同库才可读写。

`09 §十` 待拍板 #5 本来就写着「`hunter_fin` 独立库 vs 同库 schema」**未决**，取「同库」分支。
**「谁能写账本必须是一条 GRANT」的设计意图保留**：运行期角色 `fin_paper_rw` 与逐表 GRANT 照 `§一` 建，只是授权对象是应用库里的 `fin_*` 表。

> ⚠️ **这一条要在 M8 前重新确认**：同库下 `hunter`（应用角色，表 owner）仍可写账本，「只有 `fin_paper_rw` 能写」目前不是强约束。真正的隔离要么等 `paper` 容器（M4/M8）上线时把表 owner 迁给 `fin_paper_rw`，要么届时改 `app.migrate` 支持事务外的建档语句。已列入遗留问题。

### 偏离 2 · `fin_project.user_id` / `fin_account.user_id` 用 `TEXT`，不用 `INTEGER`

`09 §四` 写成 `INTEGER`，注释假设关联整数型 `hunter.users(id)`。**实测不成立**：
本仓 `users.id` 是 **`UUID`**（`db/migrations/0001_local_users.sql:7`），鉴权中间件经 JWT 传下来的 `request.state.user_id` 是字符串。
往 `INTEGER` 里放 UUID 只能靠「编一个映射」，违反红线 1（不许编）。故取 `TEXT` 原样存 UUID 字符串 —— 与现仓同类表 `screen_quota_usage.user_id TEXT`（0021）同口径。

### 偏离 3 · 表数 25 张，不是 `09 §零` 写的 19 张

`09` 内部不自洽：`§零` 说「一期 19 张」，`§三` 清单枚举出 20 张，`§四` 给了 20 张 DDL + `§4.9` 5 张。
任务书明确要求「`§三` 清单 + `§4.9` 的 5 张空表」。**以 `§三`/`§四` 为准**：20 + 5 = **25 张**。

### 偏离 4 · 前端技术栈按仓库实测，不用 shadcn/ui 与 TanStack Query

任务书写「Next.js + React + Tailwind + shadcn/ui + TanStack Query」。**实测本仓 `apps/web/package.json` 里没有这两项**：
实际栈是 Next 15 + React 19 + Tailwind v4 + lucide-react。按仓库现状做，不引入新依赖（`_ui.tsx` 顶部写明）。

### 偏离 5 · 前端构建用 `npm`，不是 `pnpm`

任务书给的是 `pnpm build`，但本仓**跟踪的是 `apps/web/package-lock.json`（npm）**，CI（`.github/workflows/ci.yml:305-317`）也是 `npm ci` + node 22。
故按仓库口径用 `npm ci` + `next build`。另：本机只有 node **v20.20.2**（仓要求 `>=22.12.0`），实测 Next 15.5 在 node 20 上构建通过。

### 未偏离但需记录 · 一次性「编造」检查

占位页与向导里**没有一个假数字**：四个正文页只写「本页尚未交付 + 交付里程碑」，向导的档位数字全部来自 `GET /api/v1/fin/tiers` 的真实返回。
符合 `CLAUDE.md` 开头铁律与 `总控规则` §六-10。

## 四、遗留问题（按优先级）

1. **【高】账本写权限隔离未真正成立**（偏离 1）。同库下应用角色是表 owner，仍可写 `fin_*`。M4/M8 上 `paper` 容器时，需把表 owner 迁给 `fin_paper_rw`，或改 `app.migrate` 支持事务外执行建档语句。**在 M8 前必须解决，否则红线 7「实盘隔离」的账本侧是纸面的。**
2. **【高】`09 §四` 的 `user_id INTEGER` 与实际 UUID 不符**（偏离 2）。已用 `TEXT` 绕开，但**设计文档应同步修订**，否则后续表（二期 `fin_segment` / `fin_experience`）会继续照抄错的类型。
3. **【中】真浏览器端到端未做**（3.4）。菜单可点、六步可走完、开户成功卡，只有接口与 SSR 证据。
4. **【中】窄屏与客户端 JS 报错未实测**。
5. **【中】`m1-fin-pg`（5599）与 `m1-pytest` 是本轮起的临时设施**，不在 compose 里。`m1-pytest` 已可删；`m1-fin-pg` 建议留到 M2（省得再起一次库）。
6. **【低】`fin_param.params_locked_at` 一期恒 NULL**（一期没有成交，「首次成交时刻」未发生）。M2 首笔成交时要补上。
7. **【低】`fin_account.locked_at` 开户即写 `now()`**，而 `09 §四` 注释写「开启即锁；档位制下恒为真」—— 语义一致，但 `params_locked_at` 与它不同步，二期要理清「哪个才是锁定锚点」。
