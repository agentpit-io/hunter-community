### 1.1 唯一写入口 `propose()`：三件事同一事务

提案落库时**同时**写 `fin_evolution_plan`（算出 `plan_hash` 存下）与第一条
`fin_evolution_event(kind='created')`。**缺一即整体回滚**（验收 §⑪）。

### 1.2 四条护栏（`plan/R6.md` §一.3）

| 护栏 | 口径 | 越界 |
|---|---|---|
| **白名单** | 只许改白名单参数（类型 / 范围 / 单次最大变化 / 基线版本，见 §三） | 400 + `rejected_by_gate` |
| **证据** | `evidence_refs` ≥1 条 · 同项目 · 同时间边界 · 非 holdout · 来自**冻结快照**；`refute` 同样可引用 | 400 + `rejected_by_gate` |
| **`param_diff`** | **服务端机器算**，比对写入方传进来的 diff | 不一致 → 400 + `rejected_by_gate` |
| **方向（红线 8）** | `risk` 走 `risk.compare()`；`strategy` 走白名单方向语义。**AI 无权放宽风控** | 放宽 → **400 + 不入库** + `rejected_by_gate` |

### 1.3 证据经 `memory.get_snapshot()`（不碰经验表）

经验的唯一读入口是 `services/fin/memory.py`（红线 2）。`evolution.py` **不碰经验三表**
（`test_fin_memory_guard.py` 盯着），而是调 `memory.get_snapshot(id)` 拿那份**冻结集合** ——
「拿的是哪一批经验」由快照固定，不是「此刻查得到的那批」（防未来函数）。

## 二、偏离方案的决策与原因

| # | 事 | 决定 | 原因 |
|---|---|---|---|
| 1 | **`fin_evolution_event.proposal_id` 不加外键** | **不加**（`01 §8.2` 草案写的是 FK，这里**有意偏离**） | 红线 8 / 白名单越界 / 证据不合规**都要**记 `rejected_by_gate` 事件，而这些提案**从不入库**。加了 FK，拒绝事件一条都写不进来 —— 审计反而瞎了。审计日志必须能记「从未存在的提案」。已写进 `0043` 表四注释与 `tests` |
| 2 | **`target` / `direction` / 两个 hash 全部服务端算** | 请求体里**根本没有**这些字段 | 「不采信写入方」。`direction` 由 `risk.compare()`（risk）或白名单方向语义（strategy）判；两个配置哈希由服务端读 `fin_param` 后计算。**不实现放开参数，就不可能被误开** |
| 3 | **候选配置必须是「完整配置」** | `set(candidate) == set(base)`，多一个少一个都拒 | 只存 diff 脱离 base 无意义；`candidate_config_hash` 要能代表「**完整**候选配置」。少了字段 = 静默删除，多了 = 新参数，两者都不是「改参数值」。这条让 `param_diff` 篡改（谎报 old）当场露馅 |
| 4 | **一次提案只改一类（risk 或 strategy）** | 混类拒绝 | `target` 是单值列；混类会让「这条提案是收紧还是放宽」说不清。拆成两条提案是更清晰的做法 |
| 5 | **regime 依据从「证据 + 请求声明的 tags」来，不现调判定器** | `propose` 收 `regime_tags`，与证据的 `regime_tags` 一起过混组规则 | `R5` 的判定器在本部署**没有基准行情源**（`observe()` 默认 `None` → 恒 `unknown`）。若提案入口现调判定器，**所有提案都会被「无可靠数据源」挡死**。做法改为：标签必须**明确且可用**（`regime.is_available`），证据的明确 regime 必须落在提案声明范围内；`unknown` 与明确 regime 不得混组。真接了基准行情后，`regime_tags` 由工作流填判定器输出即可，**本模块不用改** |
| 6 | **`plan` 默认值留 `pass_line` / `fail_line` 为非空占位** | `DEFAULT_PLAN` 给 +0.01 / −0.01，并注明是**实现时默认值** | 红线 13：「把默认值、计算依据、验证样本公开在配置文档」。见 §四 |
| 7 | **`plan_overrides` 只许覆盖 `DEFAULT_PLAN` 已有键** | 允许（**本轮默认不覆盖**） | 不同市场可能要给不同的窗口；同时它也是验收 §⑪ 的现场（注入 `metric=None` 触发计划写入失败，证明三件事同事务）。未来若不需要，删掉这个参数即可，不影响任何已落库数据 |

## 三、白名单参数表（`proposal_algo_version = "evolution-algo-v1"`）

**改成带版本号的表**（`evolution.ALGO_VERSION` 指回来）；**改白名单任何一项 = 换版本键**
（旧提案指着老版本，永不被新口径重新解释）。`public_whitelist()` 是它的可序列化视图。

每个参数带：**类型** · **取值范围** · **单次最大变化** · **基线版本** · **方向语义**（strategy 用）。

### 3.1 `target='risk'`（三个风控字段，**方向由 `risk.compare()` 判**）

| 字段 | 类型 | 范围 | 单次最大变化 | 方向语义 | 基线版本 |
|---|---|---|---|---|---|
| `max_position_pct` | ratio | [0, 1] | 0.10 | 越小越紧 | `risk-fields-v1` |
| `daily_loss_halt_pct` | ratio | [-0.5, 0] | 0.05 | 越接近 0 越紧（**负数是更紧**） | `risk-fields-v1` |
| `account_drawdown_halt_pct` | ratio | [-1, 0] | 0.10 | 越接近 0 越紧 | `risk-fields-v1` |

> ⚠️ 两条熔断线是**负数**，方向与单票占比**相反** —— 与 `risk.py:_TIGHTER_WHEN_SMALLER` 同源。
> `direction` 由 `risk.compare()` 判（不采信白名单里的 `tighter_when`，那只是文档）。

### 3.2 `target='strategy'`（**方向由白名单每参数自带语义判**）

| 字段 | 类型 | 范围 | 单次最大变化 | 方向语义 | 基线版本 |
|---|---|---|---|---|---|
| `stop_loss_pct` | ratio | [0.005, 0.5] | 0.05 | 越小越紧（越早离场） | `strategy-fields-v1` |
| `take_profit_pct` | ratio | [0.005, 5] | 0.5 | 越小越保守（越早落袋） | `strategy-fields-v1` |
| `hold_days_max` | int | [1, 60] | 5 | 越小越保守（持有越短） | `strategy-fields-v1` |
| `vol_mult` | ratio | [0.1, 10] | 1.0 | 越大越紧（入场越严） | `strategy-fields-v1` |
| `confirm_days` | int | [0, 10] | 2 | 越大越紧（确认越多） | `strategy-fields-v1` |

策略参数的两类键：`stop_loss_pct` / `take_profit_pct` / `hold_days_max` 是 `fin_param` 顶层列；
`vol_mult` / `confirm_days` 出现在 `strategies[].params`，外层键形如
`strategies.<key>.params.<name>`（`whitelist_for` 取最后一段当参数名）。

**为什么不借用 `risk.compare()` 判策略方向**：它只认识自己的三个风险字段
（`_TIGHTER_WHEN_SMALLER`），拿它判 `vol_mult` 会得出「没有变化」或方向反了的结论 ——
所以策略方向由白名单里**每个参数自带的 `tighter_when`** 决定。

## 四、`plan` 默认值与计算依据（红线 13）

`evolution.DEFAULT_PLAN`：

| 字段 | 默认值 | 依据（**实现时默认值，非既成阈值**） |
|---|---|---|
| `metric` | `portfolio_net_return` | `03 §4-C`：优先用**同资本基准的组合净收益**，不是单笔 `realized_net_pnl`（持仓周期 / 频率会让它失真） |
| `window_days` | 20 | 一个交易月；`R7` 会拿真实影子数据校准 |
| `min_comparable_sample` | 20 | 最小**可比样本**（红线 11：两臂均有可比机会的交易日 / 事件计） |
| `cost_model` / `slippage_model` | `fee-model-v1` / `slippage-v1` | 版本键，`R7` 落实体 |
| `data_source_version` | `data-v1` | 数据源版本键 |
| `pass_line` / `fail_line` | +0.01 / −0.01 | 通过 / 失败线；`R7` 校准前是占位 |
| `early_stop_condition` | `{max_drawdown_pct: -0.08}` | 提前停止条件 |
| `rollback_line` | `{max_drawdown_pct: -0.10}` | **预注册**的观察期回滚线（与 plan 同时冻结） |

**本轮只保证它们能被写、不能被改**（触发器 + `plan_hash`）。`R7` 之前的样本不足一律 `inconclusive`。

## 五、`0043_evolution_loop.sql` 全文

```sql
-- ════════════════════════════════════════════════════════════════════════
-- 0043_evolution_loop.sql · 智能炒股 · 受控自进化 · 提案层（第四段 R6）
--   四张表：提案 / 冻结计划（不可变）/ 影子事件（追加）/ 状态事件（追加 · 审计权威）
--
-- 依据：`plan/R6.md` §一 · `plan/记忆系统追加规则.md` §四 / §五 第 7-10、13 条 ·
--       `00记忆新方案/03…代码修改方案.md` §4-B ·
--       `00记忆新方案/01…调整建议.md` §八 8.2（DDL 草案，**按 `03` 的六条修订落**）。
--
-- 执行：`app.migrate` 在 api 每次启动时按文件名顺序执行（`boot.sh` → `python -m app.migrate`）。
--
-- ⚠️ 三个"只做加法"的纪律（`记忆系统追加规则.md` §四）：
--     `CREATE TABLE IF NOT EXISTS` / `CREATE INDEX IF NOT EXISTS` / `DROP … IF EXISTS` 再建；
--     **不带 `BEGIN;` / `COMMIT;`** —— `app/migrate.py:apply_one` 已把每个文件包在独立事务里。
--     可重复执行、不改历史行。
--
-- ── 与 `01 §8.2` 草案的三处**有意修订**（`03 §7` 的六条里第 3、4 条）────────────
--   1. 不可变 `fin_evolution_plan` + 追加式 `fin_evolution_event`；`proposal.status` 只是投影。
--   2. 改用**数据库触发器**拒改 + 事件表**哈希链**兜底审计；不宣称对机器所有者"绝对不可篡改"。
--   3. `aggregate_basis` / `base_strategy_key` 按 `03` 的修订替换为
--      `evidence_snapshot_id` + `base_config_hash` / `candidate_config_hash`。
-- ════════════════════════════════════════════════════════════════════════

CREATE TABLE IF NOT EXISTS fin_evolution_proposal (
  proposal_id            TEXT PRIMARY KEY,                    -- evp_<24hex>
  project_id             TEXT NOT NULL REFERENCES fin_project(project_id),
  evidence_refs          TEXT[] NOT NULL,
  evidence_snapshot_id   TEXT,
  base_config_hash       TEXT NOT NULL,
  candidate_config_hash  TEXT NOT NULL,
  param_diff             JSONB NOT NULL,
  regime_tags            TEXT[] NOT NULL DEFAULT '{}',
  rule_version           TEXT,
  proposal_algo_version  TEXT NOT NULL,
  target                 TEXT NOT NULL CHECK (target IN ('strategy','risk')),
  direction              TEXT NOT NULL CHECK (direction IN ('tighten','loosen','mixed')),
  status                 TEXT NOT NULL DEFAULT 'draft',
  rationale              TEXT NOT NULL,
  created_by             TEXT NOT NULL,
  created_at             TIMESTAMPTZ NOT NULL DEFAULT now(),
  CHECK (status IN ('draft','validating','passed','rejected','applied','rolled_back','inconclusive')),
  CHECK (cardinality(evidence_refs) >= 1),
  CONSTRAINT fin_evo_risk_never_loosen CHECK (target <> 'risk' OR direction <> 'loosen')
);
CREATE INDEX IF NOT EXISTS fin_evolution_proposal_by_project
  ON fin_evolution_proposal (project_id, created_at DESC);
CREATE UNIQUE INDEX IF NOT EXISTS fin_evolution_proposal_one_pending
  ON fin_evolution_proposal (project_id, base_config_hash)
  WHERE status IN ('draft','validating');

CREATE TABLE IF NOT EXISTS fin_evolution_plan (
  plan_id                TEXT PRIMARY KEY,                    -- evpl_<24hex>
  proposal_id            TEXT NOT NULL REFERENCES fin_evolution_proposal(proposal_id),
  metric                 TEXT NOT NULL,
  window_days            INTEGER NOT NULL,
  min_comparable_sample  INTEGER NOT NULL,
  cost_model             TEXT NOT NULL,
  slippage_model         TEXT NOT NULL,
  data_source_version    TEXT NOT NULL,
  pass_line              NUMERIC(18,8),
  fail_line              NUMERIC(18,8),
  early_stop_condition   JSONB,
  rollback_line          JSONB,
  plan_hash              TEXT NOT NULL,
  frozen_at              TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE UNIQUE INDEX IF NOT EXISTS fin_evolution_plan_by_proposal
  ON fin_evolution_plan (proposal_id);

CREATE TABLE IF NOT EXISTS fin_evolution_shadow_event (
  shadow_event_id  TEXT PRIMARY KEY,                          -- evsh_<24hex>
  validation_id    TEXT NOT NULL,
  arm              TEXT NOT NULL CHECK (arm IN ('incumbent','candidate')),
  trade_date       DATE NOT NULL,
  point            TEXT NOT NULL,
  symbol           TEXT NOT NULL,
  quote_as_of      TIMESTAMPTZ,
  signal           TEXT,
  filled           BOOLEAN,
  reject_reason    TEXT,
  fee              NUMERIC(18,8),
  slippage         NUMERIC(18,8),
  position_ref     TEXT,
  valuation_ref    TEXT,
  created_at       TIMESTAMPTZ NOT NULL DEFAULT now(),
  UNIQUE (validation_id, arm, trade_date, point, symbol)
);

CREATE TABLE IF NOT EXISTS fin_evolution_event (
  event_id     TEXT PRIMARY KEY,                              -- eve_<24hex>
  proposal_id  TEXT NOT NULL,                                 -- 无外键（见文件内注释）
  kind         TEXT NOT NULL CHECK (kind IN (
                 'created','validating','passed','rejected','applied',
                 'rolled_back','inconclusive','rejected_by_gate')),
  payload      JSONB NOT NULL DEFAULT '{}'::jsonb,
  prev_hash    TEXT NOT NULL,
  event_hash   TEXT NOT NULL,
  actor        TEXT NOT NULL,
  created_at   TIMESTAMPTZ NOT NULL DEFAULT now()
);
CREATE INDEX IF NOT EXISTS fin_evolution_event_by_proposal
  ON fin_evolution_event (proposal_id, created_at, event_id);

CREATE OR REPLACE FUNCTION fin_evolution_immutable()
RETURNS trigger
LANGUAGE plpgsql
AS $fn$
BEGIN
  RAISE EXCEPTION
    '% 是追加 / 不可变表：禁止 %（plan 写入即冻结、事件表是审计权威；改口径 = 新建提案）',
    TG_TABLE_NAME, TG_OP
    USING ERRCODE = 'restrict_violation';
END;
$fn$;

DROP TRIGGER IF EXISTS fin_evolution_plan_immutable ON fin_evolution_plan;
CREATE TRIGGER fin_evolution_plan_immutable
  BEFORE UPDATE OR DELETE ON fin_evolution_plan
  FOR EACH ROW EXECUTE FUNCTION fin_evolution_immutable();

DROP TRIGGER IF EXISTS fin_evolution_event_immutable ON fin_evolution_event;
CREATE TRIGGER fin_evolution_event_immutable
  BEFORE UPDATE OR DELETE ON fin_evolution_event
  FOR EACH ROW EXECUTE FUNCTION fin_evolution_immutable();
```

### 6.2 不可变触发器（plan/event × UPDATE/DELETE 全被拒）+ proposal.status 可更新

```
[plan UPDATE]  被拒 → fin_evolution_plan 是追加 / 不可变表：禁止 UPDATE（plan 写入即冻结、事件表是审计权威；改口径 = 新建提案）
[plan DELETE]  被拒 → fin_evolution_plan 是追加 / 不可变表：禁止 DELETE（…）
[event UPDATE] 被拒 → fin_evolution_event 是追加 / 不可变表：禁止 UPDATE（…）
[event DELETE] 被拒 → fin_evolution_event 是追加 / 不可变表：禁止 DELETE（…）
[proposal.status UPDATE] 成功（投影允许更新）
  → status = validating
```

### 6.3 投影一致性校验（不一致行数 = 0）

```
projection_mismatches() = []
```

对应的 SQL（`evolution.projection_mismatches`）：按每个提案取**最后一条事件**的 kind 映射成
状态，与 `proposal.status` 比；不一致的行应是 0。

### 6.4 哈希链（三事件接得上 + 篡改后校验失败）

```
第一条(created) 由 propose 写入
第二条 event_hash = 70585515f140cb53a5e3283bebee7cc571e2f68c401ec45f6345a3d246da87b4
第三条 prev_hash  = 70585515f140cb53a5e3283bebee7cc571e2f68c401ec45f6345a3d246da87b4
接得上？ True
verify_chain: {'ok': True, 'count': 3}
--- 篡改一条事件的 payload（绕过触发器）---
篡改后 verify_chain: {'ok': False, 'broken': [{'event_id': 'eve_d3391e0e59964c499f82fcf5',
   'why': 'event_hash 与内容不符（内容被改过）'}]}
```

> `event_hash = sha256(prev_hash | proposal_id | kind | payload 规范序 | created_at)`。
> 篡改 payload 用 `ALTER TABLE … DISABLE TRIGGER` **绕过触发器** —— 这正是下一节的边界：
> 触发器挡应用代码（含属主），但 superuser 能关掉它；**关掉之后还有哈希链兜底**。

### 6.5 连接身份实测 + 书面结论

```
{'current_user': 'hunter', 'is_superuser': 'on', 'rolsuper': True}
```

**结论（诚实）：**

- 本仓 api 的连接身份是**库属主 `hunter`（`rolsuper=true`，`is_superuser=on`）**。
  因此 `01 §8.2` 的「零 GRANT 使 plan 不可改」**在本部署不成立** —— 属主的读写能力来自连接身份，
  不是来自 GRANT。这正是 `03 §7.3` 点名的情形。
- **触发器对表属主同样会触发**（PostgreSQL 触发器语义），所以它**真的挡得住应用代码** ——
  §6.2 的四条报错就是以属主身份跑出来的。这一条比"零 GRANT"硬。
- 但**库属主 / superuser 永远能 `ALTER TABLE … DISABLE TRIGGER`**（§6.4 就是这么篡改的）。
  所以**不能宣称「对机器所有者绝对不可篡改」**（`03 §4-B` 原话）。
  绕过触发器改数据这件事，由**事件表哈希链**兜底发现（§6.4：链校验报错）。
- **是否引入「最小权限运行角色」：本轮不做**。理由：(a) 本方案是**单人本地部署**，库属主就是
  机器所有者本人，「防机器所有者」没有对手；(b) 引入非 owner 运行角色要动 `0023` 的
  `fin_paper_rw` 模型与 `DATABASE_URL` 连接配置，是多处可出错点（「不许新增平行权威」同精神）；
  (c) 触发器 + 哈希链已覆盖「应用代码写错 / 被误改」这一真实威胁。
  **后续建议**：真要多用户 / 公网部署时，另起一个**非 owner 的最小权限连接**给 api（迁移账号与
  运行账号分开），那时零 GRANT 才有意义 —— 这是 `R10` 之后的事，写在这里免得下一个人重猜。

## 七、遗留问题与下一阶段（`R7`）交接

1. **`plan` 的阈值是占位**（§四）。`R7` 拿真实影子数据校准后，**改口径 = 新建提案**（旧 plan 不动）。
   `pass_line` / `fail_line` / `window_days` / `min_comparable_sample` 都可能被 `R7` 调。
2. **`fin_evolution_shadow_event` 本轮只建表**。`R7` 写入时的口径（`03 §4-C`）：两臂同行情快照 /
   同初始现金 / 同费率滑点；`validation_id` 由 `R7` 生成（本轮不设外键）；唯一键
   `(validation_id, arm, trade_date, point, symbol)` 保证**重试不重复记账**。
   **`fin_trade` 绝不进这张表**（只记真实 / 现行策略成交）。
3. **`regime_tags` 由 `R7/R8` 的工作流填判定器输出**（`regime.detect_for_market`）。本模块
   已按「必须明确且可用、`unknown` 不与明确 regime 混组」判；判定器真接上基准行情后，本模块不用改。
4. **`proposal.status` 是投影**：`R7/R8` 用 `evolution.append_event(kind=…)` 追加事件——
   它**同时**更新 `status`。**不要直接 `UPDATE … SET status`**（那会让 `projection_mismatches` 非空）。
5. **审计工具就绪**：`evolution.verify_chain(proposal_id)` 与 `evolution.projection_mismatches()`，
   `R7/R8` 的验收可直接复用。
6. **`R8` 的 CAS**：提案记着 `base_config_hash`；生效前用 `control.py` 的唯一入口校验当前
   `fin_param` 的配置哈希是否仍是它（变了说明基线动过，提案过期）。
7. **`FIN_EVOLUTION_MODE=off` 时提案被拒（503）**。本机 / 测试要设 `observe`；
   演示站按 `03 §2` 先 `observe`，验收后再 `paper`。
8. **本机开发库已应用 `0043`**（增量 1 个）。`R6` 未改动开发库任何历史行（迁移只建表）。
