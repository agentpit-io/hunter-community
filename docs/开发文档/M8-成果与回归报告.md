## 四、ST 判定实际走的通道（拍板 §七）

**结论：ST 一律看 `qt.gtimg.cn` 的中文证券简称（字段 `f(1)`），不走 hunter、也不用 `company_master`。**

- hunter 网关的 `quote` 返回 `name` **就是代码本身**（实测 `601398` → `"name":"601398"`），无中文简称、无 ST 标记；
  该网关本次只解锁 `quote` / `kline` / `news`，**没有** instruments / universe 类接口。
- `company_master` 在演示库只有 300 行（沪深 300 种子），拿它判全市场 ST 会**大面积漏判** —— 漏判的后果是把
  一只 ±5% 的 ST 股按 ±10% 撮合。

实现（`apps/api/app/services/fin_data.py` + `routers/fin_data.py`）：

- 新增 `tencent_names(codes)`：一张 URL 批量取（`q=sh600519,sz000001…`，GBK 解码），
  **1 批/秒限速**，见 **501 立即中止整批**（腾讯 WAF 有前科，硬闯会把整机 IP 送进黑名单）。
- `instrument()` 新增 `st_name` / `require_st_name`：**ST 只认 `st_name`**；
  同步路径 `require_st_name=True` 时**判不出 ST 即 `available=false`**（零容忍 → fin-worker 不写
  `fin_instrument` → 风控第 4 条拒绝该标的）。
- `fin_instrument.source` 如实记 `quote_name`（还是 `company_master/stock_universe`）。

### 回归顺带跑出来的**真缺陷**（已修）

hunter 网关 A 股报价的 `ts` **只给到日期**（`"2026-09-30"`），没有盘中时刻。
落到快照上就是当天 `00:00:00`，于是：

1. 风控的**交易时段校验**必然判「不在交易时段内」（实测委托回执原文：
   `不在交易时段内（00:00 上海时间，当日时段 09:30-11:30、13:00-15:00）`）；
2. **新鲜度**必然判 stale（`PAPER_SNAPSHOT_STALE_SECONDS=900`）。

两条叠加 = **委托永远不成交，而且不报错**，看起来像策略没信号。

修法（只补缺口，不换来源）：`_is_date_only()` 识别「零点时刻」，命中就用腾讯通道的 `f(30)`（到秒）
补 `event_time`；`name` 等于代码本身时同样补简称。**价格与 `source` 仍是 hunter**，补了什么写进 `gaps`：

```
gaps: ["event_time: official 只给到日期，盘中时刻取自腾讯通道（2026-09-30T16:14:58+08:00）",
       "name: official 返回的是代码本身，证券简称取自腾讯通道（工商银行）",
       "orderbook: 该来源没有买一/卖一盘口"]
```

**结论：本阶段**没能**把 v1.3.0 部署到演示站 `35.198.212.241`。原因是本机没有到那台机器的 SSH 凭据。**

`08` §6.2 / 任务书 §3 给的命令是：

```bash
ssh -i ~/.ssh/id_rsa_google_longterm support@35.198.212.241 …
```

实测（逐条证据）：

| 检查 | 命令 | 结果 |
|---|---|---|
| 私钥是否存在 | `ls ~/.ssh/id_rsa_google_longterm` | ❌ `No such file or directory` |
| 全盘找私钥 | `find / … -iname '*google_longterm*' -o -iname 'id_rsa*'` | 只找到 `~/.ssh/mixplode_deploy`（github 只读用） |
| 用现有 key 试 `support@` / `root@` / `ubuntu@` 等 7 个用户 | `ssh -i ~/.ssh/mixplode_deploy …` | ❌ 全部 `Permission denied (publickey)`（服务端只接受 publickey） |
| gcloud 备用通道 | `gcloud compute ssh support@35.198.212.241 --zone=asia-southeast1-c` | ❌ `Request had insufficient authentication scopes` |
| 有没有隧道 / docker API | `ss -tnp \| grep 35.198.212.241`；探 2375/2376/5000 | ❌ 无隧道；docker 端口全关 |

演示站**本身是活的**（公网 `http://35.198.212.241:8100/api/health` → 200、web 3100 → 200），
缺的只是**本机到它的 shell 通道**。拍板 §一 也预见到这种情形（「HK 这台没有到演示站的通道时……」），
本轮按红线 1 记「未跑 + 原因」，**不拿本机结果冒充演示站结果**。

**补齐这一步要什么**：把 `id_rsa_google_longterm`（或等价私钥）放到 `~/.ssh/`，
或给本机 GCE 服务账号补 `compute.instances.*` scope。拿到之后照 `08` §6.3 的顺序
（postgres → api 建库建角色跑迁移 → temporal → paper → fin-worker → web）执行即可，本文的回归步骤可原样复跑。

**镜像已经躺在 GHCR 上**（§二），演示站只要 `git pull --ff-only origin main` +
把 `.env` 的 `HUNTER_VERSION` / `FIN_TAG` 改成 `1.3.0` + `docker compose pull && up -d` 就能上线，
不需要在演示站上构建（它的根分区只有约 12 GB 余量）。
