## ⚠ 关键前置踩坑 · Alpine 容器 TLS 指纹被 aihubmix CDN 拦截

**症状**:hunter-community 的 `llm-shim`(Alpine 3.24 + Python 3.12 + OpenSSL 3.5.7)从容器内 `POST https://aihubmix.com/v1/...` 时 · 100% 报:
```
SSLEOFError: [SSL: UNEXPECTED_EOF_WHILE_READING] EOF occurred in violation of protocol (_ssl.c:1010)
```
容器内 curl、python urllib、python httpx、node fetch 全都失败 · **同一台 macOS host 的 curl 却完全 OK**。

**根因**:aihubmix 前置 CDN(IP 段 `104.244.43.136` · Meta AS32934)按 JA3/JA4 TLS 指纹拦截 · Alpine + 系统 OpenSSL 的 ClientHello 被识别为异常来源。测过:
- ✅ macOS host curl / python
- ✅ macOS Python urllib
- ❌ Alpine container curl(`error:0A000126:SSL routines::unexpected eof while reading`)
- ❌ Alpine container python urllib / httpx
- ❌ Alpine container node fetch(`unknown certificate verification error`)

**Workaround**(本次评测采用):macOS host 上跑 [`/tmp/aihubmix-host-proxy.py`](../scripts/aihubmix-host-proxy.py) · 监听 `:3998` · 让容器改走 `http://host.docker.internal:3998/v1`(HTTP 无 TLS 握手)· host 用自身 TLS 栈完成到 aihubmix 的 https 转发。

```
container shim → http://host.docker.internal:3998 → macOS python → https://aihubmix.com
                    (无 TLS · 无拦截)         (host TLS 指纹 · 通过)
```

**长期方案**(未做):
1. 换 `curl-impersonate` 到 shim 容器 · 伪装成 Chrome/Firefox 指纹
2. 换 shim base image 到 debian(非 alpine)· 用 debian OpenSSL(可能通过)
3. 让 aihubmix 加白容器 IP 或换后端 CDN

## 2. 关键发现

### 2.1 满分 2 家 · 主推 Claude Sonnet 5(海外)· Qwen 3.8 Max(国内)

Claude Sonnet 5 在 7/7 全 hit 基础上 · B2 深度分析主动编排 4 个 tool(quickview → 2× deep_analysis → news)· 是唯一展现"agent 级"多轮 tool 编排能力的模型。Qwen 3.8 Max 稍慢但 hit 齐 · 中文场景无违和。

### 2.2 GPT-5.6 sol 的"tool description 匹配偏差"(**已尝试修复 · hit 持平但错法改善**)

**症状(修复前 · 17:01)**: GPT-5.6 sol 在 A3 和 B1 两个 case 都错选了 `hunter_user_list_my_sources` — 一个"列出用户订阅数据源"的读接口。用户可见的表现:"茅台未来走势预测的数据源暂不可用:当前无法获取用户身份..."(错误信息)。

**修复方案 · 20:23**: 改 `hunter_user_mcp.py` 里 `list_my_sources` 描述 · 加详细负向清单:
```
❌ 不要用于以下场景 · 它们已有专用内置 tool(直接调即可):
  · '加自选' → 调 watchlist_watchlist_add
  · '预测走势' → 调 hunter_cap_kpred
  · '当前股价' → 调 watchlist_stock_quickview
  · '深度分析' → 调 uzi_stock_deep_analysis
  · ...(全清单见 dev 分支代码)
```

**修复效果 · 20:41 复测**:
| Case | 修复前 tool | 修复后 tool | 用户体验 |
|---|---|---|---|
| A3 加自选 | `hunter_user_list_my_sources`(报错) | `watchlist_watchlist_add`(50%)或 无 tool(50%)| 有时命中 · 有时说"当前工具暂不支持" · 至少不报错 |
| B1 预测走势 | `hunter_user_list_my_sources`(报错) | `watchlist_stock_quickview`(仍非 kpred) | 拿到股价数据(有用但非预测)· 不再报错 |

**核心结论**:
- ✅ **修复生效**: GPT 100% 不再误入 list_my_sources(2/2 case 都逃离)
- ⚠ **hit 未提升**: 5/7 → 5/7 · GPT 释放的 slot 换到了"次错"tool 而非"正确"tool
- 🔍 **深层原因**: GPT-5.6 sol 对 `hunter_cap_kpred` / `watchlist_watchlist_add` 这类"双前缀 tool 名"的语义匹配天生较弱 · 更偏爱语义"更普通"的 `watchlist_stock_quickview` 兜底 · 这是 OpenAI 系模型的 tool selection 算法特性 · **描述层再改也就这个上限**

**推荐**:
- 需要 GPT 精确 hit hunter tool 的场景 → 优先 Claude Sonnet 5 或 Qwen 3.8 Max(6 家中 hit 唯二满分)
- 用 GPT 的场景 → 修复后至少不报错 · 用户看到的是"次优但可用"的结果

### 2.3 边界 case C1 · 3 家超时

"分析一下这只股票"(不给代码)· 期望模型说"请提供股票代码"就好。但 Gemini/Doubao/MiniMax 3 家都强行调 `question` 或 `watchlist_digest` tool · **进入无止境澄清循环 · 240s 超时**。**Claude / Qwen / GPT 3 家理解到"信息不足需澄清" · 直接返回文本 · 4-6 秒。**

**修复方向**: hunter-guard 可加"当 prompt 无实体标识时 · 优先让 LLM 直接回应而非调 tool"的短路逻辑。

### 2.4 MiniMax M3 的 `<think>` 泄漏(**修复前 · 已在 shim.py 修好**)

**症状(修复前)**: MiniMax M3 **每一个 case 的 assistant content 里都包含原始 `<think>...</think>` 段** · 前端不做剥离直接展示会露出内部推理链 · 且部分片段是英文思考中文回答混着。

**修复方案(双保险)**:
- **方案 A · 请求端**: 在 `shim.py` `sanitize_body` 里对 `model` 包含 `minimax` 的请求自动注入 `"thinking": false`(MiniMax 官方参数)· 关掉 think 输出 · 推理迁移到独立 `reasoning_content` 字段
- **方案 B · 响应端**: 在 `shim.py` SSE 流处理器加通用 `ThinkStripper` 状态机 · 跨 chunk 边界安全剥离 `<think>...</think>` · 兜底覆盖任何未来接入的 thinking 模型(Qwen thinking / Kimi thinking / GLM-Z1 等)

**修复效果**(2026-08-16 20:11 复测):
| 指标 | 修复前 | 修复后 |
|---|---|---|
| think_leak(7 case)| 7/7 全泄漏 | **0/7** ✅ |
| hit | 6/7 | 6/7(持平) |
| C1 边界超时 | 1(question 死循环)| 1(未变 · A/B 修不了 tool 编排问题) |
| 总耗时 | 426s | 541s(+27% · 但 case 间差异是模型 tool 编排变化 · 非 shim 开销) |

**shim.py 关键代码**:
```python
# 方案 A · request-side
def _maybe_inject_no_think(obj: dict):
    model = (obj.get("model") or "").lower()
    if "minimax" in model:
        obj.setdefault("thinking", False)
    elif "thinking" in model and "qwen" in model:
        obj.setdefault("enable_thinking", False)

# 方案 B · response-side · 状态机跨 chunk 剥离
class ThinkStripper:
    def process(self, chunk: str) -> str: ...    # 保留 7 字节尾巴防误伤未闭合部分标签
    def flush(self) -> str: ...
```

**紧急关闭开关**: `LLM_STRIP_THINK=0` 环境变量 · shim 会跳过剥离 · 出 bug 时不用改代码回滚。

**11 个单元测试全过**(byte-by-byte / cross-chunk / multiple blocks / unclosed / prefix-like-tag)· 见 `shim.py` 内注释和 `2026-08-16_2011_aihubmix-minimax-m3-fixed-final_v3_summary.csv`。

### 2.5 Doubao Seed 2.1 Pro 深度分析慢 3-5 倍

Doubao 在 A2(K 线)222s · B2(深度)145s · 全场最慢。可能是 aihubmix 到 ByteDance/火山引擎的中转延迟叠加。**如需 Doubao · 直连火山引擎 endpoint 会快很多**(见 `.env.doubao.example`)。

### 2.6 aihubmix 网关本身的观察

- **一 key 打通 30+ 家上游**: 极大降低试模型成本
- **完全 OpenAI-compatible**: hunter-community 零代码改动
- **cost_usd 字段全 0**: aihubmix 对 OpenAI-compat 通道不透传 upstream 成本 · 需要自己在 aihubmix dashboard 查账单
- **Meta AS32934 CDN + TLS 指纹拦截**: Alpine 容器直连不通 · 需 host proxy(见 §开头踩坑)
