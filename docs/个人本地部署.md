# 个人本地部署 · 记忆系统与受控自进化

> 对应 `1.6.0`。这份文档只讲**单人本机**部署那一档（`03 §5` 路径 B）。
> 只想跑六服务投研助手（postgres / redis / api / web / opencode / llm-shim）的，照
> `README.md` 的「5 分钟跑起来」即可，**不需要也不应该**叠加下面的覆盖文件。
>
> 覆盖文件与示例 env 在仓库根：`docker-compose.personal.yml` · `.env.personal.example`。

---

## 一、它是什么 / 不是什么

`1.6.0` 起，智能炒股多了一层「**经验 → 提案 → 独立影子验证 → 人工确认生效 → 紧急线回滚**」的闭环：

- **经验库**：复盘产出的结论、证据、冻结快照。防评估泄露是**零开关**（服务端永远只查
  `searchable` 且未被 holdout 污染的条目，没有任何参数能放开）。
- **提案层**：AI 只能提**白名单参数**，验证口径（`plan`）在知道结果之前就冻结、写后不可改；
  **AI 无权提案放宽风控**（API、数据库 `CHECK`、端到端三处都会被拦）。
- **影子验证**：候选臂有**独立模拟记账**，与现行臂同行情快照 / 同初始资金 / 同费率滑点；
  样本不足一律 `inconclusive`，**窗口结束前绝不通过**。
- **生效与回滚**：**只能人工确认**（`FIN_AUTO_APPLY` 恒为 0）；观察期只有**已冻结的紧急线**
  能自动把配置摁回上一个已验证版本，并顺手产出一条有证据的失败经验。

**不做的事（诚实边界，`03 §5` 要求写明）：**

1. **本方案不交付 `live`**。`FIN_LIVE_ORDER_ENABLED` 恒为 0，没有实盘订单出口，
   也没有接任何券商。
2. **「不可篡改」是对应用而言，不是对机器所有者而言。** 冻结计划由数据库触发器
   （`BEFORE UPDATE OR DELETE`）保护、状态事件另有**哈希链**兜底，两者都挡得住应用代码
   写错 / 被误改；但**本机文件管理员（库属主 / superuser）永远能 `ALTER TABLE … DISABLE
   TRIGGER` 再改库**。所以**不能宣称对机器所有者「绝对不可篡改」** —— 绕过之后能靠哈希链
   **发现**，不能靠它**阻止**。要真挡机器所有者，需要另起一个非 owner 的最小权限连接给
   API（迁移账号与运行账号分开），那是以后的事。
3. **「有记忆」或「有影子结果」不等于收益保证。** 影子成绩是模拟的，不是市场跑出来的绩效。

## 二、前置

- Docker + Docker Compose v2.24 以上（覆盖文件用了 `!override`，见下文「为什么」）。
- 能访问 GHCR（镜像公开发布，匿名可拉）。
- 本机端口 `5542 / 6579 / 8230 / 3230 / 4031 / 8291 / 8394 / 7291 / 8292` 未被占用
  （都可在 `.env.personal` 里改）。

## 三、第一次跑

```bash
cp .env.personal.example .env.personal
# 编辑 .env.personal：
#   · HUNTER_INTERNAL_KEY=<openssl rand -hex 32>   ← **必须非空**，见下「两个坑」
#   · FIN_PAPER_PASSWORD=<openssl rand -hex 24>     ← 要不要跑 paper 那一档
#   · 想让数据源 / 模型走本机自己的，填 LLM_* / DATA_SOURCE_PROVIDER / HUNTER_API_KEY
#   · **保持 FIN_EVOLUTION_MODE=observe**、FIN_MEMORY_ENABLED=0（P1 验收后再开到 1）

# 1) 先起最小三件（postgres / redis / api）—— 迁移在 api 启动时自动跑
docker compose -f docker-compose.yml -f docker-compose.personal.yml --env-file .env.personal \
    up -d postgres redis api

# 2) 检查：api 健康 + 迁移账本到 0045 + 起一次备份
docker compose -f docker-compose.yml -f docker-compose.personal.yml --env-file .env.personal \
    exec -T postgres psql -U hunter -d hunter -tAc \
    "select count(*) from schema_migrations;"     # → 46
docker compose -f docker-compose.yml -f docker-compose.personal.yml --env-file .env.personal \
    exec -T postgres pg_dump -U hunter -Fc hunter > ~/hunter-backup-$(date +%F).dump

# 3) 需要纸上交易 / 复盘 / 影子那一档时，再带 profile 起
docker compose -f docker-compose.yml -f docker-compose.personal.yml --env-file .env.personal \
    --profile paper up -d
```

> **记得每次都带 `--env-file .env.personal`。** 不带的话 compose 会去读仓库根的 `.env`
> （如果存在），端口与口令就是另一套了。也可以把它写进 shell：`export COMPOSE_FILE=docker-compose.yml:docker-compose.personal.yml`。

打开 `http://127.0.0.1:3230`。

### 起 paper 之前要建一次账本角色

账本运行期角色 `fin_paper_rw` 的密码**不进仓库**，要自己 provision 一次（幂等）：

```bash
COMPOSE_FILE=docker-compose.yml:docker-compose.personal.yml \
COMPOSE_PROJECT_NAME=hunter-personal \
FIN_PAPER_PASSWORD=<填 .env.personal 里那个值> \
  bash scripts/fin_provision_paper_role.sh
```

不跑这一步，`paper` 会以「连接账本库失败」反复重启。

## 四、启用记忆系统

按 `03 §6` 的顺序：**先观察，再影子**。

1. **P1 验收**：把 `.env.personal` 的 `FIN_MEMORY_ENABLED` 改为 `1`，然后
   `... up -d api`（**`up -d` 不是 `restart`** —— restart 不重读 env）。
2. 打开 `GET /api/v1/fin/runtime`（或直接看成长页顶部的运行模式横幅），确认
   `memory_enabled: true`、`evolution_mode: observe`。
3. **先连续观察几天的复盘与影子记录**，觉得可信之后，再把 `FIN_EVOLUTION_MODE` 切成 `paper`
   并 `up -d`。切成 `paper` 需要五个前置依赖健康（模拟账本 / 市场日历 / 行情快照 / 策略决策器 /
   验证调度）；缺一服务端会**自动降回 `observe`** 并在 `degraded_reason` 里写明是哪一项
   —— 这是按设计，不是故障。
4. 生效按钮**只在成长页**、且必须人工确认；`FIN_AUTO_APPLY` 与 `FIN_LIVE_ORDER_ENABLED`
   是非 0 就被服务端拒绝的硬开关，别改。

## 五、升级

```bash
git pull --ff-only
# 改 .env.personal 里的 HUNTER_VERSION / FIN_TAG（覆盖文件里镜像 tag 也一并改）
docker compose -f docker-compose.yml -f docker-compose.personal.yml --env-file .env.personal \
    --profile paper pull
docker compose -f docker-compose.yml -f docker-compose.personal.yml --env-file .env.personal \
    --profile paper up -d
```

迁移由 api 启动时按账本**增量执行**，只做加法，不需要手工跑 SQL。**升级前先 `pg_dump -Fc`。**

## 六、两个坑（实测踩出来的）

1. **`HUNTER_INTERNAL_KEY` 留空 → `paper` 拒绝启动。** api 留空时确实会自动生成一把写进
   `hunter_secrets` 卷，但 `paper` 与 `fin-worker` **不挂那个卷**，只读这个环境变量；
   留空时 `paper` 的启动自检直接拒绝（「服务间鉴权会形同虚设」）。六服务那一档可以留空，
   **fin 栈这一档必须显式设一个非空值**。
2. **`POSTGRES_PASSWORD` 只能在第一次 `up` 之前设。** postgres 只在**数据卷为空**时用它
   初始化；卷建好之后再改这一行，容器会以新口令去连一个仍记着旧口令的库 → postgres 反复重启
   （连带 temporal / api 起不来）。改口令的正确做法是改库里的角色。

## 七、为什么覆盖文件长这样（三条设计决定）

- **端口一律绑 `127.0.0.1`**：默认 `docker-compose.yml` 里 postgres / redis / api / web /
  opencode 五个的 `ports` **没有**回环前缀（实测 `0.0.0.0:5598` 之类），在个人机器上等于
  对局域网开着。覆盖文件用 `ports: !override` 把它们全部收到回环上。
  ⚠️ **必须是 `!override`**：compose 对 `ports` 是**追加**合并，普通写法会变成
  「原来的 0.0.0.0 映射 + 新加的回环映射」两条并存、第二条直接因端口被占而失败。
  `!override` 需要 Compose v2.24+。
- **fin 栈收进 `paper` profile**：默认文件里 `paper` / `temporal` / `temporal-ui` /
  `fin-worker` 挂在 `fin` 上；覆盖文件把四个都改挂 `paper`，与 `03 §5` 的操作顺序一致。
  ⚠️ **Compose profile 不会自动启用被引用的服务** —— `fin-worker` 的 `depends_on` 虽然写着
  `paper` / `temporal`，但三者都只在显式 `--profile paper` 时才起，**不能只 `up -d fin-worker`**。
- **镜像 tag 显式钉死**：覆盖文件里不写 `build:`。个人用户 `git clone` 之后不需要本地编译
  （根分区只有十几 G 的机器编不动 Next.js），一律从 GHCR 拉同一版镜像。
